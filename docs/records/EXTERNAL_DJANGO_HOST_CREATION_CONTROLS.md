## 新诊断把等待定位到了镜像复制链路

重试在未测量的准备阶段，每5秒记录本统计组进程CPU、存储读写和等待状态，共120点，跨度595.462秒。服务在13:26:30 UTC开始缺层镜像复制，直到13:36:19请求返回仍没有镜像解析完成、guest创建或ublk设备添加记录。

| 进程 | 最长记录跨度／秒 | CPU增加／秒 | 存储写入增加／MiB |
| --- | ---: | ---: | ---: |
| `server` | 595.462 | 1.60 | 310.590 |
| `regctl.real` | 580.454 | 2.51 | 128.137 |
| `uvm-ublk-daemon` | 595.462 | 0.00 | 0.000 |

`regctl`是镜像复制程序。通过本组同一进程的现场元数据，确认最长记录对应`regctl image copy`，并有两条到现有本机代理的已建立TCP连接。一次线程快照为8个同步等待、1个网络事件等待；最后约115秒里，该进程只增加0.680 MiB存储写入和0.02秒CPU，服务没有增加存储写入。

观察支持：较长等待在镜像复制／准备完成之前，长期进程没有持续消耗大量CPU；guest后段启动尚未开始。`write_bytes`是内核归给进程的存储写入，不是网络下载量；主线程等待也不代表全部线程状态。5秒记录可能漏掉短进程，因此不据此计算总转换CPU或断言代理、远端和转换中的某一个已被证明为根因。

固定源依赖中的`regctl`包装脚本只拦截旧Sphinx镜像；Django会进入真正的`regctl.real`。未更改这份源依赖或代理设置。
