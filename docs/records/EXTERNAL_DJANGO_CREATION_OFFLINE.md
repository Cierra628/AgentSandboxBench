## 结论：不再重复完整任务，下一项应单独比较本地镜像的创建

2026-10-30只读取[两对四次Django实验](EXTERNAL_DJANGO_SAMPLING_CONTROLS.md)的保存日志、事件和host采样表，没有新服务、guest、业务动作、网络请求或驻留查询，也没有更改运行代码和设置。四次原成功结果及完整用时保持。

第三次的较长等待主要在镜像准备；第一对的创建增幅却主要在现有镜像日志没有覆盖的部分。现有资料足以定位这两个不同问题，但不足以将它们归为网络、转换、磁盘或采样中的某一种原因。继续照原范围重复完整任务，不会补出缺少的阶段计时。

建议下一项只比较**镜像已准备好时，host周期采样是否影响创建**。这与原先包含镜像获取／转换的冷创建不同，应独立报告；原来+10.42%／+43.86%的创建变化仍保留。

OCI是容器镜像格式。这里的区间从“标准OCI开始后台镜像复制”到“解析为OverlayBD配置”，包含镜像获取、复制、转换和相关等待，不是纯下载时间。四次都记录同一镜像、10层，以及“至少一层尚未转换”；每轮使用新私有镜像缓存，后续实验并未复用前一轮的转换结果。

表中另有解析完成至创建标记的0.327～0.401毫秒，完整数值在证据JSON中。剩余用时为客户端单调时钟测得的总时长，减去服务端UTC日志中的三个区间；它是**持续时间之差**，不是已对齐的客户端／服务端时间线。原事件未保存UTC起止，无法把这部分进一步分为请求前段、解析前等待和启动后返回；不能直接称为网络耗时。

按开启减关闭分解：

- 第一对创建多10.893秒：OCI区间反而少3.262秒，启动多0.079秒，日志区间外多14.075秒。
- 第二对创建多47.198秒：OCI区间多51.136秒，启动多0.252秒，日志区间外少4.189秒。

两次ublk设备添加均在各自“创建标记→启动完成”的区间内，进一步说明第三次143.487秒不发生在该次设备添加和guest后段启动中。保存的server.log各34行，均无ERROR或retry文字；没有内部逐层记录，不能据此排除内部重试。

99%分位采用向上取整的排序位置。查询只读取`memory.stat`和`memory.current`；累计查询用时不含每0.1秒的休眠，也不等于任务增加的阻塞时间。现有记录没有创建窗口专属CPU计数，原0.453／0.496秒是host采样线程全生命周期CPU，不能重新标成创建CPU。

这些数字没有显示某次计数读取卡住几十秒。它们也不能给采样引起的间接延迟设上界：后台采样与服务并行，资源竞争的后果不由采样器CPU或读计数墙钟直接决定。

约4～5 GiB脏页是创建期间的实际观察。没有关闭组的连续脏页／I/O数据，也没有逐层I/O归属，不能确定写回是否造成等待；它提示镜像写入和转换是需要区分的候选原因，而不是已验证原因。此前准备后同步只约束基线，不能消除创建期间新写入的脏页。

## 下一步建议：一个服务、一次镜像准备、四次只创建对照

先确认固定服务支持复用转换后的镜像，并在现有隔离／冷创建／host采样组件上增加显式的只创建入口；旧任务入口和默认行为不变。已转换层可复用不等于完全不联网；如果解析仍访问镜像仓库，须记录该范围，不称为无网络的纯本地启动。现有七guest启动对照固定Prettier和guest采样，不能直接当成Django的host对照。

最小实跑范围建议为：

1. 一个新私有服务／统计组、原32 GiB卷，固定Django镜像。先创建并删除一个准备guest，单列镜像准备时间，不执行业务或上传采样程序。
2. 确认镜像准备完成，复用同一服务；每次在取基线前同步本次文件系统，随后按关闭→开启、开启→关闭依次创建和删除四个新guest。每个仍为2 CPU／8192 MiB，仅切换host的0.1秒采样，无guest采样。总计五个guest，其中一个用于准备，四个用于比较。
3. 保存客户端两种时钟起止、实际镜像解析日志、host采样次数／成本及清理结果。测量创建如果再次触发缺失层转换，就不满足本地镜像对照条件；停止扩展，保留现场并说明原因，不静默混入新一轮镜像获取。

新路径首个正式关闭组兼作必要验证，通过后完成剩余三次；不增加完整Django／C4动作，不调整回收、不额外预读任务文件。继续遵守分配前>58 GiB磁盘、>64 GiB MemAvailable和失败卷保留／定向删除规则。

完成条件是四次范围正确、真实开关、无业务／guest采样、无重新转换、有效计时及全部自有清理通过；报告每对有符号变化，不以结果必须接近零为条件。这只能回答已准备镜像的创建影响，完整冷创建里获取／转换造成的变动仍按上表保留。此建议尚未实跑。
