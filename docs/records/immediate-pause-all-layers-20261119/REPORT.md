## 四来源为何在本次对象上停止

运行时核实：直接后备是映射 guest RAM 的块设备 `/dev/ublkb2`，(st_dev, inode) 为 [6, 30364]；内存镜像配置指向的下层 (st_dev, inode) 为 [[1797, 1048837]]，由本批 provider 打开。与上述 19 个镜像文件匹配数分别为 **0/19、0/19**。已有直接后备查询以 guest PFN 经 RAM 映射换算偏移，下层查询再按内存快照区段换算（`scripts/snapshot_cache_residency.py:291–323`、`scripts/snapshot_layer_metadata.py:64–108`）。磁盘镜像文件页号不是输入的 guest PFN。即便另挂探针读出普通文件自己的 PFN，也不代表这两种来源。本次在此停止：两种来源均未发出 PFN 查询，调用 0 次、实际查询 0 页次，耗时无数据，不按零耗时计。四来源总耗时及其是否在 1 秒内均无法判定。这不是暂停使 PFN 接口失效。

## 两个比较回答不同的问题

- 1,358,865 ÷ 37,352 = 36.38。前者是整套镜像文件的宿主驻留偏移数；后者是历史恢复实例的 guest 缓存经归属核实、按物理页去重的页数。镜像准备时已复制和校验文件，文件也可被服务使用。**数量更高不能证明立即暂停保住了 guest 缓存峰值**，也不能说明驻留是本分支引起的。没有不暂停的同对象对照。
- 数值上本轮文件扫描页数是上轮 9,750 页次的 139.37 倍，全文件扫描墙钟是上轮 208.030 ms 的 0.493 倍。上轮的分母是候选页在 RAM 后备与内存快照下层各查两遍的页次；它还读取了 provider 和 VMM 页表。本轮按文件长度枚举每个偏移一次，没有候选集合。工作量变化来自**更换了对象与查询操作**，不能解释为同一个四来源流程中“候选更多”或“文件变大”。两次测量都只是单分支。
