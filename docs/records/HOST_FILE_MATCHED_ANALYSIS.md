## 已确认的现象与尚不能归属的部分

- **未见同步的组内shmem增长。** shmem在这段窗口不变，且整个双沙箱任务窗口相对恢复前只增加8 KiB；原有约7.082 GiB输入tmpfs镜像属于公共准备。
- **不只是已映射文件页增加。** 快速增长窗口file_mapped仅增加2.961 MiB。任务内两次邻近VMM文件PSS总和在0.122秒和1.123秒约为181.178／181.863 MiB，也没有与file同步增加约515 MiB。file_mapped和PSS覆盖的都是映射范围，不能据此否定未映射文件缓存的实际增长。
- **确有同期写回活动。** 0.321898秒file_writeback读数为36.879 MiB；稍后的1.323—1.423秒，脏文件页读数从约194 MiB降至约2 MiB。整个任务的脏页范围为2.160—493.965 MiB，说明背景写回状态并未保持不变。脏页转为干净页本身不要求file减少；经loop写回也可能增加后备文件的缓存副本，但现有数据没有把该机制与这514.559 MiB逐页关联。
- **不能认定只是统计汇总延迟。** 同期memory.current也增加577.805 MiB；但两个文件顺序读取、各计数的更新方式不同，不能把它当作同一瞬间的逐页证据。此前小镜像已实测统计延迟，本轮未采集统计汇总完成事件，不能指定这一段发生了多少延迟汇总。

当前缺少这个时间段按文件身份和偏移记录的缓存页加入／移出事件及实际记账组。最终普通文件清单只在guest和服务退出后查询；运行时设备查询也在任务后，不能用后来驻留反推0.3秒窗口的来源。**已有证据足以排除部分误读，不足以把约515 MiB全部分配给某个镜像、文件或机制。**

源码核对使用此前定向校准对应的本机`6.19.9+`源码树`/home/yxli/linux-6.19.9-ioctl/`：`mm/memcontrol.c:1463–1490`在格式化memory.stat前尝试汇总；`597–649`的阈值和强制汇总路径表明尝试不等于完成；`drivers/block/loop.c:1870–1925`表明loop后备I/O按请求的I/O组取得内存记账组。这些是机制依据，不是本轮写回来源的事件证明。已有[逐页记账校准](HOST_LOOP_CHARGE_ATTRIBUTION.md)保留其原结论。

## 哪些可以验收，哪些仍未完成

| 验收对象 | 判断及可交付内容 |
| --- | --- |
| 轻量host监控工具 | **可以按限定范围验收。** 每0.1秒记录统计组file、anon、current等，每1秒记录PSS；创建顺序、I/O记账条件、身份、数据和清理已验证。file是组内记账曲线，不保证0.1秒物理变化已经汇总。 |
| 指定共享内存设备驻留 | **当前短任务范围已验证。** 实际两个VMM使用同一个4 GiB设备，按设备只计一次；单／双沙箱分别407.309／398.676 MiB。mincore查询不是内容读取，保留各自扫描窗口。 |
| 完整文件缓存记账 | **仍有缺口。** 最终11根190文件的mincore为26.962662 GiB，组内file为26.961269 GiB，净不足1.425781 MiB。小镜像已证明真实组外页和汇总延迟存在，但没有证明本轮差额的逐页原因。 |
| 全部host物理内存节省、guest缓存对应的物理并集 | **尚未完成。** file遗漏组外页，PSS遗漏未映射缓存；现有不同窗口、不同覆盖范围不能相加或直接与guest Cached相减。两组guest缓存状态不同，匿名PSS也从155.027增至336.086 MiB，不能只看共享设备驻留近似不变。 |

1.425781 MiB是两种范围读数的净差，不是实际组外页总量或整体误差上限，不能因它相对26.96 GiB很小就宣布完整记账。当前机器输出`SHORTFALL_REQUIRES_RESOLUTION`继续保留，不为了监控工具验收而改成PASS。

指定设备相对单沙箱线性参考少51.06%，可作为明确标注条件的参考数字；它没有实测不共享后端，也不是全部host内存节省率。这里的问题不只是缺一个“不共享”组：即便继续采用用户提出的单沙箱换算，也必须先有覆盖范围一致、起始缓存条件可比较的A和B。
