## 40次请求的额外工作仍有明确边界

“合并2页空隙”指两个原请求区段之间最多缺2页时，将它们放入一次mincore调用。多个空隙可以连续连接，因此仍按首末偏移的完整跨度查询，不把原请求数误当作跨度。页大小4096字节。

| 全会话数量 | 当前：合并1页 | 候选：合并2页 | 候选相对当前 |
| --- | ---: | ---: | ---: |
| mincore调用次数 | 59756 | 49952 | −9804，−16.41% |
| 原请求去重页次 | 806414 | 806414 | 保持 |
| 查询页次 | 830814 | 850422 | +19608，+2.36% |
| 相对原请求多查页次 | 24400 | 44008 | +19608 |
| 每张表最大键数上界 | 66035 | 66905 | +870 |
| 每张表剩余容量 | 65037 | 64167 | −870 |
| 40次整表读取条数上界合计 | 2548336 | 2582110 | +33774，+1.33% |
| 单次调用最大跨度/页 | 2048 | 2048 | 保持 |

原请求去重页次是每次查询内去重后再跨请求相加，前后请求均计入；不是当前缓存容量。整表条数上界是按每次查询结束时的键集合计算，再对40次读取求和，不是两张表的最终键数相加。

本批输入中，每少一次调用需多查2页。原请求和额外页仍触发既有查询处理，因此是否节省时间，关键是少做一次调用的固定成本能否抵消这2页的额外处理。

前置两次查询共20次，是guest前后表之间的耗时来源之一。这部分调用单独从29878减到24976，少4902次；查询页次从415407增到425211，多9804页次。不能按调用次数下降比例折算原81.864 ms前置mincore循环。

## 每张表必须同时计入两层的键

本次直接复用[既有内核与跨层容量证据](PROVIDER_MINCORE_MERGE_REVIEW.md)，没有重复研究内核源码。保存的`snapshot_cache_residency.py`和`live_task_cache.py`与当前源码逐字一致，内核版本仍为`6.19.9+`。

`snapshot_cache_residency.py:113–125`中的探针按采集器进程号筛选，键是文件页偏移，不区分直接后端和原始层；两张表都会记录这两层的查询。`live_task_cache.py`在启动采集线程前建立两个查询器，因此容量按整个会话、两层偏移的并集计算。相同数字偏移在表中是同一个键，不能把两层键数简单相加；筛选仍依赖当前查询号和本次原请求集合。

按保存计时恢复真实串行顺序：每点依次为直接后端前查询、原始层前查询、直接后端后查询、原始层后查询。当前1页策略的40个逐次键数预测全部与实际整表返回条数相等，最后每张66035键；原请求缺失统计均为0。该对照支持在同一输入上计算2页策略的键数上界。

候选最终66905键，容量没有成为本批输入的阻塞。它不是任意任务规模的容量保证；后续真实查询仍须保留缺失统计，读取到表尾不代表所有探针更新都成功。无需扩大表、清表或增加回退。
