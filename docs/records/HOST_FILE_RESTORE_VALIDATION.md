## 实际完成的范围

成功运行只执行Prettier原共同前缀11步，保存一次，删除父guest；先从同一个实际快照恢复1个guest，删除后再恢复2个guest。每组在全部恢复检查及采样准备通过后正常运行5秒，无后缀或官方评测。各guest为2 CPU/4096 MiB，沿用普通内核，没有改变回收策略或为采集额外暂停。原生保存的暂停与测量分开。

新统计组在输入准备前建立，私有服务及guest从创建时在组内；创建父guest前Firecracker为0，三个池和预热开关关闭。三次恢复的文件边界、原guest探针进程连续性通过；三个新sandbox ID和host VMM身份分别关联。恢复guest的boot ID可以相同，不使用冷启动时的不同boot ID条件。

两次恢复前基线相差5.086 MiB。输入准备完成、首次创建父guest之前，file已经为20.813 GiB；不能把此前冷启动实验约14 GiB的基线套到本次。

本次恢复入口会复制一份镜像commits，冷启动只读路径则绑定原commits。原始输入和私有副本的设备号/inode不同，确实是不同缓存对象。这解释了本次公共准备范围更大，不能将这些成本重复外推成沙箱共享收益。依据为`validate_isolated_agentenv.py`的`copy-immutable-cache`及后续只读绑定条件。

图上三行host数据对应同一个5秒区间；底行guest曲线覆盖各自采样程序的完整存活时间，包含检查准备及区间后的驻留查询，两种时钟没有强行对齐。guest Cached与host file不是同一层，两者不相减。当前默认后台回收保持，曲线变化不逐段归因于某个回收动作。

## 运行时设备驻留已取得真实数据

在每组5秒区间结束后、guest仍运行时，按实际VMM映射查询设备；用设备身份与容量检查，不使用块设备的`st_size=0`。查询完成关闭自己的句柄，然后删除guest，确认设备释放后才开始下一组。

N=2的两个VMM都以私有可写映射使用同一个内存设备，清单只计一次。两组之间设备经过释放和重新创建，不能只凭重复的设备路径就认为它一直存活。

| --- | ---: | ---: |
| 4 GiB内存后备设备的host缓存 | 326.172 MiB | 321.523 MiB |

内存设备的缓存包括快照中的程序、内核及缓存等数据，也可能保留写时复制前的页；它不等于当前guest Cached的物理对应量。原始层与设备缓存是不同对象，不因内容有关就合并；运行中的逐项驻留也不是原子物理快照。匿名副本继续通过anon和PSS观察，不混入上述设备量。

两组运行时清单均未检测到大于同期file的差额。最终普通文件清单发生在另一个时间窗口，见下一节；两次检查不能相加。

## 最终清单暴露了4.232 GiB记账差额

私有服务及写入进程停止后、卸载前，138个保留普通文件按设备号/inode去重查询，全部文件稳定。

| 来源 | mincore全局驻留 |
| --- | ---: |
| 只读输入commits，31文件 | 6.685 GiB |
| 私有image-cache，101文件 | 6.686 GiB |
| 输入RAM中的20 GiB loop镜像 | 7.082 GiB |
| 本次24 GiB私有loop镜像 | 5.611 GiB |
| 保留快照仓库及运行配置，4文件 | 约0.538 GiB |
| 合计 | **26.602 GiB** |
| 检查前后统计组file | **均22.370 GiB** |
| 需要解释的差额 | **4.232 GiB（4333.316 MiB）** |

报告已标记`accounting_validation: SHORTFALL_REQUIRES_RESOLUTION`，与`functional_validation: PASS`分开。file仍是主曲线，但不能单独代表本次文件的完整host占用。另列清单全局驻留及窗口内驻留下界参考，不将mincore总量直接加到file，不把差额当作节省。

离线分项后，除去私有loop镜像这一项，其他文件清单合计20.991 GiB，小于file；加入该镜像后才出现不足。因此下一步优先检查私有loop镜像的记账路径，**保留该镜像在总量内**。这项范围核对没有确定每一页记在哪个组，也不能据此断言全部差额来自loop。

本机`6.19.9+`的构建源码提供了一个具体方向：`/lib/modules/6.19.9+/build`指向`/home/yxli/linux-6.19.9-ioctl`。`drivers/block/loop.c:1878–1885`从I/O请求的blkcg（块I/O统计组）取得memcg（内存统计组），`1914–1924`在执行后备文件I/O时切换到它，而不是简单沿用最初写文件进程的内存组。内核配置启用MEMCG、BLK_CGROUP和CGROUP_WRITEBACK。

该次实验时systemd默认`IOAccounting=no`，入口仅显式设置了`MemoryAccounting=yes`，没有保存运行时I/O控制器状态和逐页记账来源。后续小镜像已验证这个条件对新增后备缓存归属的影响，新入口已改为同时开启两项；仍需取得新设置下的大卷结果，才能量出旧差额中的相关部分。

## 已修正的检查问题与实际成本

第一次尝试在N=1运行时查询后被稳定性检查拒绝，未进入N=2。原检查要求块设备节点的修改时间不变，但运行中的可写磁盘允许该时间变化。现在块设备核对身份与前后容量，并单列时间戳变化；普通只读文件仍要求大小和修改时间稳定。修正后实际记录到可写设备时间戳变化，而身份和容量保持。

第一次拒绝前没有保存逐项结果，无法事后确定是哪一项触发。代码已改为判定前保存完整查询结果；原FAIL不改写，24 GiB失败卷及快照状态保留。两次尝试共执行22个共同前缀动作、创建2个父guest及4个恢复guest；完整任务和后缀执行次数均为0。

成功运行全流程1418个host点，最大间隔0.100159秒；5个guest采集会话共368点。host线程累计1.592 CPU秒，其中计数读取0.410秒；最终普通文件mincore另用1.739 CPU秒。

当前运行时全清单扫描偏重：N=1/N=2分别3.302/4.812进程CPU秒，主要是额外扫描两个/三个64 GiB磁盘设备；各内存设备查询本身用时约0.107/0.110秒，原始层约0.016秒。驻留查询发生在主观测区间后，但guest仍继续运行，成本没有消失。后续应优先保留内存设备及原始层查询，其他磁盘仅列身份与未覆盖范围，避免为轻量测量扫描全部64 GiB地址空间。本次数字按实际全清单保留，没有改写成优化后的成本。

20项host相关、9项原分支及27项隔离存储检查通过；报告增加记账状态后另补离线回归通过。没有关闭host采样的任务对照，本次CPU时间不换算成任务减速率。
