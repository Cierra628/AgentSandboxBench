# BPF表批量读取离线核对：建议按容量一次读完（2026-10-16）

**源码和已安装库支持进入私有验证，首选只读、按表容量一次读取，而不是分小批循环。** 当前瓶颈是四次后端/原始层查询，合计300.538 ms CPU；批量接口可减少其中的逐页BPF表读取，但不会减少`mincore`驻留查询。本阶段完成了支持条件、错误语义和最小方案核对，没有实现运行分支、访问真实BPF表或启动沙箱。

[脱敏证据](evidence/provider-bpf-batch-20261016.json)保存环境、来源及数量；本机目录为`.artifacts/provider-bpf-batch-20261016/`，源码副本和23项锚点核对在其中。现有采集和缓存物理并集保持，不把方案评估写成批量实测。

实际内核`kernel/bpf/syscall.c:5620–5651`将只读批量命令分发到表自身的读取方法，只检查读取权限；`hashtab.c:2244–2260`为HASH表登记批量方法，`1917–1922`选择不删除的实现。它不要求更换内核、删除记录或冻结表。

## 接口是遍历表，不是按一组输入键查询

`bpf_map_lookup_batch`的键、值缓冲都是**输出**；第一次输入游标为NULL，后续游标用于继续遍历，不能把待查偏移数组当成输入键列表。[libbpf接口说明](https://github.com/libbpf/libbpf/blob/v1.3.0/src/bpf.h)给出的7个参数依次为表FD、输入游标、输出游标、输出键、输出值、数量指针及选项。

在本机64位ABI中，数量指针指向32位无符号数；HASH游标在实际内核中也是32位，分配8字节游标缓冲足够。选项传NULL使两个标志都为0。将返回类型声明为有符号`int`，按负errno解释返回值，不能一律当作`-1`。

实际内核`hashtab.c:1669–1897`的行为决定了以下处理：

| 返回情况 | 含义和最小方案的处理 |
| --- | --- |
| `-ENOENT`，数量大于0 | 已到表尾，但本次仍带最后一组有效记录；先读取指定数量，不能整批丢弃。 |
| `-ENOENT`，数量为0 | 空表或已到表尾；没有取得的请求偏移仍为未知。 |
| `0` | 一般接口允许尚未遍历完。本方案一次给足整表容量，若仍出现该返回，则完整性检查失败，不把它当作已读完整表。 |
| `-ENOSPC` | 输出容量容不下同一哈希桶内的记录。本方案按实际整表容量分配，正常静止HASH表不应出现；明确报错，不盲目重试。 |
| `-EFAULT` | 用户缓冲地址出错，返回数量不可信；丢弃本次输出并报错。 |
| 其他错误或数量超过容量 | 不使用本次输出，记录失败，不静默切回逐页分支。 |

非`EFAULT`错误时，通用接口可能仍给出已处理数量；最小实现只消费已正常到表尾的结果，避免引入部分遍历恢复逻辑。表尾数量小于容量是正常情况，不要求等于请求页数；其中缺少或标记不符的请求行继续保持未知。

## 推荐的最小改动

为`SnapshotCache`增加默认关闭的批量选项，仅私有新路径显式启用。旧逐页调用不新增库符号、表布局或内存预算前置条件；批量不支持或检查失败时明确失败，不自动退回旧路径伪装成功。

1. **复用现有创建时取得的map info。** 新模式只接受预期的普通HASH、键8/值16字节、`map_flags=0`，以及正数且不超过131072的容量；从同一自有表取得信息。旧代码当前只使用这些信息中的表名，可将完整信息留下，无需枚举其他人的表。
2. **按实际容量预分配并复用接收缓冲。** 每张表的键和值缓冲最多`131072×(8+16)=3145728`字节，即3 MiB；直接后端和原始层两张表合计6 MiB。该数仅是接收缓冲容量，匹配结果的临时内存另计，实际驻留量仍需实测，均不能加进guest缓存的物理并集。
3. **原查询顺序不动。** 仍先写入本次查询号（token），按原范围执行全部`mincore`，返回后只读整表一次。当前单采集线程按顺序执行四次查询，前后观测次数保持；只替换其后逐页`bpf_map_lookup_elem`的部分。
4. **按请求偏移和查询号筛选。** 只接受本次请求、查询号相同、PFN非零且驻留位为1的记录。历史查询号、未请求键和尾部未返回缓冲不参与归属；按原输入顺序和重复次数还原无符号64位结果。输入无文件偏移（`UINT64_MAX`）时，输出仍为0且不增加缺失计数；这个0表示未确认PFN，不表示物理占用为零。
5. **缺失统计原义保持。** 请求键没有记录或查询号不符才增加原`missing_kernel_results`，按原输入行计数；查询号有效但PFN为0是“有查询结果、未确认物理页”，不能改成丢失结果。新增模式、返回码、返回条数及表信息另记，不改原指标含义。

选择整表容量，是因为当前表有明确上限；在表无写入期间，所有桶的记录都能放下，应一趟到达表尾。小批遍历还要处理游标推进、桶放不下及多次调用，当前没有必要。使用只读lookup接口，不使用lookup-and-delete，也不清表、停探针或延迟设备请求。

这里“表无写入”仅指采集器的BPF元数据表，不是要求guest缓存或沙箱停止变化。项目程序只记录本进程的`mincore`调用；本次私有流程只有一个采集线程，原查询返回前不会开始下一次查询，正常关闭也在采集线程退出之后。因此，完成`mincore`至批量读取结束之间没有新的本流程写入。

过滤条件按进程号而非线程号，以上论证不覆盖同进程并发执行`mincore`的用法。最小分支先只用于当前私有单采集线程流程，不为其他调用新增串行化要求，也不以此扩大原缓存有效窗口。

## 已有数量与验证条件

只读最近一次短恢复的20份后端/原始层数组，并与40次查询日志核对：原逐页表查找共829584次，平均每点82958.4次；另有76290次`mincore`调用。请求过的不同偏移共54308个，这是请求集合，不是实际表条数。20份输入的inode、大小和修改时间保持。

若每次都完整一趟读完，表读取将由829584次变为40次；40次查询号写入和76290次`mincore`保持。整表扫描会读取历史键并增加数据复制，所以不能按调用次数比例推算CPU降幅。当前300.538 ms是整个查询方法的成本，不只是逐页表读取。

本阶段未运行行为测试：只做源码、库文件和保存数据核对。实现后的必要检查为：

- 合成返回覆盖空表、带数据的末尾、旧查询号、PFN为0、额外键、重复偏移、无文件偏移、缓冲未返回部分、数量越界、`EFAULT`和不支持错误；不得把错误或缺失写成零占用/PASS。
- 用一张新建、未固定到文件系统的自有HASH表做一次小型接口检查，保存实际map info，比较旧逐项读取与批量还原的合成键值；关闭自有FD后释放，不访问既有表。
- 接入沙箱前另核定一次既有3/10短恢复范围，继续检查内容、恢复、独立PFN集合及实际分项CPU，报告新增采集器内存开销。

23项源码锚点和数量核对通过，支持“进入显式私有验证”的判断。运行代码、当前确认物理并集及已有任务结果保持；本次源码评估到此结束。
