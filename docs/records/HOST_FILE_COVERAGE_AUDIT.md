# host记账残余与文件清单的离线核对（2026-10-20）

**已把两个问题分开：小loop的约1.125 MiB差额属于合成数据写入前已存在的初始化阶段差异；大卷多出的359.023 MiB则有明确的清单缺项。** 最值得先补的是输入和私有卷各一份的`deps`依赖文件，两份逻辑大小合计360.596 MiB，与359.023 MiB接近，但旧记录没有它们的mincore驻留量，当前不作等量扣除。

本次只读取既有JSON、执行时保存的脚本及对应host源码，没有启动服务、沙箱、loop或新负载，也没有重新查询后备文件驻留。既有曲线和原始结果保持；本段完成标准是残余分类、源码依据和最小验证条件齐全。

## 小loop能确定到初始化阶段，不能确定每页归属

复算[小loop原始对照](HOST_LOOP_ACCOUNTING.md)，以下单位为4096字节页。这里的“差额”是镜像／内部文件全局驻留减测量组全部file记账，不是已经找到的组外物理页数。

| 阶段 | 关闭I/O记账：驻留 / file / 差额 | 开启I/O记账：驻留 / file / 差额 |
| --- | ---: | ---: |
| 格式化、绑定、挂载、同步后，写合成文件前 | 317 / 34 / 283 | 325 / 33 / 292 |
| 写入64 MiB并同步后立即查询 | 33085 / 16428 / 16657 | 33093 / 32805 / 288 |
| 再等待2.2秒后查询 | 33085 / 16429 / 16656 | 33093 / 32805 / 288 |

开启组初始化时镜像已驻留325页，即1.270 MiB。文件在本轮以独占方式新建，记录采集于合成文件创建之前，因此这批镜像驻留可列为**初始化阶段的镜像缓存**，不算64 MiB数据负载产生的缓存。它包括本轮格式化、设备识别和挂载可能产生的访问，现有记录不能再分到每个动作。

初始化差额为292页（1.141 MiB），最终差额288页（1.125 MiB），减少4页（16 KiB）。新增驻留128 MiB，file增量128.016 MiB，新增数据的记账对照仍然通过。所有这些检查中，外层file减测量组file在开启组均为0；**没有证据把残余定位到这个外层组**。外层以上的记账和统计未更新仍需区分，残余不记零。

### 源码支持两条待区分的解释

使用运行记录中的host `6.19.9+`及其构建目录`/home/yxli/linux-6.19.9-ioctl`，不是其他版本的通用结论。

- **统计可能尚未汇总。** `mm/memcontrol.c:535–649`：读取时只有更新量超过`MEMCG_CHARGE_BATCH × 在线CPU数`才同步汇总，另有周期工作；`include/linux/memcontrol.h:332`的批量值为64。核查时128 CPU对应8192次页量级更新阈值（按4 KiB换算32 MiB），这不是允许漏记32 MiB的验收标准。执行时保存的`host_file_monitor.py:33–40`直接读取`memory.stat`，没有强制汇总；2.2秒固定等待和前后值一致不能独自证明对应页已汇总。旧结果没有保存汇总事件，不能将1.125 MiB全部归因于延迟。
- **其他组可能在初始化时先缓存了镜像。** `drivers/block/loop.c:1092`发出设备变化事件；本机`/usr/lib/udev/rules.d/60-persistent-storage.rules:6–10,123–133`允许loop进入文件系统识别并调用`blkid`，除非前面规则明确禁用。udev是host设备管理服务，不属于本轮测量组。结合`loop.c:1870–1924`按请求I/O组选择内存组的路径，以及内核文档`cgroup-v2.rst:1961–1972`中页记账不随后来的访问者迁移的规则，组外设备识别是具体候选原因。旧记录没有该次识别请求和逐页归属；当前规则只能证明这条路径存在，不能证明它产生了288页残余。

mincore本身不能回答页记在哪个组。`mm/mincore.c:111–145`检查文件缓存页是否存在且内容有效，返回驻留位，不返回内存组。现有保存结果也只保留每文件页数，没有驻留位向量或物理页身份，不能离线补出页归属。

| 来源 | 旧记录能确定的范围 | 处理 |
| --- | --- | --- |

| 原始内存层文件 | 两次运行时均551.734 MiB；按设备号／inode核对，它也出现在最终清单 | 不跨时间重复相加 |

两份deps属于两个文件系统中的文件，私有卷的loop后备镜像是另一层缓存，包含该镜像不等于已经查询了内部deps文件缓存。执行时保存的`validate_isolated_agentenv.py:613–631`确认复制并核对这些依赖；最终清单根路径在`1166–1168`没有加入两份deps。逻辑大小只说明清单缺项的规模：没有驻留结果，不能按360.596 MiB修正file或宣布359.023 MiB已经解释完。

上述10个遗漏可写路径按长度向上取整共31页（0.121 MiB），不是其实际驻留量，也不是最终驻留上限：列表比最终查询早，文件可能继续变化，且未保存inode，路径去重不等于物理去重。

另一个已解释的大项是输入RAM镜像：驻留7,604,273,152字节，即7.082 GiB，其创建于tmpfs（以内存作为存储的文件系统）的过程有脚本和回执。同期`shmem`前后均恰为同一数值。`file`包含tmpfs，因此主曲线包含这笔准备开销；不能把这7.082 GiB当作guest任务文件缓存。`file−shmem`可辅助阅读，但仍不等于guest缓存或共享节省，主曲线定义保持不变。

### 为什么359 MiB不能当作“记账完整”的证明

把清单驻留记作I、统计组file记作C；清单中记到组外的部分为M、组内没有被这次清单驻留数覆盖的缓存为U，统计与查询时间差为E，则差值可写成：

```text
C − I = U − M + E
```

本轮只确定左边为+359.023 MiB，没有分别测出右边三项。缺项U可能掩盖M；这个差值既不是M的上限，也不能拿来抵扣小loop的初始化残余。当前可用结果是组内file曲线、已列来源的全局驻留，以及独立的映射内存PSS；共享节省比例继续留空。

## 最小改动与后续验证条件

**清单改动优先补两份deps。** 后续经授权修改入口时，复用现有`residency_check()`，在原六个根路径之外增加输入和私有deps，以及已确认遗漏的logs、persisted-sandboxes、template-builds目录；仍按设备号／inode去重。无需改后端、主曲线、guest或PSS。完成条件是新增文件身份、驻留及前后file计数齐全，缺失量重新分类；不要求差值恰好为零。当前已清理成功卷，不能用清理后状态重建旧驻留，此次未修改在线入口或重跑大卷。

**初始化定位只需一个小镜像，不需沙箱。** 建议下一次仅开启I/O记账，创建一次128 MiB镜像，不写64 MiB合成文件；在格式化后、loop绑定后、挂载同步后分阶段保存镜像mincore和内外组计数，保留各查询时刻与实际控制器状态。这样先确定差额最早在哪一步出现。若仍要判定是统计延迟还是组外归属，需要对应统计汇总事件或同一缓存页的归属证据；不能仅延长等待或以差额很小代替证据。页身份、释放或事件丢失无法核对时继续保留未知量，不预读、锁页、关闭全机设备管理服务或清理全局缓存。

本段的离线分类及源码核对已完成。上述一次小镜像定位随后按用户授权完成，见[分阶段结果](HOST_LOOP_INITIALIZATION.md)：首个可见差额在格式化后、loop绑定前，最终残余289页（1.129 MiB），归属仍未知。此后清单入口已补入确认缺项，并完成[一轮真实采集](HOST_FILE_EXPANDED_RESTORE.md)：新增52文件实测360.898 MiB，补齐后不足1.766 MiB。旧288页、旧六根清单及359.023 MiB记录保持，不追溯改写。
