## 先明确要回答的问题

问题是：在现有“准备镜像后再运行任务”的流程中，共用文件与每个沙箱持有独立文件相比，指定文件的host缓存实际少占多少？

这与“任务按需读入了多少缓存”不同。五轮冷启动的N=1／7共10个保存点中，19个系统盘下层文件都已经全部驻留；每套文件长度为5,565,854,720字节，按4096字节页计驻留5,565,911,040字节，即5308.066 MiB。最后一页按整页计，因此驻留容量略大于文件长度。已有代码准备时复制并校验镜像层，故不能把这批全部驻留的容量说成11个任务动作新增的缓存。

旧的约31.1 GiB来自七份容量换算。新对照改用两组实际驻留相减，并分别保留准备后的差值和运行后的差值。若主要差异在准备后就已存在，应直接报告为准备好的文件缓存共享收益，不归给任务按需读入。

## 复制范围固定为19个文件

使用五轮冷启动中顺序、引用和大小均一致的19个`user_rootfs`下层文件。每套约5.184 GiB；两个独立副本共约10.367 GiB文件内容，驻留多少仍由查询决定。

| 对象 | 共享组 | 独立副本组 |
| --- | --- | --- |
| 19个指定系统盘下层文件 | 一套文件，两个guest实际引用同一组inode | 每guest一套，共38个不同的文件身份 |
| 其他镜像层、配置、索引和工具盘 | 原准备规则，两服务各自所需资源 | 与共享组保持相同规则 |
| 每guest的可写upper和保留卷槽 | 各自独立，原行为 | 各自独立，原行为 |
| 快照内存设备／原始内存层 | 不创建、不导入 | 不创建、不导入 |
| 公共种子、归档、准备源 | 单列，不乘沙箱数量 | 同样单列 |

文件使用正常复制，禁止硬链接、符号链接替代复制或reflink；不因digest相同合并不同inode。准备源不进入目标容量，但若出现在组内file中，仍按上下文如实保留。只改变这19个文件，不能顺带把全部31个镜像层都改为不共享。未来若实际引用出现第20个未列对象，应先查清变化，不自动扩大清单或填0。

## 优先使用两个相同私有服务，避免修改后端

每组在新建且开启内存／I/O记账的父cgroup中启动两个私有服务，每服务创建一个guest。两组的服务数量、二进制、配置、采样及创建顺序一致；各服务使用独立状态目录、端口和不冲突的网段。原服务不替换，预启动池关闭。

共享组把第一套指定文件以只读绑定挂载方式提供给两个服务，容器内原路径不变；第二个服务准备时跳过这19个文件，避免留下不再使用但仍驻留的副本。独立组分别复制这19个文件到两个自有目录，再以同样的只读方式提供给各服务。其余文件按相同规则准备。不要把共享组文件绑定到RAM准备源、却把独立组放到磁盘卷；两组目标文件都使用自有磁盘ext4卷。

选择两个服务的原因：现有入口已经支持只读绑定commit目录，OverlayBD会打开实际本地文件；通过挂载即可改变文件身份，不需要给镜像解析器新增逐沙箱选项或编译实验后端。两组都用两个服务，避免把一个服务与两个服务的差异混入对照。相应结论适用于这19个文件的host缓存，不评价同一服务内的内存设备共享或调度性能。

离线确定时原入口不能直接执行这个对照。本轮接入项是：显式文件清单的准备／只读挂载、同组两个现有私有服务的生命周期协调，以及两服务活对象合并查询。每组两个guest完成后都保持正常运行，立即查询，查询完再按原流程删除；不暂停guest，也不为等待缓存变暖增加停留时间。失败和等待必须有超时，清理只针对本组资源。

## 相同任务阶段与两个查询点

两组都执行Prettier原共同前缀`read_repo`、`read_typescript`，每guest原11个动作。每组22动作，一对44动作；不运行后缀、保存／恢复或完整GRPO／BPO。

1. **P0：准备完成、两个私有服务就绪、guest尚未创建。** 对自有文件系统执行`sync -f`，保存`file_dirty`／`file_writeback`，记录同步开始、结束与查询时间。随后按清单对目标文件去重查询一次，同时保存组内file上下文。同步只写回，不清缓存，也不保证这些计数恒为零。
2. **P1：两个guest都完成相同11动作、删除前。** 从活VMM配置确认实际lower顺序、文件身份及服务打开描述符；立刻查询同一目标清单。每组每点各实际文件只查一次，共享组19个、独立组38个。保存查询起止和线程CPU时间，查询不是原子快照。

P0清单来自准备元数据，P1必须补上实际使用者证据。P0→P1包含guest启动和原前缀，不称为纯工具执行阶段。两个guest按相同顺序创建，全部就绪后并发运行前缀；两组执行同一顺序，不再在中途插入N=1驻留查询。guest／host周期采样仍为0.1秒，PSS关闭、默认回收，不清缓存、预读、强制驻留或关闭DAMON。

现有共享采集器默认排除单使用者文件，不能直接用于独立组。新对照必须按明确的实验清单查询两组文件，并核对共享组每对象两个使用者、独立组每对象一个使用者；旧入口的共享筛选不变。不能因为独立组文件不共享就漏查其驻留。

## 主指标直接相减，准备和运行分开

令共享组两个点的目标驻留为`S0、S1`，独立组为`U0、U1`：

- 准备后容量差：`D0 = U0 − S0`。
- 前缀结束容量差：`D1 = U1 − S1`；当`U1 > 0`时比例为`D1 / U1`。
- 从准备后到前缀结束的差值变化：`D1 − D0`，同时列出两组各自的`S1 − S0`和`U1 − U0`。

所有差值保留正负，分母为零保持未定义。这里不再用`2A`或`7A`换算。如果两组目标都全驻留，双沙箱的一份／两份容量差应为约5308.066 MiB、50%；这是容量示例，不是已测得结果，也不是通过门槛。

`mincore`目标驻留是主指标；cgroup file曲线用于说明整组上下文及脏页变化，不与目标驻留相加。两组实际准备／运行状态分别保存，不把不同组的file基线差当目标节省。两组查询时间、工具时延、启动和收尾时间分列，不从查询占比推算任务减速。

## 源码依据与已验证事实

- `scripts/validate_isolated_agentenv.py`的`copy-immutable-cache`阶段使用普通复制，并保留已验证的只读commit绑定分支；创建容器时先设置父cgroup，随后启动私有服务、确认预启动池关闭。本轮已复用这些能力并接入逐文件绑定及双服务协调。
- `scripts/isolated_storage.py:verify_container_boundary`核对自有可写目录，并拒绝额外可写挂载；新增目标绑定应为只读，仍需明确核对源／目标文件身份，而非只以“只读”判为正确。
- `AgentENV/src/sandbox/firecracker/sandbox.rs`新建系统盘时把`source_image_config`传给`create_overlaybd_runtime_device`；`AgentENV/storage/ublk-daemon/src/runtime.rs:materialize_overlaybd_image_config`保留并重写lower路径，为各guest创建独立upper。
- `AgentENV/storage/overlaybd/src/image/image_file.rs:open_lower_layer/open_localfile_path/open_ro_file`优先打开本地`file`或目录中的commit／sealed。因此相同配置路径经过不同绑定，可落到不同实际文件；最终仍以打开描述符和`device,inode`验收。仅创建不同虚拟盘设备不等于底层文件不共享。
- `AgentENV/src/sandbox/ublk/device.rs:get_or_create_shared_readonly`按规范化配置路径复用只读设备；因此给内存设备换名字不是文件副本对照。本轮排除该层，保留后续独立研究。
- `scripts/host_rootfs_layers.py`已按实际`device,inode`建立有序lower引用与使用者；`scripts/host_file_monitor.py:mincore_file`使用`PROT_NONE`映射和`mincore`，不读取文件数据页。

这些源码说明接入路线；新入口的真实身份、功能与成本以本轮实跑记录单列，不沿用旧单服务结果代替。
