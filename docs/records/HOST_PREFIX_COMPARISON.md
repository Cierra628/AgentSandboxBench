# 1对7短对照：共享只读后备的物理缓存与整组记账（2026-10-22）

**七个实际VMM共用同一个只读rootfs驱动，查询时它的host缓存为12.496 MiB；单沙箱为12.508 MiB。相对七份单沙箱容量的参考，指定对象少驻留75.059 MiB，约85.73%。** 这是指定只读系统／工具盘的缓存，不是任务仓库缓存、全部guest缓存或整体host内存。

## 两组做了完全相同的11步前缀

分别新建私有服务、16 GiB卷和统计组；每个guest均为2 CPU／4096 MiB。N=1执行backbone前两段；N=7的七个角色都只执行相同的read_repo、read_typescript，共11／77实际动作。逐条命令、顺序和退出码已核对，原预期退出127保留。每个guest实际执行的11条命令相同，没有执行后缀、官方测试、保存或恢复。首次单沙箱的测量失败另列，下表只列修正后的有效两组。

| 项目 | 1个沙箱 | 7个沙箱 |
| --- | ---: | ---: |
| 实际动作数 | 11 | 77 |
| guest周期样本 | 58 | 700 |
| host周期样本，含准备阶段 | 1187 | 1183 |
| 原工具累计时间／秒 | 0.766 | 6.368 |

两组固定先单后七，各一次；初始化和并发调度会影响耗时，不用这两次判定稳定性能。早完成的guest自然等待其他前缀结束，没有另加空闲观察窗口。

## 指定只读后备：全局驻留只计一次

| 指标 | 1个沙箱 | 7个沙箱 |
| --- | ---: | ---: |
| rootfs逻辑容量 | 64 GiB | 64 GiB |
| mincore驻留页数，4 KiB／页 | 3202 | 3199 |
| 实测缓存驻留／MiB | 12.508 | 12.496 |
| 七份单沙箱容量的参考／MiB | — | 87.555 |
| 相对该参考少驻留／MiB | — | 75.059 |

通过实际沙箱ID绑定VMM，再只读查询Firecracker的[GET /vm/config接口](https://github.com/firecracker-microvm/firecracker/blob/main/src/firecracker/swagger/firecracker.yaml)，保存驱动字段而不保存整份配置。七个VMM的只读rootfs路径最终指向同一设备号、inode和块设备号；查询该对象一次，没有把七条路径各算一份。不同实验虽复用了块设备号，inode不同，按不同设备存活期分别观察。

本轮rootfs对应只读系统／工具盘；user_rootfs和额外卷均为独立可写驱动，未把它们当作这个共享对象。只读镜像层文件另查31个：两组创建前和任务后均驻留6845.805 MiB，文件身份和大小稳定。这部分在公共准备时就已存在，净变化为零；不乘七并冒称为本轮启动节省，也不与rootfs、file或PSS直接拼成整体物理总量。

mincore只查询已有缓存页，通过PROT_NONE映射，不读取内容、不触发预读或锁页。rootfs设备创建前没有对应驻留查询，初始容量标为NOT_OBSERVED_BEFORE_DEVICE_CREATION，不补零。上面的75 MiB是任务后对象容量的线性参考差，不是该设备从创建前起的实测净增量差。

## 整组记账：file少22 MiB，不等于整体节省85.7%

分别使用各组首个guest创建前的直接计数作为基线，全部前缀完成后、额外驻留查询开始前直接取端点。共同输入和固定服务准备不乘七。

| 记账指标 | 单沙箱净增量／MiB | 七沙箱净增量／MiB | 7×单沙箱参考／MiB | 相对参考少记账／MiB |
| --- | ---: | ---: | ---: | ---: |
| file，含shmem | 13.828 | 74.469 | 96.797 | 22.328 |
| memory.current | 571.242 | 3917.816 | 3998.695 | 80.879 |
| anon | 549.676 | 3787.020 | 3847.730 | 60.711 |
| kernel | 7.812 | 50.562 | 54.688 | 4.125 |

file相对参考少23.07%，memory.current少2.02%；这两个比例属于组内净增量的单次参考。匿名内存也发生变化，不能将全部current差额归因于文件共享。指定设备的全局驻留和file可能重叠，不能把75.059与22.328 MiB相加。内核计数读取、汇总和分项时间也不同，不强行让分项精确相加为current。

**起点仍有准备阶段写回，整组比例只作描述。** 两组基线的file_dirty分别4008.547／4042.867 MiB，基线file相差34.313 MiB，大于本轮22.328 MiB的file参考差。各自扣基线可以去掉固定容量，但不能消除准备活动、后台回收和统计汇总时机的影响。因此本轮最直接的共享证据是同一只读对象的实际身份与驻留，不把整组23.07%或2.02%当成文件共享的因果收益。

## 采集范围和成本

guest每0.1秒只读meminfo；host每0.1秒读独立组的memory.stat/current，每1秒读全组PSS。会话均为light，正常结束并确认回收；没有CPU、块设备I/O、旧服务／逐VMM采集或逐页探针。没有额外暂停、清缓存、预读、锁页或DAMON改动。

只读rootfs查询分别用时1551.862／1560.958毫秒；整个任务后端点查询分别1852.274／1874.391毫秒。查询在前缀完成后进行，不计入上表创建至前缀完成的时间；不同对象是顺序观察，不是同一瞬间的物理快照。尚无这条短路径关闭采样的耗时对照。

## 首次失败与修正

首次N=1完成11动作，但Firecracker返回agentenv_volume_slot_2.img等相对路径，查询程序错误地从进程根目录解析，导致任务后的后备对象查询失败。已按进程工作目录cwd解析相对路径；绝对路径仍按进程root解析，补了回归。源码依据为AgentENV/src/sandbox/firecracker/instance.rs中cmd.current_dir，以及extra_drive.rs中在sandbox工作目录建立相对附件路径。实际修正后的两组查询通过。

原VMM已清理，缺失的当时设备驻留无法离线补查，因此只补了一次N=1短采集，再完成N=7；没有重跑完整任务。原11动作与FAIL保留，不混入有效两组的88动作。原16 GiB失败卷保留，自有活动资源已回收，源服务恢复停止。此前GRPO的另一份16 GiB失败卷未删除。

81项相关离线回归通过，其中6项新增；路径修正后只补跑受影响的6项。测试不启动服务或设备。所有新报告图片已查看，缺失或未覆盖项不补零，未暂存、提交或推送。
