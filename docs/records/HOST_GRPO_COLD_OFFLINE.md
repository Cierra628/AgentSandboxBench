# 七沙箱新页共享曲线：离线接入核对（2026-10-26）

**可以接入原七沙箱并发流程，但不能直接套用两沙箱入口。建议保持原调度，用一个后台工作线程每次查询结束后等5秒再查；只在创建guest前定向释放目标文件缓存。** 本页记录接入前的源码与已有结果核对；后续[离线实现及57项相关检查](HOST_GRPO_COLD_IMPLEMENTATION.md)和[一对真实完整验证](HOST_GRPO_COLD_LIVE.md)均已完成。

这一步要展示的是：指定系统盘下层文件从零驻留开始，随正常启动及任务读取进入host文件缓存，共享19文件与独立133文件的容量如何变化。主容量仍为这些文件的`mincore`驻留之和，不换成匿名页、整个统计组的file或guest Cached。

## 对象清单可以复用，释放范围必须补上独立副本目录

原完整入口在同一私有服务内准备共享1套／独立7套初始文件。每套19文件，共1,358,865个4 KiB页；独立133文件共9,512,055页。这里是查询覆盖的逻辑页数，不代表全部驻留。两沙箱短实验的19／38文件与完整入口的初始清单对应相同相对路径及大小。

源码依据：

- [`host_full_rootfs_control.py:prepare`](../../scripts/host_full_rootfs_control.py)按同一初始清单准备副本，并检查独立文件没有共用inode。第0套在自有卷的`env/image-cache/commits/`，第1～6套在`env/rootfs-copy-control/copies/1`～`6`。
- [`prepared_objects`](../../scripts/host_full_rootfs_control.py)已包含19／133文件；[`after`](../../scripts/host_full_rootfs_control.py)核对七个活guest的真实系统盘引用、打开文件、分配记录及使用者，共享每文件7使用者、独立每文件1使用者。不能套用“只选至少两使用者”的旧筛选，否则会漏掉独立组。
- [`ColdFileRead.initial`](../../scripts/host_cold_file_read.py)目前只允许自有`env/image-cache/commits/`，会拒绝完整入口第1～6套的目录。需要将新模式的范围限定为同一自有卷内、准备清单中的上述两个目录，逐文件保留身份和打开后核对；不要改成允许任意项目路径。两沙箱旧模式仍只接受原目录。

完整入口已有自有文件系统`sync -f`，上限300秒，见[`validate_isolated_agentenv.py`](../../scripts/validate_isolated_agentenv.py)。复用此步骤，不再加一次全局同步。顺序应为：副本准备及同步→服务就绪且无guest→精确目标文件`POSIX_FADV_DONTNEED`→mincore确认P0全部为0→七路并发创建。P0非零就停止新模式，不通过反复回收、等待或填零继续。

这样只控制指定文件的host缓存起点。卷后备文件、其他缓存及后端正常预读保持原状态；它不是“整机冷缓存”或磁盘读取量实验。运行中不再主动释放缓存，AgentENV默认回收保持。

## 七路并发必须保留，查询不要放进任务协程同步执行

[`do_grpo`](../../scripts/run_prettier6604_grpo.py)先并发`start`七个guest，再并发执行七条完整路径。`start`除了创建guest，还含原采样器启动、仓库初始状态和baseline检查、工具及负载上传。因此“全部guest就绪”实际指原任务准备也已完成。

保存结果支持这一调度：

| 已有完整运行 | 七次创建派发跨度 | 七个首段派发跨度 | 创建及原准备 | 原路径及结果下载 |
| --- | ---: | ---: | ---: | ---: |
| 优化后的共享组 | 4.146毫秒 | 5.709毫秒 | 6.194秒 | 20.526秒 |
| 旧独立组 | 3.516毫秒 | 7.180毫秒 | 5.987秒 | 18.921秒 |

两组七次创建都在任何一次创建完成前派发，当前`do_grpo`与两组保存版本相同。原两沙箱入口则逐个创建guest，不能把它扩成七个来代替完整GRPO。

完整流程没有短实验的协调等待循环。把`cold.tick()`直接放入`do_grpo`或`run_segment`会同步阻塞事件循环，延迟其他沙箱派发。建议只增加一个后台工作线程，顺序查询固定对象集合，不与原0.1秒host计数线程合并，以免一次较长查询拖慢周期计数。工作线程独占驻留点的写入；主流程单独记录阶段时间，避免两个线程同时改写同一份状态。

## 每次查询后等5秒，比直接沿用2秒合适

复用短实验保存的全部查询和源码，而不是重新查文件。短实验与当前`mincore_file`、驻留位计数函数相同；旧133文件实跑仍用优化前计数，不能当最新版成本。

| 已有真实查询 | 单次查询用时 | 证据含义 |
| --- | ---: | --- |
| 新短实验19文件，17点 | 中位0.057379秒，最大0.069880秒 | 当前实现，两个guest共享 |
| 新短实验38文件，13点 | 中位0.096790秒，最大0.104491秒 | 当前实现，两套独立副本 |
| 优化后完整共享19文件 | P0／P1为0.068692／0.075510秒 | 当前实现，七guest |
| 旧完整独立133文件 | P0／P1为1.165090／1.171955秒 | 旧计数，保留原观察 |

按38文件的非初始查询用时乘`133/38`，新版133文件单次估计中位**0.340秒**、最大样本换算**0.366秒**。这是规模估算，不是新版133文件实测或成本上界；初始P0单列，未混入运行中预算。

若每次结束后等2秒，按中位估算，查询占工作线程循环墙钟约14.54%；改成5秒约6.37%。建议两组都用**结束后5秒**，不补追错过的采样、不并发查询。它只用于展示大致读入过程；guest／host普通计数仍0.1秒。查询线程占用比例不等于任务减速率，也不直接当CPU百分比。

初始释放本身也要计时：短实验19／38文件分别用0.291429／0.497982秒，属于创建前的准备成本。正式接入应分别记录释放、P0、周期查询及P1的墙钟和线程CPU、实际间隔、写出与等待结束时间，保留原整轮计时，不扣掉查询后另报任务时长。

## 阶段只记时间，不为取点新增等待

保留现有P0和P1，并新增独立的单调时钟阶段记录：

1. **P0确认结束**：创建前，准备对象；全部容量为0。
2. **七次创建开始**：原创建计时起点。
3. **全部原准备完成**：原`await joined(self.start(...))`返回处，只记时间，随后仍立即并发执行完整路径。
4. **首段派发及各段开始／结束**：用host单调时钟记录；段完成包含原结果下载及检查，单个工具的执行用时仍取原`steps.tsv`，不混用两种计时。
5. **原路径及下载全部结束**：现有`paths_end_monotonic_ns`；停止后台查询并等待当前查询结束，再执行原P1真实对象核对、查询和查询后复核，最后仍走原官方检查及清理。异常出口也必须先停止查询，再卸载卷。

现有`.phase`只覆盖写入最后一个文本，见保存的`code/controller.py:73`，不能用于还原历史阶段；已有`role_first_segment_monotonic_ns`是首段派发，不是每个工具的实际开始。新记录应保留各点查询开始／结束，跨“准备完成”等边界的点标为跨阶段；不插值成精确的阶段容量，也不在该边界暂停任务等查询。

共享、独立两组分别从各自P0计时。图上标出启动准备区间和任务区间；P1可按相同完成阶段比较，过程曲线按任务进度辅助解释，不能把两次运行相同秒数的纵值直接相减。后台查询不包括官方检查或清理阶段，避免把无任务时的回收混入任务曲线。
