第一次普通文件扫描后，控制程序执行第一组官方检查、删除，再开始第二次恢复。这一顺序由原事件时间及`scripts/host_file_matched_task.py:41–88`共同确认。源码中的扫描发生在本组额外检查之前，但第一组的额外检查仍发生在第二组基线之前。

两份运行中普通清单按11类逐项复算，只有私有loop后备卷增加723.574219 MiB、日志增加0.0390625 MiB，其余类别的驻留合计不变。前者就是两组共用的同一个可写卷。这个区间包含第一组检查、删除、第二组恢复和任务，不能全归因于双沙箱运行。

因此，分别减去各组基线可以描述“本次从实际起点增加多少”，却不能消除热缓存、脏页和写回状态对后续运行的影响。原指定设备49.702%的线性参考保持原范围，不扩展为整体节省。

## 哪些统计重叠，哪些应当保留

| 对象或指标 | 处理方式 |
| --- | --- |
| 普通文件缓存 | 按文件系统设备号和inode去重；同内容的两份独立文件不因内容相同而合并 |
| 原始内存层 | 本轮556.230469 MiB已经在普通文件清单内，不重复加 |
| 块设备缓存 | 同组内按实际设备身份去重；双VMM共用的内存设备只计一次 |
| 设备号复用 | 本轮N=1和N=2设备号相同，但inode不同，属于先后创建的不同设备；不能跨组当成同一个对象 |
| VMM文件PSS、其他进程文件PSS | 可能覆盖已查询的文件／设备缓存，不加到缓存合计中 |

最终普通文件清单另有0.480469 MiB净不足，继续保持`SHORTFALL_REQUIRES_RESOLUTION`。不能把这个净差当成全部组外缓存，不能从旧设备组外量抵扣，也不能因为它很小就补出一个精确总量。

## 线性参考要扣掉公共成本，再明确分母

沿用用户选择的单沙箱换算，不改后端，也不把它称作实测“不共享”组。设同一种指标下：

- `C1`、`CN`：两组任务前、不含活动VMM的公共准备和服务基线；
- `M1`、`MN`：单沙箱与N沙箱在约定任务阶段的量；
- `X1 = M1 − C1`，`XN = MN − CN`：各组相对自身起点的增量，包含恢复与后缀，不仅是工具执行。

若起始状态和测量范围可比，则：

```text
任务增量的线性参考 = N × X1
相对参考减少量 = N × X1 − XN
任务增量的相对减少比例 = (N × X1 − XN) / (N × X1)

把公共准备计入部署成本时：
部署参考总量 = CN + N × X1
部署相对减少比例 = (CN + N × X1 − MN) / (CN + N × X1)
```

百分比只在相应参考分母为正时计算，负减少量照实报告。两个分母回答不同问题，不能都称为“整体节省”。`2 × M1`会把公共输入、快照及固定服务重复外推；本轮已经观察到大幅基线差异，不能套用这组公式生成总体百分比。

公式也不会改变测量含义：用current计算得到总记账增量的参考差，用file得到文件缓存记账的参考差。只有物理覆盖、重叠处理和比较时间均成立时，才可以将对应结果称为物理节省。当前轻量方案的整体物理节省仍为`NOT_MEASURED`。
