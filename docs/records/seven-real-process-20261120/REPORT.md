## 探针写入如何隔离、实际测到多少开销

基线 `scripts/snapshot_cache_residency.py:89–121,179–200,325–350` 按控制器 PID 过滤，再按原生线程 ID、地址范围和代号选读者结果表。**每个查询子进程调用原接口在自己 PID 下挂直接后备与快照下层各一个探针。** 不是让子进程共用父进程探针或写句柄。结果只写本角色目录；父进程通过控制管道收完成通知，再从专属文件读出集合，以原有 set 去重规则合并。两帧是同一共享设备的前后证据；先在各支调用原 `DeviceRound.match` 归属与核对，再在父进程合并得到的 provider PFN，不拼帧、不按支均摊设备页。

挂载列含编译、挂载、等就绪和查找映射表，发生在恢复前，不在 645.601 ms 内；查询墙钟包含这两只探针对真实读取的影响。CPU 列来自探针进程时钟差，不含在查询线程内同步执行的内核探针指令；没有关闭探针的同负载对照，不能把它当作探针的全部开销。旧运行中的两个探针进程 CPU（不暂停旧批）为 1.350 / 1.273 ms，窗口和工作量不同。**两只挂载合计已经超过 1 秒。14 只未挂，因此没有其逐只用时、合计、运行 CPU 或相对于两只的增量；也没有证据判定七进程净收益为负。** 即便今后获准测量，14 探针墙钟也不能与 2 探针墙钟直接相减来量化纯多进程收益。

工作 PID 1293838，两个探针 PID 1293839 / 1293907，结果 map ID 10462 / 10538 不同。工作进程在读窗开始时检查只有一个原生线程。两只探针都捕捉到按实际连续段重算的 5,160 次调用；两层各查两遍，共 **92,522** 有效页次，均无缺失的内核返回。父进程核对结果文件的角色、sandbox ID、工作 PID 与行数，并离线用两份清单、宿主行表和 provider 两帧重算，所得集合与原文件逐项相同（四来源 36,411，provider 当前集合 0）。这验证的是本次单支；不能用它证明七进程同时写时绝不串号。

## 页数与结论边界

旧串行同支确认 37,509，本次 36,411，少 1,098；两次的首份 guest 清单已经不同（30,263 对 29,163，相差 1,100）。因此工作集在查询前就有差别，不能把 1,098 页之差归给进程模型，也不能由两批清单总数确定每一张差异页的原因。旧七支 168,829 页与本次单支不能比较。运行二未执行，没有七支 CPU、折合并行度或对旧批 16.116 CPU 秒的实测差值，更不能断言七线程的等待开销已消失。
