## 为什么不能混算为新版采样开销

| 采集条件 | 旧三项单任务 | 新#14400 | 七沙箱GRPO参考 |
| --- | --- | --- | --- |
| guest周期采样 | 0.1秒，light | 0.1秒，light | 每guest 0.1秒，light |
| host current周期 | 0.1秒 | 0.1秒 | 0.1秒 |
| PSS周期 | 开启，1秒 | 关闭 | 关闭 |
| mincore驻留查询 | 结束时普通文件清单 | 关闭 | P0／P1指定文件查询 |
| guest采样管理的合并调用 | 未使用 | 使用 | 使用 |
| 自有卷 | 8 GiB | 20 GiB | 48 GiB |
| 准备后、取基线前显式同步 | 未记录该步骤 | 未记录该步骤 | 已执行 |

PSS按共享比例统计进程映射内存，mincore查询指定文件页是否驻留；两者都增加查询工作，但不能加到current上。旧#6604最终清单只有100文件、缺输入RAM镜像和私有loop卷；Sphinx／Xarray为157文件；GRPO仅查询其固定文件集合。离线报告切换主图不会移除当时已发生的查询成本。

从实际源码快照逐字节核对，Sphinx和Xarray的host采样器相同；它们与旧#6604、新#14400分别属于不同版本。旧三任务guest采样控制代码相同，新#14400和GRPO又各有不同版本。即使某个采样器相同，整个执行路径、任务和准备条件仍不相同，不能据此认定是性能对照。#14400未保存冷启动辅助脚本的执行快照，本次将该项列为未记录，不用当前工作区文件代替当时证据。

| 任务 | host采样线程CPU／秒 | 计数读取墙钟累计／秒 | 保存的驻留查询墙钟／秒 |
| --- | ---: | ---: | ---: |
| Prettier #6604 | 1.264 | 0.335 | 0.240 |
| Sphinx #7590 | 1.316 | 0.393 | 1.053 |
| Xarray #6992 | 2.750 | 0.481 | 1.210 |
| Prettier #14400 | 0.360 | 0.286 | 未请求 |
| 七沙箱GRPO参考 | 0.455 | 0.370 | 0.134（仅P0／P1） |

前三项线程CPU包含PSS工作，查询窗口长度也不同，不能把CPU差直接算作移除PSS的收益。上述CPU和墙钟分别列出，不叠加成减速率。原官方结果继续保留：#6604为0通过／2失败，Sphinx为24／1、Xarray为945／12，后两项按原诊断规则通过而非严格重放通过；#14400为4／0。

## 准备成本不同，减去基线也没有变成同条件对照

#6604和#14400使用同一来源备份，准备的RAM镜像均7252 MiB；Sphinx为8708 MiB，Xarray为10644 MiB。只读转换层、私有卷、任务仓库和控制程序的后续变化都可能影响current。Sphinx／Xarray及新#14400取基线时`file_dirty`约114.46 MiB；七沙箱参考的同步后基线约0.207 MiB。默认回收保持，未额外采集回收计数，不能把每段下降直接归因于DAMON。

因此可以复用四项的真实曲线说明各自运行过程，也可以统一列出三项有效增量；要比较同一采样方案的成本、重复均值或共享收益，则须使用相同任务、准备、采样和调度条件。本次不将不同任务相减为优化收益，也不为填补旧基线重跑已成功任务。
