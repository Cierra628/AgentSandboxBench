上轮删除的Sphinx／Xarray旧镜像已经不存在，但其构建缓存仍持有24层。本次将全部24层逐一对应到构建缓存记录、快照和保留记录，确认了删除镜像后仍不释放这些层的原因。这里的保留记录（lease）用于告诉Docker哪些资源仍需保留，不是正在运行的沙箱。

本轮只读，没有清理缓存、删除文件、拉取或构建镜像，也没有启动服务、沙箱或Xarray。推荐只清理清单中的24条构建缓存，不扩大到其余276条。

## 为什么工具显示不到1 MiB，实际层却占4.285 GiB

这24条缓存内部记录的大小之和只有950725字节，约0.907 MiB。其中20条基础层的`cache.blobonly=true`、记录大小为0，但其快照保留记录仍在，层目录也仍在。

匹配当前二进制依赖的[BuildKit v0.29.0大小计算源码](https://github.com/moby/buildkit/blob/v0.29.0/cache/refs.go#L318-L347)显示：大小已有记录时直接返回；需要计算时，`blobonly`记录会跳过快照用量。这解释了本机的0B记录为什么不能当作不占磁盘。

[同版本创建保留记录的源码](https://github.com/moby/buildkit/blob/v0.29.0/cache/manager.go#L216-L247)将快照资源加入保留记录；[清理源码](https://github.com/moby/buildkit/blob/v0.29.0/cache/refs.go#L431-L463)通过删除保留记录释放资源。因此，删除镜像并没有解除已查明的这24条构建缓存引用。

复用上轮有效的文件分配和硬链接核对：24层去重后实际分配4.284641 GiB，没有层外硬链接。本轮核对层身份及父层未变，不重复扫描所有文件。当前可用58.686920 GiB；若支持的缓存清理正常释放这些最后引用，预计约62.971561 GiB。这个数是有条件的空间估计，实际释放须执行后读取文件系统可用量；Xarray启动前仍须严格>62 GiB。

## 推荐只用精确缓存ID筛选

已用`docker buildx du --builder default --filter <精确ID表达式> --format json`验证，表达式恰好命中这24条，没有命中其余276条。表达式使用首尾锚定的完整ID集合，不用任务描述或时间范围模糊筛选。Docker[官方筛选说明](https://docs.docker.com/reference/cli/docker/buildx/du/#provide-filter-values---filter)说明`du`和`prune`使用相同筛选方式；候选查询通过不等于已执行删除。

新的清理范围须用户确认。获准后重新核对完整ID集合、可回收／共享状态、父子及保留关系，使用保存的精确筛选命令清理这24条。不得去掉筛选器，不加`--all`，不使用按剩余空间或缓存总大小扩大范围的选项，不手工删除Docker内部目录。BuildKit清理末尾会执行正常的垃圾回收，具体流程见[同版本源码](https://github.com/moby/buildkit/blob/v0.29.0/cache/manager.go#L949-L966)。

影响是丢失已删除的两个旧TrEnv-X任务镜像的剩余本地构建缓存，未来需要按已保留配方和固定基础来源重建。当前AgentENV输入、源服务镜像、其他镜像和其余缓存记录不在拟清理范围。完成条件是目标24条清理情况、其他缓存与镜像／容器状态、实际磁盘变化都有记录；若空间仍未释放，保存原因，不继续扩大清理。清理后停止，不自动启动Xarray。
