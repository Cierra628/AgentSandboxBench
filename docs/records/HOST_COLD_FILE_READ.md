## 怎么做的

复用原有双私有服务短前缀入口，每组两个新guest，分别执行相同的原11动作前缀，共22动作／组；共享19文件、每文件2使用者，独立组实际复制两套、共38个不同文件身份，每文件1使用者。没有执行完整路径、模型训练或官方任务测试，官方评估明确为`NOT_RUN_PREFIX_ONLY`；前缀动作、顺序、预期退出码、关键输出和清理通过原检查。

只在显式`--cold-read`模式增加以下操作，旧入口默认行为保持：

1. 两个自有文件系统完成原同步，服务已就绪但guest尚未创建。
2. 对本次自有目标文件调用`POSIX_FADV_DONTNEED`，不使用整机`drop_caches`。逐文件核对归属及设备／inode／大小／修改时间。
3. 用原mincore查询实际驻留。只有全部为0才继续创建guest；建议调用成功但仍有驻留会失败，不把它填成0。
4. 原等待循环中约每2秒顺序查询一次；另在两个guest及任务准备均完成、原前缀结束时记录阶段点。没有新增采样线程、暂停VM、修改原11动作、额外预读任务文件或运行中主动回收。
5. 结束前核对真实活guest的系统盘引用、全部目标文件及实际使用者，再复查身份。默认AgentENV回收保持，guest／host计数仍0.1秒，PSS关闭。

这里控制的是指定下层文件的host缓存，不代表整个存储路径或整机缓存都冷。正常后端读取及正常预读引入的目标页均计入当时驻留。

## 新页确实进入了host缓存，共享组没有形成两份完整副本

单位MiB：

| 同一执行阶段 | 共享19文件 | 独立38文件 | 独立减共享 |
| --- | ---: | ---: | ---: |
| 创建guest前，实际初始驻留 | **0.000** | **0.000** | 0.000 |
| guest启动及任务准备完成 | 207.203 | 411.180 | 203.977 |
| 两个guest各完成原11动作 | **209.750** | **419.695** | **209.945** |
| 仅11动作期间的容量变化 | +2.547 | +8.516 | 差值再扩大5.969 |

这次约210 MiB的差不是复制准备留下的热缓存：初始已直接查询为0，之后由正常执行过程带入。目标文件及实际引用对应关系全部通过核对，独立组38个文件全部查询。

**收益仍主要在启动和任务准备阶段形成。** 原11动作期间，两组也出现进一步驻留增长，但只有数MiB，不能将全部209.945 MiB解释成这11步新增的节省。新实验说明了从零驻留到实际缓存共享的形成过程，没有为了得到持续上升曲线而添加读文件命令。

左图从各组自己的零驻留基线计时。两组创建和准备速度不同，不能直接按相同横坐标相减判断共享效果；右图按相同执行阶段比较。曲线连接17／13个顺序观察点，不是0.1秒连续物理轨迹，也不是累计读取字节。正常回收可使驻留下降，未要求单调增长。
