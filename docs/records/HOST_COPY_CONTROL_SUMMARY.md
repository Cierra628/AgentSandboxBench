## 原热准备对照的范围

**Prettier #6604的完整GRPO和BPO各有一对真实共享／独立文件对照，均已完成。** 七沙箱共用初始19个系统盘文件，相比各用一套、共133文件，任务结束时分别少驻留24.695663／24.693775 GiB，减少约85.71%。收益主要在复制准备阶段形成；运行期间差值分别只再增加4.148438／2.214844 MiB。

本表来自四个有效组、546个实际动作，原任务、恢复、对象关联、测量及清理检查通过。每种调度只有一对有效对照，是单对实测，不是多轮均值或稳定性结论。单位：1 MiB＝2^20字节，1 GiB＝2^30字节；原始驻留按4096字节页计。

## 相同对象、相同阶段，分别在各调度内部比较

每组一个新私有服务、七个原角色。共享19文件、每文件7使用者；独立复制7套，共133个不同文件身份，每文件1使用者。来源、层顺序、文件长度一致，不用硬链接或reflink代替独立副本。device/inode，即设备编号与文件编号，用于识别实际文件，而不是按路径或相同内容标识合并。

- **P0：**普通复制并同步自有文件系统后、guest创建前查询准备好的目标。副本准备本身会形成缓存；不额外读取目标全文来使其驻留。
- **P1：**所有原路径／后缀结束、官方检查和删除前，先确认活VMM、实际系统盘引用、打开描述符及副本分配，再查询目标，最后复核文件、配置、设备和VMM身份。独立组单使用者文件全部查询。

`mincore`配合`mmap(PROT_NONE)`只查询驻留位，不读取或触碰数据页，不锁页、不预读，不额外暂停guest。运行中仍为0.1秒guest meminfo及host组内计数；显式副本模式关闭PSS，保留AgentENV默认回收。BPO自身的原生保存暂停和恢复顺序不改，中间阶段只记录元数据。

## 先离线复算，需要时才重新实跑

日常查看不需要服务或设备。以下命令只读已保存JSON，在新目录生成`SUMMARY.md`和`summary.json`：

```bash
bash scripts/report-host-copy-summary.sh \
  --output .artifacts/host-copy-summary-new
```

默认读取本报告的两份有效证据；也可用`--grpo FILE --bpo FILE`显式指定。输入需连同其指向的原始JSON保留，输出目录必须不存在。缺失、未知或与原始记录不符会失败，不补0。该命令不调用服务、mincore或负载文件。

若要重新实跑并已获得授权，先准备本机固定源服务、原冻结输入、验证过的准备归档及实验二进制，使用以下独立命令。GRPO实测用原实验二进制，BPO用扩展版；它们不是同一次构建，但初始19层的统计对象与公式一致，旧GRPO程序保留。

```bash
# GRPO：共享／独立各189动作；48 GiB卷，可用磁盘须严格超过74 GiB。
bash scripts/run-host-full-rootfs.sh \
  configs/platform-prettier6604-host-file.json \
  --schedule grpo \
  --copy-daemon .artifacts/host-full-grpo-build-20261024/uvm-ublk-daemon

# BPO：共享／独立各84动作；64 GiB卷，可用磁盘须严格超过90 GiB。
bash scripts/run-host-full-rootfs.sh \
  configs/platform-prettier6604-host-file.json \
  --schedule bpo \
  --copy-daemon .artifacts/host-bpo-copy-build-20261025/uvm-ublk-daemon
```

这一对副本入口要求固定源服务`asb-source-rebuilt-20261018T160925Z-2726362`原先停止，确认身份后自行启动，结束恢复停止；只给新私有服务使用实验程序，不替换原服务、不复用预启动池。统计组在准备和新服务创建前建立，同时启用内存与I/O记账。300秒准备同步上限仅用于显式完整副本模式，真正同步成功后才进入P0，不额外固定等待；其他旧入口保持原行为。

每组通过才继续下一组。失败先定位并保留新卷；新失败卷删除需单独批准。实跑前重新检查实际负载、空间及原准备入口要求的可用RAM超过64 GiB，不降低20 GiB磁盘保留和6 GiB余量，也不要求其他用户停止工作。
