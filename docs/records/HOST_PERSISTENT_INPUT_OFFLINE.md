# 持久化文件输入：离线确认结果

## 推荐方案：备份临时恢复到磁盘，运行只使用新导入的普通文件

当前不能直接绑定源服务目录来替换RAM种子。只读检查实际挂载来源后，105个已验证普通文件路径中，源服务缺少93个缓存文件；12个依赖文件都存在，但1个大小不同。大小相同的11个文件本次也没有读取内容验证，不能据此替代固定输入。原20 GiB裸卷已不存在，已保存并通过原完整性校验的压缩备份仍在。

推荐新增一个独立选项，首版仅服务于已通过的Prettier #6604同组1→2短测：**先在统计组外恢复临时磁盘镜像，再在新统计组内导入普通文件；临时镜像清理后才启动私有服务和guest。** 原RAM种子和旧入口保持行为，不原地修改源服务。

这个方案去掉运行时的RAM整卷容器，也避免把旧文件缓存直接当作新组内缓存。方案已离线确定，后续[独立入口及模拟检查](HOST_PERSISTENT_INPUT_IMPLEMENTATION.md)已完成；真实输入尚未构造或实跑；后续[空间清理](STORAGE_CLEANUP_20261029.md)已使磁盘达到准备门槛，启动前仍需重查。

## 执行顺序和统计范围

1. **统计组外准备来源。** 驱动在自有目录新建并完整预留20 GiB临时文件，按原协议验证并恢复固定备份，再以只读loop／ext4挂载。恢复写入不能截断文件而丢失预留，恢复后核对逻辑大小和实际分配。归档读取和临时镜像准备不在新组内执行。
2. **建立新统计组，再导入运行输入。** 导入进程必须在组内出生，目标是本轮新建的普通目录及新文件；拒绝复用旧目标、硬链接原文件或直接绑定旧inode。原清单、字节内容和完整性要求保留，不重新转换镜像。
3. **只同步自有普通文件。** 导入后对目标文件及目录逐个`fsync`。普通目录位于共享host文件系统，不能对它执行`sync -f`而把整个共享文件系统都同步；原8 GiB自有文件系统的同步策略不变。
4. **先清理临时来源，再分配运行卷。** 内容验证通过且文件句柄关闭后，正常卸载临时ext4、分离loop、删除自有临时镜像；不使用延迟卸载。清理未完成就停止，不创建运行卷或取基线。统计组保持存活，导入后的普通文件保留在组内使用。
5. **复用原运行路径。** 分配原8 GiB可写卷，依赖和可写元数据按原路径准备；只把commits来源换成本轮导入的普通目录，并只读绑定。服务和guest都在同一统计组内创建，不复用池中的进程。
6. **准备完成后测量。** 记录无guest基线，再执行原N=1／2、各11动作及各5秒窗口；0.1秒guest和host采样、默认回收、原任务检查和清理保持。

第1步的恢复来源由同一个实验驱动管理，第2步后的统计组负责运行输入及私有服务。临时资源的移交、关闭和清理由同一驱动按自有资源收据处理，不让两个控制程序同时拥有清理责任。准备失败保留现场；成功的临时来源在运行前清理，整个任务成功后清理本轮输入目录及运行卷。

**新选项的范围与旧模式不同：**旧模式的组内current覆盖RAM备份恢复全过程；新模式从运行输入导入开始记账，备份恢复位于组外，且相关临时文件和挂载必须在基线前消失。新报告必须明确这一差别，另存组外准备耗时和资源收据，不能用新旧current差直接宣布物理节省。原current字段仍表示该组及后代的总记账，不改成“扣除准备后的总量”。

## 完整性检查保留，明确这是暖缓存准备

保留已有明确要求的备份完整性和导入文件内容校验，均安排在准备阶段，计时单列。校验会读取文件，所以新入口同样不声称host冷缓存；不为降低基线跳过校验，也不通过反复读取、锁页或暂停guest维持驻留。进入任务阶段后由默认回收决定缓存变化。

旧`--immutable-cache-seed`明确要求`readonly/env`路径、只读loop和对应挂载身份，不能把普通目录伪装成旧种子。应为新选项增加独立的输入校验分支：检查任务与服务镜像、完整性收据、新文件身份、创建时所在组、目标只读绑定及临时来源已释放。新条件只用于新选项，旧预条件和检查行为保留。

## 旧缓存归属：首版不用旧目标inode，不把查询塞进周期采样

- 原归档在组外读取，只属于实验恢复来源；临时镜像及内部文件随后解除挂载并删除，其缓存不应作为运行输入保留。
- 实际运行的目标文件在新统计组内首次创建和填充。需要同时保存组建立、文件导入、服务创建的顺序和新文件身份，不能先写文件再把进程移进来。
- 新入口首版不接受已有目标文件或硬链接替代新导入；同一轮N=1／2仍共享同一批新目标inode。这样无需每轮逐个追查旧输入的所有者，也不增加0.1秒路径的开销。
- Docker镜像程序页、全局服务等仍可能在组外；本方案没有把它们归零，也不自动给出全host物理并集。

若后续要支持长期复用已有文件，单靠mincore驻留量不能判断记账组。项目已有[`host_existing_cache_owner.py`](../../scripts/host_existing_cache_owner.py)，可查询指定文件实际组内／组外／未知容量；它依赖当前内核布局并有编译、挂探针和前后核对成本，不适合放进周期采样。只有需要复用旧文件时再作为显式明细接入。未知或失败保持未知，不套用旧1.7 GiB结果；已知驻留量也不能全部加到current，因为组内部分会重复。

## 磁盘预算：准备前严格超过54 GiB

为避免依赖稀疏比例或另写受限解压器，首版完整预留20 GiB临时镜像；105条路径的逻辑长度不足7 GiB，普通输入目录按8 GiB预算。沿用20 GiB host保留量和6 GiB余量。

| 阶段 | 本轮新增空间预算 | 连同原26 GiB保护，阶段开始前可用空间 |
|---|---:|---:|
| 临时镜像＋普通输入目录 | 20＋8＝28 GiB | 严格超过54 GiB |
| 临时镜像已清理，普通输入目录＋运行卷 | 8＋8＝16 GiB | 从初始状态预算为严格超过42 GiB |

第二行的42 GiB是“还未创建输入目录”时的总预算；输入目录已创建后，分配运行卷仍按原条件要求当前可用空间严格超过34 GiB。压缩归档已经存在，不重复预留其文件大小。严禁临时镜像、输入目录和运行卷三者同时存在；否则新增空间为36 GiB，连同保护量需严格超过62 GiB，不能沿用54 GiB门槛。

本次元数据检查时可用约38.487 GiB，距离准备门槛还差约15.513 GiB，并且最终必须超过门槛。当前没有删除其他文件的授权，本段不清理或恢复备份。后续实跑前重新读取空间和实际负载，并保留现有MemAvailable严格超过64 GiB、有限超时、写盘锁与失败现场保护，不能沿用本次空间数字。
