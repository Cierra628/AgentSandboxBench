# GRPO创建、准备与采样顺序：离线核对（2026-10-26）

**建议新增一个显式的“先全部创建，再准备”对照模式，旧默认顺序不改。** 新模式先并发创建七个guest并登记身份，全部创建返回后，再并发执行每个guest原有的“启采样→源码检查→基线检查→上传任务”流程，最后仍等七个准备全部完成才执行原189动作。

这能把两组的采样和准备请求都移出创建窗口，便于观察创建完成后的采集影响；不会让镜像解析本身变稳定，也不能用来倒改原十对结果。本轮只核对源码与保存日志，运行代码和配置未改，没有启动服务或guest。

## 现在的`start`不只是创建

实际执行本批十对的代码与当前相关实现相同。`scripts/run_prettier6604_grpo.py`中的`SampledPaths.start`（513–555行），对普通新guest按以下顺序执行：

1. 调用原`agentenv_cold_start.py`，等待API返回沙箱ID。
2. **立即登记`self.live`和身份／启动记录**，之后任何准备失败都能找到已创建guest清理。
3. 开启组调用`runtime.start`：上传采样包、启动后台采集、等待首点就绪；关闭组跳过。
4. 检查任务源码初始状态，上传检查程序并运行基线检查，上传冻结任务。
5. 返回该guest ID。

`do_grpo`（707–758行）的`joined(self.start(role) for role in roles)`并发运行七条上述流程。每条流程都是创建返回后立即准备，而不是七个创建都返回后才准备。只有七条完整`start`全部返回，才并发执行原任务路径。

简化时序如下：

```text
现在：
  guest A：创建 ─→ 采样/检查/上传 ─→ 等待 ─┐
  guest B：创建很慢 ─────────→ 准备 ─────┤→ 七条原任务并发
  其余guest：创建 ─→ 各自准备 ─→ 等待 ──┘
```

这里的源码／基线检查是控制程序的准备操作，不是原189动作。因此，**准备和采样可能与其他创建请求重叠，原任务轨迹没有提前执行**。`joined`会等待全部在途操作结束后才报告其中的错误（同文件133–140行），不是首个失败就丢弃其他请求。

## 十对日志确认：两组的准备都与创建重叠

只使用host单调时钟的命令事件、采样控制回执及身份记录；不把guest时钟与host时钟直接比较。核对了20次运行、140个guest的创建→准备→任务顺序，并将70个采样就绪回执按进程身份对应到角色。

| 已有运行中的事实 | 关闭采样，10次 | 开启采样，10次 |
| --- | ---: | ---: |
| 至少一个guest在最后创建返回前已开始源码检查等准备 | 10次 | 10次 |
| 至少一个guest在最后创建返回前已完成任务上传 | 2次 | 4次 |
| 至少一个guest已确认首个采样点，而其他创建请求仍未返回 | 无采样器 | 10次 |

开启组最早采样就绪比最后创建返回早0.025797～45.373324秒。部分具体情况如下，时间均相对**最后一个创建客户端命令返回**：

| 对照与模式 | 已开始准备的guest数 | 已完成任务上传的guest数 | 最早采样就绪提前/秒 |
| --- | ---: | ---: | ---: |
| 第1对，关闭 | 6 | 0 | 未采样 |
| 第1对，开启 | 1 | 0 | 0.029553 |
| 第4对，开启 | 6 | 6 | 45.373324 |
| 第6对，关闭 | 6 | 6 | 未采样 |
| 第10对，关闭 | 6 | 6 | 未采样 |
| 第10对，开启 | 6 | 0 | 1.411397 |

全部20次的首个原任务派发都在七个准备结束之后；最后一个任务上传完成至首个原任务派发只相差约1.02～1.95毫秒。原任务并没有执行几十秒再等最后一个guest，长空档发生在任务之前。

因此，不能仅延后采样器，却让关闭组的源码检查、基线检查和上传继续夹在其他创建请求中；那样仍没有隔离完整的准备活动。现有记录能证明重叠，但不能单凭重叠证明它造成了慢创建，或把镜像解析、服务调度与准备请求的影响分别算出。

## 推荐只增加一个批次分界，不再增加七个等待点

新显式模式的顺序应为：

```text
阶段一：七个创建请求并发 → 每个返回立即登记ID → 等全部创建结束
阶段二：七个准备流程并发 → 每个内部仍先启采样，再检查和上传
阶段三：等全部准备完成 → 原七条任务路径并发 → 原检查与清理
```

两组都采用同一新顺序；开启组仅比关闭组多原采样操作。创建仍并发，准备也仍并发，不改成逐个启动；不增加固定`sleep`，不暂停VM、不清缓存、不预读或强制驻留。等待的是控制程序，已启动guest及其默认后台回收继续正常运行。

不选“全部准备完成后才启采样”：这会漏掉源码／基线检查和任务上传引起的内存变化。推荐模式仍在这些准备操作之前采样，只移动创建与准备之间的分界。

### 曲线覆盖会改变，旧结果不能平移复用

早创建guest会在没有本项目采样器、源码检查和上传的状态下，等其他创建结束。现有模式中这段等待已有采样：例如第4对开启组，至少一个采样器提前45.373秒确认就绪。新模式不再覆盖这种“其他guest仍在创建时”的早期区间，但继续覆盖原准备、全部189动作、任务检查及删除前阶段。

默认回收和guest后台活动仍可在等待期间改变缓存；新模式的初始Cached和实际创建耗时都可能不同。上述旧重叠时间不能直接换算成新模式减少的样本数、节省时间或新曲线，也不能将旧曲线平移／补0作为新结果。新报告应标明“七guest创建完成后，各自从采样就绪开始”，缺失启动区间不插值。

该模式用于普通guest-only采样开销对照，不自动推广到host共享文件物理测量、冷缓存释放、BPO或恢复。它是新的调度配置，不替换原十对+5.65%或原三对+2.60%的整轮指标。

## 最小实现范围与计时

后续若获准实现，优先复用现有一对工作流，不另建服务启动或任务执行框架。

| 位置 | 必要改动 |
| --- | --- |
| `run_prettier6604_grpo.py` | 将新guest的分配／立即登记与准备拆为两个内部操作；旧`start`仍按原顺序串接，恢复分支原样保留。仅新模式在`do_grpo`中分两批等待 |
| `platform_tasks.py` | 新增一个可选、默认关闭的配置项，如`grpo_create_before_setup`；它不能变成旧配置的必填项。限制于普通七guest GRPO的轻量开启／完全关闭两种配置 |
| `validate_isolated_agentenv.py` | 新选项必须同时传入输入检查和真实执行两处参数重建；不满足新模式范围时，在分配卷和启动服务前拒绝 |
| `run_grpo_light_pair.py` | 可选新模式从原开／关配置各生成一份带上述字段的自有配置，仍用原`use-platform`工作流；默认配置和原十对入口保持原行为 |
| 计时和报告 | 保存调度名称、全部创建完成、全部准备完成及控制程序结束时间；新组只能与同调度组配对，原三对／十对汇总应拒绝混入新模式 |

当前配置入口会拒绝未知字段，也没有任意后端参数透传，因此只在最内层增加一个开关并不足以形成可复现入口。需要走上述参数链，不能靠环境变量让检查与实跑采用不同顺序。

原`controller_elapsed_ns`、工具累计、动作及下载窗口、“创建至分支检查结束”和原创建请求跨度均保留。新增明确的**“全部创建完成至控制程序结束”窗口**，涵盖准备、采样控制、原任务、检查、收尾和删除：两端都记录实际单调时间，再比较新调度开／关组。可以另列“创建完成至全部准备完成”来定位部署和准备成本。

新窗口是新模式的附加指标，不是从旧整轮扣掉冷启动后改名，也不替代整轮结果。创建前的本地工作、创建请求及新窗口之间的间隔仍包含在原整轮中；不会因新增字段而丢失。没有新模式实测前，不给出它的用时或减速率。

## 验证与最小实跑建议

离线实现的完成条件：

1. 用模拟guest验证七个创建在任何采样／源码检查／上传之前完成；阶段二仍可并发，且每guest的采样→检查→上传顺序保持；原任务等待所有准备。
2. 创建返回即登记，某个创建失败时等待其他在途请求结束，清理全部已创建guest且不开始准备；某个准备／采样失败时也完成其他操作的收尾，不启动原任务，不漏删未准备的guest。
3. 默认普通GRPO、BPO／TVCache和恢复入口的动作顺序、状态及清理保持；新模式不允许与host、快照、缓存控制、单角色或旧完整CPU／I/O模式组合。关闭组仍没有采样或伪造内存值。
4. 参数在配置检查、后端检查和真实执行中一致，新增时间窗覆盖到收尾，原整轮定义和结果检查不放宽；报告显式区分新旧调度，禁止混合配对。

通过后，最小真实验证建议为**同一新调度下关闭→开启各一次完整GRPO，共378动作／14个新guest**。第一组直接验证新路径，不另做只启动不执行任务的短组；仍须原结果、时序、0.1秒采样及清理通过，分列创建、新时间窗、工具和原整轮。每组16 GiB卷，启动前可用磁盘严格超过42 GiB。首对只验证新路径与初步差值，不继续自动加到十对，也不拿新开启组对旧关闭组计算开销。
