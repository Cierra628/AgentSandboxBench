# 七支为什么只用到约 1.57 个核

基线 `handoff-20261118`，提交 `dd9ba4c9ebae59db68055da5e8ad566b87d6eb16`。指定检查 `bash scripts/check-platform-offline.sh` 退出 **0**，末行 `status=PASS scope=platform-offline`。本轮只读历史记录，在宿主运行合成输入，没有打开实验卷、挂探针、启动沙箱或改采集器。

**判断：七支确实同时开始，但它们在同一 CPython 解释器内反复执行“少量 Python → 一次很短的 C 调用 → 回到 Python”。最有证据的主因是这个线程模型，特别是 GIL（同一时刻只允许一个线程执行 Python 字节码）及反复交接的成本，不是宿主凑不出七个核。** 在没有真实探针写入、没有 provider 屏障的情况下，直接运行生产查询内循环就重现了 1.47；仅换成独立进程，同一输入变为 6.58。真实运行没有 GIL 等待计数，不能把每一秒等待归到 GIL。暂停后串行的 2.147 秒仍是已验证的完整方法；进程版只测了内循环。

## 实测：不要把两批的并行度和每页次成本拼成一行

并行度 = 七个工作线程 CPU 秒之和 / 墙钟秒；每页次 = 墙钟 / 两层两遍的有效偏移数，不是单次查表延迟。

| 批次 | 页次 | 墙钟 s | 工作线程 CPU 秒 | 并行度 | µs/页次 |
|---|---:|---:|---:|---:|---:|
| 11-18 旧七支，guest 运行，整轮 | 645,238 | 10.264852 | 16.116435 | 1.570 | 15.909 |
| 11-19 七支暂停，并行宿主查询 | 618,684 | 9.053046 | 未记录 | 未知 | 14.633 |
| 11-19 七支暂停，串行宿主查询 | 620,732 | 2.146718 | 未记录 | 未知（调度宽度 1） | 3.458 |
| 11-19 单支暂停，另有驻留扫描 | 88,448 | 0.497715 | 未记录 | 未知 | 5.63 |
| 本机合成：七线程，两层内循环 | 645,238 | 8.765903 | 12.889338 | 1.470 | 13.586 |
| 本机合成：七进程，同一输入与函数 | 645,238 | 0.243522 | 1.601322 | 6.576 | 0.377 |

旧轮从派发前到返回后批级去重结束计时；16.116435 只算 worker，不含主线程、guest 和独立探针进程。9.904 秒是七支共同读取区间，不是此分母。暂停批从第一支宿主查询开始到最后一支结束计时，与旧整轮并列但不直接算加速比。

## 宿主没满，线程时间主要消耗在哪里？

宿主 2 路 × 32 物理核 × 2 硬件线程，当前 `nproc=128`，`MemTotal=527823908 KiB`（503.37 GiB），内核 `6.19.9+`。旧 VMM 收据的 host boot ID 与本机一致，查询收据记录了同一内核。历史 sysstat 亦记录 128 个逻辑 CPU。当前合成进程允许 CPU 0–127，所属会话、用户及 user.slice 的 cpu.max 均为 max；这不是旧控制器亲和性的记录。

旧样本起点约 11-18 21:19:30（上海时间）。宿主 `sar -u -f /var/log/sysstat/sa18` 的包围区间 21:10:00–21:20:05，全机平均 idle **99.58%**。即使把该区间全部非 idle 时间都归给这 10.265 秒，也只有约 **32 核**的平均预算，不可能是 128 核整轮打满。不能据此排除短时峰值或个别核拥挤，也不能把 1.57/7 当作全机利用率。

用旧批 `page-rounds.jsonl: readers.*.{start_ns,end_ns,thread_cpu_ns}` 得到七个线程存续时间合计 **70.671 线程秒**，其中执行了 **16.116 CPU 秒**。相减的 54.555 秒是各线程未在 CPU 上执行的时间之和，彼此重叠。各支 `samples.jsonl: host_stage_costs.*.{cpu_ns,elapsed_ns}` 给出：

| 七支两遍合计 | 线程内经过时间之和（秒） | CPU 秒 |
|---|---:|---:|
| 直接后备查询 | 36.074 | 8.884 |
| 快照下层查询 | 23.702 | 5.188 |
| provider 两次会合及读取 | 3.224 | 0.016 |

**仅两层查询就占 14.072 CPU 秒（87.32%），并有 45.703 线程秒未在 CPU 上。** 已定位到等待主要发生在哪一段；这些数不是分摊墙钟，也没有区分 GIL、调度和内核阻塞。内存访问慢时线程也可能仍在核上，CPU 时间不能诊断带宽。

## 代码中哪里串行，哪里没有全局锁

下列行号均指基线 `scripts/`：

- `seven_restored_pages.py:148–191`：一个控制进程、一个七线程池、每支提交一个同步 worker。主线程在全部提交后才收结果；依次调 future.result 并没有将查询串行化。`live_task_cache.py:298–346`：每支内部依次读两层、provider、再读第二遍。不是七个进程，也不是 asyncio 事件循环执行查表。
- `snapshot_cache_residency.py:352–372,385–401`：NumPy 去重、求相邻差、切段；Python 遍历段、建 ctypes 数组、更新本地字典。每段通过 CDLL 调一次真实 mincore；有效偏移逐个在 Python 创建键值、经 CDLL 调 libbpf 查一次，再由 Python 验代号、判读驻留、追加结果、统计。数值数组运算有 C 内核；不能把整段 NumPy 包装或整个循环都算作无 GIL。CDLL 在外部函数执行期间释放 GIL，回到 Python 要重新获取。645,238 次逐页调用意味着同量级的交接机会，不是一次释放后七支各自跑完整遍。
- `snapshot_cache_residency.py:84–121,179–206,253–265,325–350`：每来源共享一个探针，每个读者用独立结果 map；query_lock 属于读者，获取失败直接报错，不会把七支排成一队。共享管理锁用于取得/释放读者或异常拆卸，不是逐页锁。真实探针在每段使用共享的按 TID 索引的状态/计数 map，在每页 filemap_get_entry 路径访问状态并写对应读者的结果 map；不同键不保证内核不会争用。Python 的 residency、result 是单次调用本地变量，统计列表属各读者，非每页写共享日志。
- `seven_restored_pages.py:60–83,175–196`：provider 有真实的条件变量屏障；每帧等所有活跃支到齐，只让一支读共享设备。每轮两次，不是每页一次。轮末合并集合、写日志在主线程。没有可删除的“覆盖七支逐页查询”的 Python 全局业务锁。

## 本机如何复现，以及它排除了什么

[bench.py](bench.py) 直接调用基线的 `SnapshotCache._query_owned`，没有改写其 Python 循环。由旧批七份 `pair-0000-{backend,lower}.bin` 的第二列提取每支每层的段长频数、无映射行数，存为 [shapes.csv](shapes.csv)。有效偏移无重复；合成器固定种子 20261120，重排段、压缩段间空洞、打乱输入行，保留 38,434 段次、645,238 有效页次、两遍和无映射行。每支 89,490–93,722 有效页次。两个组使用同一批数组、同一批按角色独占的临时内核 BPF 哈希表以及相同人工表项。mincore、bpf_map_lookup_elem 均为真实调用；查的是匿名零页映射和预填表，不是真实沙箱文件、绝不是真实 PFN。每遍校验命中数。匿名映射与未固定到文件系统的 map 随关闭释放。

CPython 3.12.3；线程池或 fork 出的七个单线程工作进程，在各自地址空间预读零页、等屏障，再按直接/下层/直接/下层查询。墙钟取最早 worker 开始至最晚结束；CPU 只加各自 thread_time，不含建池、填表和启动。初始化试跑曾因只让父进程预读而在子进程驻留校验失败，未纳入对比；正式两组均在工作者自身预读，没有放宽断言。[逐支原始时间与 CPU](benchmark.jsonl)。复现命令（需有创建匿名 BPF map 的权限）：

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python3 -B docs/records/seven-query-parallelism-20261120/bench.py
```

**为何支持 GIL，而不是全局业务锁或带宽？** 合成线程组没有真实探针写入、provider 屏障、guest 或实验卷，仍复现低并行度；进程组保留了同样的内核查表和数据量，却接近七核，而且合计 CPU 从 12.889 降至 1.601 秒。不是简单地将同一笔 CPU 时间摊到更多核。线程调度、GIL 交接及进程内分配等开销能随模型消失；这不能精确给 GIL 单独定价。若合成输入已被宿主内存带宽硬性封顶，仅改进程模型不应出现这样的提升。真实 mincore 扫共享后备文件、探针实时更新内核 map，还要读页表、核对和留证，合成没有覆盖这些共享路径；没有 LLC 未命中、带宽或内核锁等待计数，不能宣称它们在真实链路上没有影响。

## 能否比 2.147 秒快？

- **若只提高并行度，不减少旧轮的 16.116 CPU 秒**：七路的上限是 7，完美均衡的下限为 **2.302 秒**；按合成观察到的 6.576 折算为 **2.451 秒**，均未加额外串行等待。旧批固定各支工作量时，最重一支自身就有 2.451 CPU 秒。这是旧轮的条件推算，不是暂停批的预测。
- **若隔离解释器也消除了交接开销**：在 6.576 的平均并行度下，低于 2.147 秒要求同窗口的 worker CPU 总量低于约 **14.12 核·秒**，并能容纳派发、同步、结果合并等耗时。合成发现 CPU 工作量确实可变，所以低于串行**有可能，但真实墙钟未知**。不能用 0.244 秒代替整轮，更不能拿合成加速倍数去除以旧墙钟。生产探针按控制器 PID 过滤，fork 后不会自动接收子进程事件（`snapshot_cache_residency.py:89–104`）；合成的继承只适用于已填好的只读结果表。
- **选择：暂停后正式测量仍用串行；不建议花时间删除读者锁或增加线程。** 同等量级负载下串行已经实测 2.147 秒。没有证据断言所有多进程优化都不值得；也没有证据承诺其优于串行。要给生产多进程定量，缺少相同暂停对象、正确绑定各进程探针后的实际 CPU、查询墙钟及同步合并开销；要量化 GIL 占比，则缺旧线程等待栈或对应调度样本。本轮不做这两种真实采集。
