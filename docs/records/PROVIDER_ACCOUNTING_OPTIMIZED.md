## 只共享同一点的准备工作，不缓存跨点归属

性能分析发现，旧实现分别为原单条记录和分段记录调用一次完整计数，每次都解析两份guest元数据并遍历三层查询行。10点中共完整解析40次。两种准入使用的guest身份、物理映射和偏移候选本来就是同一份数据。

在线路径只改`scripts/provider_slot_cache.py`和`live_task_cache.py`：

1. 提取`provider_context`，在同一点内准备一次缓存候选、三层物理集合和已确认guest页，供两种准入共用。原字节接口的完整解析由每点4次降至2次。
2. 在线入口传入已经由`decode_array`检查过的前后元数据及对应数组，用已有`matching_tags`和数组条件筛选。这一步不再重复解析字节数据；对当前点仍重新核对guest身份、三次VMM映射及文件物理页冲突。
3. 单条记录、分段来源、四份代次核对、完整host页准入、当前/旧副本及物理去重规则保持原样。没有跨采样点缓存候选，也没有扩大有效时间或改变请求顺序。

原有参数和返回字段保持。原字节调用仍可使用行子集或原来支持的行顺序，并保留原数据检查；只有新增的数组入口要求数据已校验、完整且与起点有效缓存页对齐。

## 剩余未知量按第一个缺口分类

新增离线脚本`scripts/report_provider_segment_unknown.py`，解释的对象是：完整缓冲驻留物理页，扣除原单条记录与分段记录共同确认的当前、旧副本后的集合。先按物理页号去重，分配边界页另列；不同物理别名给出不同原因时单列。

判断顺序是分配身份变化、段记录变化、含初始未知段、后续失效、偏移候选缺失、guest身份或VMM/文件页冲突、内容版本未知或混合。某张页只记第一个未通过条件，不跨时间累加。下表只列本次出现的类别，单位为KiB。

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 0 | 880 | 1784 | 1068 | 0 | 16 | 3748 |
| 1 | 0 | 1784 | 1664 | 0 | 28 | 3476 |
| 2 | 308 | 1784 | 1496 | 0 | 28 | 3616 |
| 3 | 1888 | 1700 | 320 | 132 | 0 | 4040 |
| 4 | 0 | 1728 | 2300 | 0 | 0 | 4028 |

| 8 | 16 | 1728 | 2208 | 0 | 0 | 3952 |
| 9 | 0 | 1728 | 2300 | 0 | 0 | 4028 |

**初始未知段不能靠延长有效窗口补齐。** 这类host整页中至少有一段仍为`generation=0, source_offset=UINT64_MAX`，即记录建立后没有获得请求填充的来源归属。表中统计的是因此未能整页确认的物理量，不是“整页从未写过”的字节数，也不解释成零占用。

缺少偏移候选表示已有稳定来源，却未匹配本次采集起点的guest缓存候选。它不直接证明内容是匿名内存或非缓存；现有查询只覆盖起点候选，不能据此给所有来源补标签。5个点以这一类最大，4个点以含初始未知段最大，另1个点以段记录变化最大。

本次后续失效类别为0，主要缺口不是GET_DATA等待期间失效过早。下一步应核对初始来源和候选范围；额外预读会改变被测内容，不作为补齐归属的方法。21张分配边界页保持单列；混合完整页仍包含在未知总量中。
