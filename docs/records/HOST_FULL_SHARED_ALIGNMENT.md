## 现有函数的三处适用条件

1. [`live_residency`](../../scripts/run_host_file_restore.py#L113)要求传入实例只有一个内存后备身份；模拟两个后备时，实际函数在任何设备查询前按预期拒绝。完整BPO不能把七个实例直接全部传入，也不能为方便查询把原主沙箱算成恢复实例。
2. [`shared_drives`](../../scripts/host_prefix_compare.py#L43)只返回传入全部实例共同使用的只读盘；[`classify_objects`](../../scripts/host_scaling.py#L43)把传入角色集合直接作为内存对象的使用者。完整任务必须保留各对象的实际使用者，不能要求每个共享对象都覆盖全部七个沙箱，否则会漏掉只在三个子沙箱中共享的对象。
3. 完整轻量入口目前[调用HostFileMonitor时没有关闭PSS](../../scripts/platform_tasks.py#L396)，其默认是开启。完整入口尚未调用[递增入口使用的准备同步](../../scripts/validate_isolated_agentenv.py#L728)。新模式需要显式关闭PSS并复用准备同步，旧入口默认不变。

当前AgentENV源码按规范化的内存镜像配置路径[复用只读设备](../../AgentENV/src/sandbox/ublk/device.rs#L570)，[恢复时取得该设备](../../AgentENV/src/sandbox/firecracker/sandbox.rs#L2175)。这是按快照识别对象的源码依据；旧完整运行没有保存实际设备身份，不能据此补写当时“恰好两个物理设备”的结论。新运行仍以实际映射和驱动身份为准。

## 固定新模式的对象分类

| 对象 | 选择与去重 | 如何报告 |
| --- | --- | --- |
| 共享只读系统／工具后备 | 从实际驱动取得，块设备按rdev去重，记录实际使用者 | 指定对象的全局缓存驻留 |
| 快照内存设备 | 仅从恢复实例实际映射取得，关联第11／24步快照；同设备只查一次 | 各设备分别列出，不把两组各三人写成七人共享 |
| 快照原始内存层 | 从实际使用的内存镜像配置取得lower文件，普通文件按device＋inode在两组间统一去重 | 完整BPO本轮保存生成的层标为“本轮保存产物” |
| 公共准备输入／导入层 | 按来源与本轮生成产物区分 | 单列，不乘沙箱数；GRPO没有快照对象也不补造 |
| 独立可写块设备 | 只保留实际身份，不做整设备驻留扫描 | NOT_REQUESTED，驻留字段为空 |

短恢复中的555.457 MiB原始层来自已有快照导入；完整BPO的内存层则由本轮保存产生，[源码会生成内存层和镜像配置](../../AgentENV/src/sandbox/firecracker/sandbox.rs#L1174)。两者可以沿用`snapshot_memory_layer`类别，但来源必须另记，不能把完整BPO新生成的层全部扣成公共准备开销。

实施时先收集两组的实际目标，再建立整批对象表，最后每个对象查询一次。不要简单调用两遍旧完整查询再求和：两组可能引用同一只读盘或同一lower文件，会重复查询、重复计数。不同目录下的复制文件若inode不同就是不同缓存对象，不能按文件名或内容相同合并。

上述范围延续已验证的指定后备测量。独立可写盘使用的不可变rootfs下层文件，是另一批可能共享的文件；当前三类查询没有完整覆盖它们，不能把“未查独立盘”解释成“这些下层文件没有缓存”。源码[另行物化rootfs层](../../AgentENV/src/snapshot/repository/backends/posixfs/runtime.rs#L75)。本阶段把这个范围列清，不自动增加目录遍历或将其混入既有三类统计。

## 查询放在活对象删除之前，保存期间只读便宜计数

保持原并发和分支顺序，不把完整任务改成1→2→4→7短测。新模式采用以下位置：

| 阶段 | GRPO | BPO |
| --- | --- | --- |
| 准备完成、guest创建前 | 同步自有文件系统后保存无guest基线 | 同左 |
| 根沙箱就绪、首段原动作前 | 实际驱动身份与组内计数 | 主沙箱身份与组内计数 |
| 第11／24步保存前后 | 无此阶段 | 记录组内计数、时刻、快照ID和来源；不做驻留扫描 |
| 原有恢复批次就绪 | 无此阶段 | 分别保存早／晚三个实例的实际映射、驱动与快照关系；不做驻留扫描 |
| 全部原路径完成、官方检查前 | 一次指定共享对象驻留查询 | 一次两份快照的指定对象联合查询 |
| 官方检查及清理 | 保持原结果与清理流程 | 同左 |

最终查询放在[`do_grpo/do_bpo`返回之后](../../scripts/run_prettier6604_grpo.py#L734)，官方检查及删除实例之前。此时原路径已结束、设备和文件仍存活。两组恢复继续使用[原有批次顺序](../../scripts/run_prettier6604_grpo.py#L608)，不另加任务中途的长驻留查询或新等待屏障。

保存前后只添加组内计数，放在原暂停段外；不延长原保存所需的暂停。快照保存后尚无恢复内存设备时标为“设备尚未创建”；运行配置尚未物化时标为“尚未物化”，不是零驻留。待原恢复流程自然建立设备后再读取实际配置，不为测量提前创建、预读或强制保留设备。暂停、回收和采样空缺继续按原行为记录。

一次完整运行只得到任务末尾指定对象驻留，不形成这些对象每0.1秒的物理驻留曲线。运行中曲线仍分别是guest Cached和host统计组file；它们与末尾对象驻留的范围不同，图注保留这个区别。完整调度中也不套用短测的七倍单沙箱参考。

## 成本与原计时保持明确

每次观察保存单调时钟开始／结束、查询线程CPU、前后组内计数及逐对象查询时段；元数据检查与驻留查询分别列出。查询仍是顺序观测，不是同一瞬间的物理并集。

在最终驻留查询前新增“原路径完成时刻”。原工具累计耗时继续只求原动作；从原路径开始到完成的用时不含随后查询。原`rollout_end`仍在官方检查之后，不把新查询时间偷偷从旧整轮定义中扣除：新模式整轮用时包含查询，报告同时列出原路径用时、查询用时及整轮用时。保存／恢复原接口耗时继续引用原事件，不把新增元数据记录或全部准备时间混作接口耗时。

五轮短恢复的3.614±0.036秒只作既有成本参考。完整BPO的目标数量和层数不同，不能直接套用这个数值或承诺相同开销。
