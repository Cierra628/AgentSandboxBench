# 连续恢复时，变的是运行设备，留下的是诊断槽位文件

基线 handoff-20261118：`dd9ba4c9ebae59db68055da5e8ad566b87d6eb16`。离线检查退出码 0，末行 `status=PASS scope=platform-offline`。分析对象为 ea6f7eb 的同一私有服务、同一快照、五批七支；没有重跑。原始证据根目录：`.artifacts/storage-isolated-service/20261121T034046Z-1477264/`。下文服务日志、设备日志分别指其 `service-logs/server.log`、`service-logs/ublk-daemon.log`，时刻均为当日 UTC。

**直接原因有两层。** 恢复按快照的内存镜像配置申请运行设备，不要求沿用旧编号。并发恢复还可能为同一配置短暂创建多个候选设备，最后共用其中一个。诊断槽位文件却保存在整个服务共用的目录里，设备释放时不删除。读取端把“同一镜像配置”的文件全部拿来核对一个当前设备，因而遇到其他设备的记录就报错；设备号再次使用时，写入端还可能因原文件同名而无法创建槽位。这不是快照保存了错误的 inode。

时间口径是批内两个事件的时间差，不冒充逐请求 RPC 耗时。起点取设备日志首次 `creating raw overlaybd device` 且配置以 `memory/image.json` 结尾，终点取服务日志 36、70、102、143、154 行。逐支映射在第 1 批的 `guest-cache/try-1/process-restored-N/snapshot-backend.json`：`regions[].path`、`identity.rdev=66312`（解为 259:8）、`identity.inode`。其中 `identity.device=6` 是节点所在文件系统，不是块设备主次号。失败批只保存 `vmm-child-binding.json:vmm_binding.sandbox_id` 等进程身份，驱动 ea6f7eb 的 `scripts/run_seven_paused_serial.py:147–175` 在内存中取设备身份，却在逐支输出之前失败。槽位文件的 inode 和下层镜像文件的 inode 都不能拿来补设备节点的值。

**槽位记录不在快照里。** `service-provider-slots/142-N-0-*.json` 的 `image_config` 相同，`dev_id` 来自当次设备，另记队列和槽位号。按各组文件修改时间与设备回执交叉核对，共 11 个设备号，每号 16 个槽位。第 1 批证实路径尾号与 16 个槽位的 dev_id 一致；主次号与 inode 只有 VMM 侧有测值，不能说两侧逐项相等。第 2、3、5 批失败的断言也只比较路径尾号与 dev_id，没有报过主次号或 inode 不符。

## 为什么同配置有多个编号，哪些记录被误选

- 设备日志的 `try add_dev requested_dev_id=4294967295` 后是内核返回的具体 dev_id（如第 34 行起）。服务端本机对应实现 `AgentENV/src/sandbox/ublk/device.rs:637–648,686–728`：已有活动对象就共用；并发创建时先记候选回执，再选已登记的设备，放掉多余对象。因此不能把某个分支名下的创建回执直接写作它最终映射的路径。
- 第 2 批服务日志 70–72：3、5 都有回执，5 随即释放；设备日志 300 行确认 5 已删除。第 3 批服务日志 102–114：6 以外的六个候选均立即安排释放。第 5 批只有 2 有成功的内存设备回执，第 7 支另在服务日志 164 行超时。表中对最终路径的推断据此作出。
- `scripts/provider_slot_cache.py:62–75` 按文件名字典序读目录，只按 image_config 排除其他镜像，接着要求每个候选的 dev_id 都等于当前设备。按保留文件与该顺序重建，第 2 批当前 3，先遇到的异号是同批 5（前批 8 也还在）；第 3 批当前 6，异号是同批 10；第 5 批当前 2，异号是前批 10。这是离线还原，异常文本本身没打印文件名。仅清理批与批之间的文件，挡不住第 2、3 批这样的**同批多候选**。

## 第 1 批清理了设备，没有清理诊断文件

设备日志 48–58、99–239：第 1 批成功创建的 1–8 号设备全部有删除完成回执，包括 RAM 的 8 号。下一批确实再次分配了 8（设备日志 265），所以不是“旧 8 号一直占用，迫使新编号向后排”。两批之间，本服务的设备事件只剩有意跨批保留的工具设备 0；实验卷 /dev/loop5 及挂载也按设计保留到五批结束（attach.stdout、result.json:mount_identity、remaining-own-loops.stdout）。上一轮 cleanup=PASS 检查沙箱、VMM 与探针，不检查槽位目录（ea6f7eb 的 seven_process_repeats.py:22–30,56）。第 1 批 8 号的 16 对 .bin/.json 仍在，不能概括为“完全清干净”。未采宿主所有设备、挂载和 loop 的逐批清单。

统计设备日志按 dev_id 配对 `added to ublkdrv` 与 `device deleted`，含工具盘和分支其他盘，只代表本服务日志中的数量，不是宿主盘点。第 3、4 批开始数和峰值相同，恢复结果却相反。第 4 批结束时除 0 号外，6、8、9、10、12、13、14 均有分号、未见对应删除；这七个号在**此前几批全都写过同名槽位文件**。设备日志 829–973 在内存设备创建请求期间记录 112 次 File exists（7 × 16），随后服务日志 143–149 七次 RPC 超时。第 5 批只出现 16 次和一次启动超时。这与槽位碰撞吻合，不支持“第 4 批开始前就堆满活动设备”。

写入路径提供了机制依据：`patches/agentenv-provider-slot-observation.patch:24–42,147–155,180–188,232–240` 和 `patches/agentenv-provider-segments.patch`：槽位任务在开始服务前创建文件，名字只含 daemon PID、dev_id、queue、slot；排他创建遇同名就返回错误。销毁时解除映射，没有删除两个文件。本系列 daemon PID 未换。**强证据支持旧诊断文件造成第 4 批启动失败**；错误行未记录具体冲突路径、设备号及 RPC 请求标识，不能逐个请求证明 30 秒等待都是由哪一个文件造成。宿主全局 loop 数亦未按批记录。

## 最小改动与验证条件（未实施）

优先修**运行时槽位文件的生存期**，不要修改快照，也不要固定设备编号。创建者应在该代槽位停止使用时只撤下自己发布的 .json/.bin，包括并发创建后被放弃的候选；不能清空共享目录或覆盖仍在用的槽位。读取端应从已经固定并核对的 VMM 设备出发，仅选同 image_config、同活动设备、当前 provider 确实映射的完整队列；保留现有进程、文件身份、槽位唯一性和完整性检查。单改读取端可以处理异号记录，却不能解开写入端的同名文件；单改跨批清理也不能隔离同时存在的候选。

改后最小验证建议：同一服务与快照连续恢复，覆盖“同批两个候选”和“旧设备号再次分配”两种情形；确认旧文件不再阻塞新槽位、新读取不接纳旧记录，每个活动设备的 16 个槽位完整，七支都通过原身份检查。为补齐缺失证据，在逐支 mapped_device 返回时保存路径、st_rdev 主次号、st_ino；在槽位创建失败时记录实际文件名、dev_id、queue/slot 及 RPC 标识；释放前后记录该代文件是否仍在。若要判断宿主设备压力，在批边界同时保存 ublk、loop、挂载清单。本轮没有修改代码或执行此验证。
