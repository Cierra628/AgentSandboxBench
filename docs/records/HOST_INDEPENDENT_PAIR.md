## 实现保持原任务和旧入口

显式增加`--independent-matched-task`，将一次41动作分为三个私有服务／卷：11步制作一份快照，导出原生仓库，随后单沙箱执行10步、双沙箱各执行相同10步。两次导入使用同一快照，前一组的可写卷不再供后一组使用。恢复前额外查询一次普通文件驻留，其他0.1秒计数、每秒PSS和任务后查询继续复用。

- `scripts/host_independent_task.py`：验证真实Prettier前缀元数据、导出与导入前缀证据；不伪装成小型恢复示例。
- `scripts/native_checkpoint_bundle.py`：共用已有原生仓库归档机制，旧`export()`的成功状态、固定服务镜像和`phase=capture`条件保留。
- `scripts/run_prettier6604_grpo.py`、`host_file_matched_task.py`和`validate_isolated_agentenv.py`：显式区分快照制作与单／双恢复，导入的11步只作证据，不计为新执行；保留原动作、127退出、补丁及官方结果检查。
- `scripts/run_host_independent_pair.py`：按顺序管理独立私有卷，不同时分配三个24 GiB卷；原`--matched-task`及普通三任务的默认行为不变。

已有前缀可用`--resume-prefix`继续，必须提供成功导出或明确的只读恢复记录。失败源卷的恢复还要求归档内容校验通过。续跑只新增30动作；完整比较包含原11步，共41动作，两者分别记录。

最终清单没有缺失路径或查询错误，唯一不稳定对象是自有`volume.ext4`：容量仍为24 GiB，但查询前后修改时间变化。此时guest和私有服务已退出。已确认的是文件元数据变化；未记录具体写入者，延迟的文件系统／loop写入是可能机制，不作为已验证根因。

新路径现将卷镜像放到最终清单的最后：先扫描卷内文件，再仅对自有文件系统执行`sync -f`，最后扫描其后备卷镜像。这样也处理前面文件查询可能引发的访问时间等元数据写入。回调位于原清理错误处理内，失败仍继续定向释放资源；不做全局同步，不暂停运行中沙箱，不放宽原稳定性判断。没有采用只读重挂载：实际内核`fs/super.c:1099–1100`会调用`invalidate_bdev`改变块设备缓存状态，不适合用来保持原扫描条件。最终清单明确取同步后的状态，不能追溯修正旧未同步读数；两组运行中的扫描不增加同步。顺序检查通过，**这项修补随后已在两组实跑通过，见最新结果**。
