# host共享内存恢复的最小对照方案（2026-10-20）

本页是执行前的离线设计。后续接入和短恢复已完成，见[执行结果](HOST_FILE_RESTORE_VALIDATION.md)：功能与运行时设备查询通过，最终普通文件记账发现4.232 GiB差额，当前优先解决该差额，暂不执行原41步任务对照建议。

**离线核对完成。推荐先比较同一实际快照恢复1个和2个guest，在恢复检查通过后的相同短区间观测；暂不执行分支后缀，也不输出内存节省比例。** 本次只读取源码、保存的元数据和日志，没有启动服务或沙箱，没有读取负载文件内容或修改运行代码。

这个短实验回答：轻量采集能否覆盖真正共享的内存设备，以及增加第二个恢复guest后，host文件缓存、匿名内存和PSS分别如何变化。它不回答完整任务的性能或物理节省率。此前[两个冷启动沙箱](HOST_FILE_PAIR_VALIDATION.md)的结果继续有效，但不是这个恢复实验。

## 1. 已有证据确定了真正的共享路径

2026-10-17的[真实双分支](PROVIDER_REAL_PAIR.md)先运行共同11步，保存一次，删除父VM，再恢复`early_1`和`early_2`。原始结果确认11+10+10=31个实际动作，两个子guest的恢复检查和清理通过。

两个保存的`snapshot-backend.json`均记录：

| 项目 | 两个VMM的记录 |
| --- | --- |
| 内存后备设备 | 同一个`/dev/ublkb105` |
| 设备身份 | device=6、inode=28564、rdev=66359 |
| 内存布局长度与基页 | 4,294,967,296字节、4096字节 |
| 文件后备映射权限 | `rw-p`，可写的私有映射 |
| 原始内存层 | 同一个普通文件，device=1802、inode=917756 |
| 原始层文件大小 | 594,051,072字节；不是驻留量 |

`rw-p`允许两个VMM起初使用同一文件缓存，写入后产生各自的匿名副本，即写时复制（COW）。不是两个guest写同一份可变RAM。只知道设备身份相同还不能量出共享多少页；旧实验另有物理页证据，本方案不把它换算成新的file数据。

源码支持该路径：

- `AgentENV/src/sandbox/firecracker/sandbox.rs`的恢复路径调用`get_or_create_shared_mem`，将返回设备交给`load_snapshot_file`。
- `AgentENV/src/sandbox/firecracker/instance.rs::load_snapshot_file`使用Firecracker的`File`内存后端。
- `AgentENV/src/sandbox/ublk/device.rs::get_or_create_shared_readonly`以规范化的`image_config`路径作为复用键；仍有有效引用时复用同一只读设备。最后一个引用释放后异步删除设备。
- `scripts/run_prettier6604_grpo.py::SampledPaths.do_bpo`保存共同前缀、删除父guest，再从同一template创建两个子guest。原检查还核对保存前后的文件状态和guest探针进程连续性。

源码描述当前工作区；旧原始记录证明当次真实映射。下一次普通内核恢复仍需重新检查实际设备、映射和身份，不根据源码直接记为通过。旧运行使用诊断guest内核和精细采集器，不能冒充普通内核轻量路径已经通过。

## 2. 最小比较范围：同一快照，先1个再2个

建议一次私有工作流程完成，统计组在所有准备和服务创建之前建立，保留同一个实际快照：

1. 新建父guest，只执行原共同前缀11步，保存一次并删除父guest。保留快照，不运行后缀。保存本身使用原生checkpoint暂停；采样不额外暂停guest。
2. 保存输入准备及服务就绪、保存完成且父guest删除后的同步计数，分别标注阶段。确认此时没有VMM，记下第一组恢复前基线`F0_1`。
3. **N=1：**从该快照新建一个guest，核对恢复边界、原探针连续性、VMM身份和后备设备；启动同样的guest轻量采样。检查通过后正常运行5秒，取得`F1(t)`及PSS。区间结束时、删除guest前查询内存设备和相关只读文件驻留。
4. 删除这一个guest，确认自有VMM和内存设备释放完成；关闭采集器打开的设备句柄，不人为保留设备以维持缓存。保留同一快照及服务，记录第二组恢复前基线`F0_2`。
5. **N=2：**从同一快照新建两个guest，执行相同检查和采样准备。两个均通过后共同正常运行5秒，取得`F2(t)`及逐VMM PSS；确认二者映射同一个内存设备。区间结束时、删除guest前再查驻留。
6. 删除自有guest、快照和服务，再做普通文件最终mincore及既有清理。失败数据和失败卷按原规则保留。

这里总共创建1个父guest、3个恢复guest；只新增共同前缀11个任务动作，没有三个完整任务或后缀重放。N=2按既有方式逐个恢复，不把它写成同时恢复；第一个guest多等待的时间保留在时间线上。两个观测区间以“本组全部恢复检查和采样准备完成”为零点，创建和准备耗时另列。

guest从同一快照恢复，boot ID及探针身份可以相同，这是预期现象；用不同sandbox ID、host VMM的PID和启动时间区分实例。不要套用冷启动检查中“两个guest boot ID必须不同”的条件。

不清理host全局缓存，不预读任务文件，不锁页，不改变DAMON策略。第二组可能受第一组留下的原始层、服务及磁盘缓存影响，释放内存设备并不清空这些缓存；用两次基线和时间线显示这种顺序条件，不宣称两组起始物理缓存完全一致。

## 3. 公共准备成本单列，暂不计算比例

此前两个冷guest创建前，`file`已约14.127 GiB。输入RAM镜像与其内部文件缓存都会占用host内存，不能将这份公共准备成本按沙箱数量重复计入“节省”。恢复实验还新增了快照制作成本，不能沿用冷启动的14.127 GiB作为新基线。

主图保留原始`file`。在旁边显示两组各自的增量曲线：

```text
A(t) = F1(t) − F0_1
B(t) = F2(t) − F0_2
```

基线是各组恢复前直接读取的值，不插值，不补造；原始计数、两次基线差、保存阶段及恢复阶段全保留。增量为负也照实显示，可能包含正常回收和背景变化；不解释为负的沙箱内存。

只有将来比较条件和记账核对成立、且A为正时，才考虑`2×A`的线性参考及`(2×A−B)/(2×A)`。它仍是外推参考，不是实测“不共享”后端。本次建议的固定顺序短实验只交付曲线和记账核对，不输出这个比例；不为获得非零增量追加运行。当前`report_host_file.py`比较命令使用完整流程file峰值，**不适用于这里的分阶段增量**。

`memory.current`、`anon`和PSS仍需保留：file增量小而anon明显增加，可能是写时复制，不能单看file就认定总内存节省。PSS用于独立观察映射内存，不要求等于file或current。

## 4. 后备清单必须覆盖内存设备，查询要早于其释放

当前`host_file_monitor.mincore_file`只接受普通文件；外层`validate_isolated_agentenv.py`在guest删除和服务停止后才执行普通文件mincore。这个时序适合避免loop镜像受日志写入干扰，却可能错过已经释放的内存设备。不能以清理后设备不存在推断它运行时驻留为零。

下一步应分开保存两次检查，不把不同时间的清单相加：

| 对象 | 来源与身份核对 | 查询时机 |
| --- | --- | --- |
| 共享内存ublk设备 | 从实际VMM映射与恢复配置关联；保存st_dev/st_ino/st_rdev、映射范围及容量；N=2只计同一设备一次 | 本组观测结束、guest仍运行时 |
| 实际使用的原始内存层 | 从该快照的memory/image.json读取引用，核对文件身份及本次provider已打开该文件；当前旧证据是单个原始层 | 与内存设备同一检查窗口，明确各自起止时间 |
| 输入commits、私有image-cache | 按实际保留文件枚举，不固定为历史100项；设备号/inode去重 | 写入进程退出后的最终检查 |
| 输入RAM loop镜像、私有卷loop镜像 | 显式记录两个后备文件及各自身份，不能只枚举内部文件 | 同上，卸载前 |
| 快照仓库及运行目录的保留普通文件 | 增加当前清单未覆盖的snapshot-store和snapshot-local-cache文件；与前述内存层去重 | 最终检查；不能替代运行时内存设备检查 |
| 实际使用的rootfs、工具等其他块设备 | 本次服务的配置和打开句柄，记录是否共享及查询覆盖 | 首次短验证列清；未查询则标为清单外，不能记零 |

内存设备查询只需复用已有`mmap`与mincore方法，采用`PROT_NONE`避免访问内容；设备长度由实际容量核对，不能使用块设备的`st_size=0`。不直接实例化旧`SnapshotCache`，它还会启动BPF和物理页查询，不符合本次轻量范围。旧块设备mincore证据可支持这个方向，但新的独立轻量实现仍需一次真实短验证。

设备句柄只在本组guest存活时打开，查询结束及时关闭，避免测量程序使设备在两组之间额外存活。采样前后核对VMM、设备身份及有效范围；设备消失、变化或权限不足明确失败，不以零代替，不拖延后端请求来维持有效时间。

mincore得到全局驻留；file得到统计组记账。运行时检查和最终检查各与自己前后的file比较，分别保存范围、时间和不足量，不合成一个时刻的物理并集。不足时保留`SHORTFALL_REQUIRES_RESOLUTION`并停止比例输出；无不足也只说明没有检测到问题，不证明组外记账为零。设备缓存和原始层文件缓存是不同缓存对象；不按内容相同合并，也不把mincore总量直接加到file。

## 5. 最小实现和完成条件

离线核对时还没有可直接调用的“普通内核恢复N=1/N=2轻量对照”命令，现已新增显式`--restore-pair`入口。原平台配置仍拒绝直接将host监控与恢复组合；新外层选项选择专用的短恢复路径。旧真实双分支入口及`root_count`保持原含义，不通过它们绕过诊断内核或暂停分析条件。

建议只补三处：为现有私有恢复控制器增加显式的短对照路径，复用前缀/保存/恢复/清理；为host采集器增加受本次资源身份约束的块设备mincore及上述快照文件清单；为离线报告增加阶段标记、双基线及增量图。普通任务、后端、guest内核和旧精细采集入口保持不变。

首次正式执行就作为新路径短验证，只运行上述一组N=1和一组N=2，不追加相近验证。完成条件是：

- 新统计组覆盖准备及服务创建，池关闭；父guest11步、一次保存和3次真实恢复分别检查通过，失败或跳过不计通过。
- N=1/N=2区间、各自直接基线、0.1秒host/guest数据齐全；每组至少2次完整覆盖正确VMM的周期PSS，缺失保留而不延长区间凑数。
- N=2实际共享同一个内存设备，私有映射、原始层和实例身份明确；运行时mincore确实在设备释放前完成，无内容读取、采集暂停或额外驻留措施。
- file、anon、current、PSS、guest Cached分开解释；mincore清单外来源、组外记账风险、固定顺序和初始缓存差异写入结果。
- 两个5秒区间、采集成本、清理和失败保留记录齐全后结束。没有新比例或完整任务性能结论。

恢复实验继续采用既有24 GiB私有卷保护：启动前可用磁盘超过50 GiB，保留20 GiB保护量及6 GiB余量；启动时重新检查实际负载和空间，不删除现存两个失败卷。源服务按原身份检查后使用，不替换原服务。
