# 小loop缓存页的实际记账归属已确认（2026-10-20）

**本次校准区分出了两种原因：格式化产生的27页已记在测量组，只是即时file计数尚未汇总；另外298个驻留页实际记在组外的`systemd-udevd.service`。** 在一次全局统计汇总完成后，两种情况可以分别核对，不再只凭mincore和file的总量猜测原因。

只运行一个128 MiB新镜像的初始化，无合成数据文件、沙箱、AgentENV服务或完整任务。沿用开启I/O记账、格式化、loop绑定、挂载同步和固定2.2秒基线，不预读负载、不锁页、不修改udev配置或全局缓存设置。本轮一次通过，当前轻量host监控默认行为保持。

## 驻留页与记账组逐一配对

Linux把连续的一组缓存页组织为folio。探针只针对本次镜像的设备号和inode，记录folio加入、移出事件及其文件偏移、大小、身份和实际内存组。最终325个4 KiB页对应237个不同大小的加入事件，没有移出事件；驻留页偏移与生命周期记录完整对应。

| 检查点 | 镜像驻留页 | 记在测量组的镜像页 | 记在udev组的镜像页 | 测量组file页 |
| --- | ---: | ---: | ---: | ---: |
| 预分配后 | 0 | 0 | 0 | 0 |
| 格式化后 | 27 | **27** | 0 | **0** |
| 挂载并同步后 | 325 | 27 | **298** | 0 |
| 固定2.2秒基线 | 325 | 27 | 298 | **40** |

loop刚绑定后的查询期间发生了目标镜像页加入，已标为`CHANGED_DURING_QUERY`，不为这个不稳定检查点配出确定的页归属。其余表中检查点在查询期间没有目标页加入或移出；没有用文件大小和修改时间稳定代替缓存集合稳定。

298页的实际记账组ID，与host上`/sys/fs/cgroup/system.slice/systemd-udevd.service`的inode一致。执行加载的线程名为`kworker/u513:10`，它所在的线程cgroup是根组；**线程在根组，页却记在udev组**。这直接验证了为什么不能用请求线程所属组代替页归属。这里确认的是设备管理服务的记账组，不依据线程名猜测具体调用了哪个识别命令。

## 统计延迟和真实组外记账都存在

格式化后的27页由`mkfs.ext4`加入，读取到的实际内存组为本轮工作进程所在组，但同一检查点file为0。这一早期差额是统计未汇总，不是这27页全部分配到了组外。

采集同时记录了21次统计汇总尝试，其中有一次根内存组的强制汇总，并捕获到其`css_rstat_flush()`返回。统计汇总是把各CPU暂存计数合并到对外读数；探针只记录这次内核事件，没有新增强制汇总请求。该完成事件发生在挂载同步检查之后、最终基线之前；最终读到的测量组file为40页。仅记录汇总尝试不够，因为实际内核会在`force=false`且`needs_flush=false`时直接返回，本轮将尝试和完成分开记录。

基线的数量关系是：

```text
镜像全局驻留       325页 = 27页组内 + 298页组外
测量组file读数      40页 = 27页镜像 + 13页其他已汇总file记账
镜像驻留减file     285页 = 298页组外 − 13页其他记账
```

组外298页为1.164 MiB，净差285页为1.113 MiB。**净差小于实际组外量**，说明组内其他缓存确实会掩盖部分组外记账。13页只是该次已汇总读数扣除已配对镜像页后的差值，本轮未进一步定位到其他具体文件。

因此，`IOAccounting=yes`解决了本轮工作负载请求的loop记账条件，但不会把udev等外部请求提前缓存的页自动迁入测量组。每0.1秒读一次file，也不保证内核每0.1秒完成一次统计汇总。

## 实现只用于一次定向校准

在原小loop入口增加显式选项：

```bash
bash scripts/run-host-loop-accounting.sh --initialization-only --charge-trace
```

无选项时仍为原关闭／开启I/O记账对照；单独`--initialization-only`仍为原初始化定位。新选项不能用于合成写入或普通沙箱入口，未接入常规host曲线采集。

新模块`host_loop_charge.py`从运行内核BTF读取元数据字段偏移。BTF是内核提供的结构布局信息，避免手写旧版本偏移。bpftrace 0.20.2直接读取`super_block.s_dev`的编译检查失败，改为读取实际BTF偏移后编译通过；这是探针编译检查，没有启动额外镜像。实际采集从folio的`memcg_data`读取指针，检查非内核对象标志，再取得对应cgroup ID。依据为当前`6.19.9+`源码：

- `include/linux/memcontrol.h:332–406`：标志掩码及文件页的memcg指针解释。
- `mm/memcontrol.c:2533–2545`、`mm/filemap.c:925–970`：先完成页记账，再发出加入缓存事件。
- `include/linux/cgroup.h:334–339`：cgroup ID来自kernfs节点ID。
- `drivers/block/loop.c:1870–1925`：从I/O请求取得内存组，并在后备文件I/O期间使用该组。
- `mm/memcontrol.c:597–649`：汇总尝试、阈值判断和实际统计汇总调用。

采集进程从创建时起位于另一个独有统计组，运行时实际检查其成员路径在测量树之外，避免把BPF编译器和采集器的大量内存／程序缓存当作镜像工作负载。探针只读取页和cgroup元数据，不访问镜像内容。新增mincore页偏移输出仅在定向校准中显式启用，默认返回字段与原查询方法保持。

## 当前方案能交付什么

- `memory.stat:file`继续作为**测量组文件缓存记账曲线**；它不包含已经确认存在的组外页，并可能延迟汇总。
- 文件清单mincore继续作为**所列文件的全局驻留量**，按文件身份去重；不与file直接相加。此次证明保留两种量有必要。
- 小镜像的原因已区分。此前大卷的1.766 MiB净不足没有逐页事件，仍按原记录保留，不能把本轮1.164 MiB当作其固定补偿，或声称旧大卷452页全部属于udev。

本段定向校准已完成，不继续为得到零差额追加镜像、修改全机设备管理或把探针常驻化。下一步建议先离线确定正式单／双沙箱对照的指标与范围：把file记账和清单全局驻留分开报告，以后者核对指定文件缓存的物理变化，同时保留匿名内存和PSS上下文。以比较对象、公共准备基线和完成条件明确为结束条件，再由用户检查实跑范围。
