## 用本次耗时推算 1 秒：可以到发请求位置，未实测拿到清单

以下是按阶段依赖推算，不是新的实跑。保持单次实测各阶段耗时不变、并行无争用、没有额外调度成本；“下限”指这一模型的乐观关键路径，不是系统保证。

1. **只提前挂两个探针，不动其余顺序：** 8343.938 − 7201.628 = **1142.309 ms**，仍比 1 秒多 142.309 ms。不能把这部分简单写成“让七个线程并发”。
2. **保留 16 MiB 核对，提前挂探针，令 capture.ready 与内容核对重叠：** 1142.309 − 264.434 = **877.875 ms** 到完整 start 就绪。这两个操作不互用结果；capture.ready 仍须在 RAM 槽绑定前成功。按此模型余量 122.125 ms。
3. **只要求首个导出请求，保持原身份校验：** 内容读写是校准负载，不是通信必需；在未来仅测导出时可不做，但缓存状态不再与这批负载等价。后备、下层和 provider 的初始化不供 `_snapshot` 使用，可移出首请求的关键路径，不能从未来的四来源查询中删除。令上传启动链、KVM 跟踪收尾和外部 VMM 绑定在返回后同时开始；从可复用的恢复分支 ID 开始，guest 安装至 marker/iomem 就绪的链长 **412.225 ms**，其后必须依赖这些数据核对槽位、打开宿主句柄、换算通信地址（15.577 ms）。所以观测模型给出的最快**可发请求**为 max(412.225, 264.434, 4.032) + 15.577 = **427.802 ms**。若仍要求内容核对在上传之前、但只准备首请求，则为 833.556 ms（外部 VMM 绑定同时进行）。没有删除 marker、进程身份、内核版本或地址验证。
4. **首份清单实际到手**还要加一次请求、guest 生成清单、host 读回的延时 L：最快模型为 427.802 ms + L；在模型中要 1 秒内拿到，L 必须 < 572.198 ms。本轮未请求，不能宣称完成了 1 秒发布或保住了缓存峰值。历史暂停对照的首次发布往返为 52.370 ms，来自另一次运行，不是本轮 L。

**启动前能否导出？** 不需要等整个业务就绪，也不需要所有四来源的宿主读取器准备好。但恢复的 guest vCPU 必须在运行，上传与 exec 的 guest 服务必须可用，正确的诊断内核接口、导出器及其通信页必须准备好。随后还需要一份可验证的宿主地址绑定才能正常发请求。仅启动 Python 进程还不够；在 guest 尚不能执行代码或收发工具命令时，原路径不能导出。能否早于其他无关启动活动完成，本轮没有单独的系统启动完成时间戳。

证据：本批 `.artifacts/storage-isolated-service/20261119T064132Z-825013/guest-cache/result.json` 和平台清理回执；旧七路 `.artifacts/storage-isolated-service/20261118T131857Z-610591/guest-cache/events.json`、各 bootstrap 回执、`results/seven-restored-immediate-20261118/read-windows.csv` 与同目录 REPORT.md。正常关闭导出器、两探针和本批存储；没有暂停、实际发布、页级查询或追加轮次。
