## 435.513 ms的实际范围，以及未解释的部分

源码`LiveTaskCache._run`在首次请求guest发布前开始计时，在各层归属计数完成后记录`host_thread_cpu_ns`及`host_elapsed_ns`；之后才编码段表JSON、转换数组字节、写raw和样本日志。此前将435.513 ms称为“完整配对CPU”不够准确，现明确为**单点采集至归属计数结束的线程CPU**。原字段、数值和计时位置均保持。

原记录与本次重放的量级对照：

| 项目 | 平均CPU/ms |
| --- | ---: |
| 原运行单点采集至归属计数结束 | 435.513 |
| 本次可重放步骤 | 111.729 |
| 原运行已单独记录的两次缓冲查询 | 4.672 |
| 原单点CPU减去以上两项 | 319.111 |

319.111 ms是两次测量的差额，不能当成原运行某一步的精确耗时。保存数据无法重放guest发布请求及导出区读取、三次VMM页号读取和筛选、两次实际映射读取、四次内核缓存查询及循环检查等步骤。这些成本保留未分解，不归给缓冲计数或写盘，也不据此预测在线总耗时。

原采集线程总CPU为4.429秒，10个单点计时合计4.355秒，区间外合计74.335 ms，平均7.434 ms/点。它包含编码、写出和循环等开销；本次内存编码平均6.050 ms，与它范围不同，不能将两者差值直接称为写盘CPU。

原两份查询日志还记录了两个BPF跟踪辅助进程合计0.910 CPU秒，覆盖整个恢复采样会话。这不在采集线程的435.513 ms内，也不能精确分摊到每个点。没有关闭采集对照，本轮不计算任务减速。

## 首选改动：批量换算，两侧仍各查一次

实际10点前后都各有16份VMA记录，初始缓存页为5835–23513页。当前`SnapshotCache.offsets`为每页调用`ram_address`查Linux虚拟化模块KVM登记的内存区，再逐项检查VMA，最后检查文件身份、权限并计算偏移。点1两次换算的单次函数调用分析显示：共有46348次`ram_address`调用，即23174页各查两次；剖析器自身有开销，其时间不与上表混用。

建议只将`SnapshotCache.offsets`中的逐页查找改为NumPy数组批量匹配。按每个KVM内存区、每份VMA生成页选择条件，然后成批写入换算结果。前后两次仍使用各自的映射，不缓存上次结果。需要保留以下条件：

- 每个输入guest页恰好命中一个KVM内存区、一个VMA；缺失或重叠仍报错。
- 只有文件后端才计算偏移；匿名区仍返回`UINT64_MAX`表示无文件来源，不由邻近映射推算。
- 对实际命中的文件映射仍检查设备号、inode及私有可写权限；不为未使用区域增加检查，也不为原无`identity`属性的旧调用新增前置条件。
- 输入顺序、重复页、空输入、旧调用缺少`path`时的原含义、返回数组类型及页内偏移计算保持。
- 后表偏移改变时，原后端/原始层后查失效处理和其他物理准入条件保持。

这项建议针对可重现的54.711 ms，不承诺消除319.111 ms差额。它比先改内核查询更适合下一步：输入完整，结果可逐页核对，而且不需要接触运行设备。批量实现尚未编写。

原四次查询按源码和日志合计每点平均85572.6次BPF表查找、7942.6次驻留状态查询（`mincore`）调用；40次已保存查询的返回数量与离线偏移数吻合，缺失内核结果均为0。这些操作可能贡献在线成本，但现有日志没有逐次查询CPU，不能据调用数量确定耗时归属。输入基本没有重复文件偏移，也不支持用简单去重来解决这部分问题。
