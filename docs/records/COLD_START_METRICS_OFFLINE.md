# 冷启动前置等待：已有指标的离线核对（2026-10-26）

**推荐先复用现有私有服务的`/metrics`，在七请求创建前后各保存一次，不改AgentENV服务或采样器。** 已有指标能分别统计整次镜像解析、镜像清单获取和服务端请求处理。两次快照可以判断七个请求的累计等待主要落在哪个阶段；不能还原单个慢请求，也不能单凭这些指标证明采样是等待的原因。

本轮只读六组保存结果、相关源码及已停止源容器的`/server`二进制，没有执行该程序、启动服务／guest、读取任务负载或更改运行设置。运行入口未修改。

## 已确认当前程序包含这些指标

本机AgentENV源码版本为`2f48c9c78ec58e4d73c49aa07cb81d984a4a4184`，本次涉及的九个源码文件相对该版本没有修改。六组创建使用固定服务镜像`sha256:db9eb044ae3d85f9b276b9d2e5dea28cb0be95263d217ea4989f095e1d828681`；从已停止的固定源容器只读检查`/server`，找到下表指标及对应阶段文本。读取前后源容器状态和启动／结束时间保持相同。

源码的服务启动函数直接初始化指标记录器，API路由注册`GET /metrics`。普通本机访问该路径不需要API密钥，且这次查询自身不写入HTTP耗时指标。隔离配置关闭的是ublk守护进程的独立指标监听，**不是API服务的`/metrics`**。

依据：`AgentENV/src/bin/server.rs:56–59`、`src/api/server.rs:36–49`、`src/api/impls/auth.rs:52–55`、`src/observability/prometheus.rs:9–11`。导出函数及直方图配置位于`crates/observability/src/lib.rs:33–77`。这次离线核对没有访问已清理服务留下的旧端口；后续实际导出已由[一对最小验证](COLD_START_METRICS_VALIDATION.md)确认。

| 已有指标 | 必须选择的范围 | 覆盖的操作／计时含义 |
| --- | --- | --- |
| `agentenv_sandbox_stage_duration_seconds` | `operation="create_cold"`，分别取`resolve_rootfs`、`resolve_attached_drives`、`create_sandbox`阶段 | 根文件系统解析、附加驱动解析、调用创建服务的耗时；均包含各自异步等待 |
| `agentenv_image_resolve_stage_duration_seconds` | `stage="manifest_fetch"`，另列`config_fetch`、`layer_convert` | 镜像清单获取，以及部分配置获取、层转换；是镜像解析内部阶段，不与整次解析相加 |

耗时指标是Prometheus直方图：`_count`是已记录次数，`_sum`是累计秒数，`_bucket`是累计落入各耗时范围的次数。阶段标签只有`operation/stage/status`，镜像内部阶段只有`stage/status`，没有角色、请求ID或沙箱ID。因此即使新一轮取得汇总值，也不能按角色还原每个请求的解析耗时；旧第二对42.570秒是日志前等待，不是已测得的解析时间。

依据：`src/observability/prometheus.rs:67–111,180–218`。阶段耗时在异步操作结束后写入；成功／错误分开。取消可能没有完成的外层阶段耗时，不能只看末次并发数为0就算收集完整，还需核对次数。

## 本地镜像命中仍然先获取清单

实际顺序是：

1. 冷启动API计时`resolve_rootfs`并调用解析器：`src/api/impls/sandbox.rs:674–680`。
2. 解析器先调用`fetch_oci_manifest`，计入`manifest_fetch`：`src/image/resolver.rs:191–212`。
3. 清单获取完成后才打开本地镜像存储并检查`cached_config`：同文件`320–366`。
4. 然后才解析附加驱动、校验配置、构造创建请求，并计时调用`create_sandbox`：`src/api/impls/sandbox.rs:698–800`。
5. 创建服务派发独立异步任务，再打印`creating sandbox`：`src/orchestrator/service.rs:277–303,410–422,442–468`。

`fetch_oci_manifest`会通过外部`regctl manifest get`获取清单，遇到镜像索引还会继续获取对应平台的清单；这一步不下载层数据。即使使用带摘要的镜像引用，也不能据此跳过现有源码里的清单获取。依据：`src/image/oci_image.rs:185–193,861–919`。

所以“已复用本地转换层”不足以排除镜像解析中的外部等待。`manifest_fetch`还包含启动regctl、获取／解析清单、可能的重试和调度等待，不能直接叫作纯网络耗时。

还有两个覆盖缺口：

- 命中本地配置但缺少运行元数据时，仍会读取配置元数据；该分支没有包在`config_fetch`计时中，见`resolver.rs:343–366`。转换锁、存储打开及配置读取也不全由内部三个阶段覆盖；`resolve_rootfs`仍覆盖其整体等待。
- `create_sandbox`计时从调用创建服务开始，包含异步任务被调度到创建日志之前的等待；这部分虽然在旧日志中属于“创建日志之前”，却不属于镜像解析。

因此，不能预设“创建日志前全部是镜像解析”，也不能将`resolve_rootfs`与其内部`manifest_fetch`相加。

## 旧六组没有保存指标响应，不能补算阶段耗时

已检查六组结果目录和实际采集入口：没有`/metrics`响应文件或读取操作。三个关闭组目录中的`code/task_metrics_prefix.py`只是保留的辅助源码，不是指标数据。旧私有服务已删除，旧计数器随进程消失，不能通过重启补回。

六组服务日志也没有`regctl failed; retrying`或镜像候选失败的记录。源码在regctl非零退出且准备重试时才打印该警告；外部命令自身成功但等待较久时不会打印。因此，现有日志既不能证明发生了这层重试，也不能排除成功请求中的较长等待。依据：`src/image/oci_image.rs:956–987`。

指标必须与七个请求的**累计时间**比较，而不是只和整批墙钟跨度比较。已有记录给出的目标量如下，单位秒：

| --- | ---: | ---: | ---: |
| 第一对 | 21.973142→14.779470 | −7.193672 | −1.025717 |
| 第二对 | 39.061844→94.645145 | +55.583301 | +32.904275 |
| 第三对 | 15.062791→27.050490 | +11.987699 | +4.486109 |

七个请求相互重叠，累计时间大于批次墙钟是正常的。该表只是从现有日志重算的比较目标，**不是测得的镜像解析时间**。原批次结果、全部42请求分段及完整GRPO整轮+2.60%均保持。

## 最小改动及完成条件

后续实现已采用下列范围：改动只放在显式启动对照入口，不改普通任务、服务二进制、配置、镜像或采样频率。

### 只增加两次本机GET

在`scripts/cold_start_sampling.py`中：

- 创建前：初始列表为空、采样控制对象已初始化后，在写入`creation_begin_monotonic_ns`和派发七请求之前保存一次指标。
- 创建后：`create_batch`及所有采样初始化结束，先记录原`all_creation_and_sampler_setup_returned_ns`，再保存一次指标，之后进行共同身份检查和清理。

两个位置都在七请求冷启动计时区间之外，不给每个创建请求加同步查询，也不增加周期轮询。原冷启动跨度仍按原七个事件计算；控制程序整轮仍包含实际执行的查询时间，另列两次GET的耗时和响应大小，不扣除或改写原计时定义。实际查询成本须实测，不先承诺上界。

请求只用本轮仍然存活的自有服务地址，绕过代理，设置有限超时，不访问旧记录中的已释放端口。保存响应到本轮自有目录，公开时只输出所需脱敏计数。`/metrics`不需要复制或读取API密钥。

### 用次数和累计值判定，不改成单请求归因

最小离线检查和首次真实验证应确认：

1. 两组各两次GET均在原创建计时外；开启组仍逐guest立即部署，关闭组没有采样；原七请求、身份和清理条件保持。
2. 在同一服务进程中计算前后差。HTTP冷启动成功次数、三个外层阶段成功次数均为7，并单列错误；末次三个inflight均为0。读取失败、末次阶段缺失或次数不齐，诊断标为缺失，不填0。
3. 基线响应有效、但首次请求前尚未注册的序列可按“尚无该事件”处理；这与响应缺失不同。错误／取消、不同标签和进程重启不能被忽略。指标解析需用模拟文本验证标签顺序、首次无序列和次数不齐，不启动沙箱做这些检查。
4. 计算根文件系统解析累计`R`、附加驱动累计`A`、创建服务累计`C`、服务HTTP累计`H`；`H−R−A−C`只表示这些外层计时未覆盖的服务处理，不是网络时间。指标选择、次数或范围不一致时先保留差额原因，不强行令其为0。
5. 内部镜像指标是全服务汇总，只有确认期间没有其他镜像解析、且次数与本批请求相符时，才将`manifest_fetch`累计`F`与`R`对照。`R−F`仍包含其他解析工作，不自动归为锁等待；配置和转换指标分别列出。
6. 如果增量主要出现在`R`且`F`也相应增加，结论限于“主要在清单获取阶段”；如果主要在`C`而创建日志后没有对应增加，继续考虑该调用内的日志前等待。现有聚合指标仍不支持指定哪一个请求慢，也不能仅靠阶段相符就确认采样因果。
