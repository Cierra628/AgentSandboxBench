## 为什么先建立统计组

统计组覆盖本次镜像准备、控制程序、新建实验服务及其所有沙箱。新Docker服务通过`--cgroup-parent`加入该组，服务的子进程从创建时起就在组内。没有把旧Firecracker移入新组。

当前入口同时显式开启内存和I/O记账。loop后备文件的缓存页会受I/O组归属影响，仅让写入进程在内存组内还不够。创建guest前保存测量组和私有服务的实际控制器状态；测量组未向下启用io或服务没有`io.stat`时明确失败。没有设置I/O限速。

新实验配置关闭Firecracker池、启动预热和块设备池。首次创建guest之前，实际检查服务cgroup位于统计组下、沙箱列表为空、组内Firecracker数为0，并记录时间及创建前的内存计数。不会根据“常驻12个”的历史记录推断当前进程数量。

准备阶段也在组内，是为了避免新准备的RAM输入文件先记账到组外。曲线同时标注服务就绪、尚未创建guest的位置，并保留该时刻基线。输入准备、控制程序和共享服务的成本属于本图范围，不能解释为单个guest新增缓存。

## 三种数据如何读取

最终文件清单已补入输入和私有两份deps，以及私有日志、沙箱记录和模板状态目录，原路径保持。新11根清单已实际采到190文件；下方历史100／102／138文件结果仍按当次范围解释，新增驻留不追溯补入旧结果。

- **每0.1秒：**读取统计组的`memory.stat`和`memory.current`，保存原始字节值、单调时间及读取耗时。`file`包含`shmem`；两者不相加。另保留`file−shmem`，用于观察不含这部分共享内存的文件缓存。
- **每1秒：**读取组内各进程的`smaps_rollup`，保留总PSS及匿名、文件、共享内存分类。进程退出造成的不完整扫描明确标记为`PARTIAL`，图上留空，不补零。
- **任务结束、本次写入进程退出后、清理私有挂载前：**对保留的只读输入commits、私有image-cache、两份deps、私有logs／persisted-sandboxes／template-builds，以及显式列出的输入RAM镜像和私有卷镜像执行`mincore`。只用文件元数据、`mmap(PROT_NONE)`和驻留查询，不读取文件内容，不触发预读或锁页；按设备号和inode去重，避免只读绑定和硬链接重复计数。

普通任务与冷启动短入口的mincore清单覆盖上述仍存在的普通文件和两类loop后备镜像；已删除文件、ublk块设备自身的缓存和其他未列入的来源不在该清单内。查询期间普通文件大小和修改时间改变、文件消失等情况按不完整报告；根目录缺失仍明确失败，不按零驻留报告。

真实恢复短入口另加guest仍存活时的块设备及原始内存层mincore，清单按实际身份关联，块设备容量由ioctl核对，不使用st_size；块设备节点的修改时间变化单列，不作为设备身份变化。最终普通文件清单还覆盖保留快照仓库及运行文件。两个检查窗口分开报告，不能相加。

## mincore和PSS怎样用于核对

`mincore`报告清单内文件的全局驻留量，cgroup的`file`报告组内所有文件缓存记账量。若前者超过检查前后两次`file`的较大值，报告差额并标记`SHORTFALL_REQUIRES_RESOLUTION`，阻止节省比例外推。可能涉及组外记账、清单范围或采样期间变化，需要进一步定位。

没有出现差额，仅表示本次没有检测到不足，不能单凭数值接近判为完整。组内其他文件页可能掩盖清单内部分组外记账。两者可能重叠，因此不把全部mincore量直接加到`file`上。报告单列两次计数与mincore量中的最大值，作为检查窗口内的文件驻留下界参考，不声称是同一时刻的精确总量。

PSS是独立的映射内存观察，可与`memory.current`辅助对照。Pss_File不全是文件缓存，还可能包括映射内核页；这部分与kernel记账重叠，不能相加。未映射缓存、PSS跳过的PFN映射、其他内核内存、组外共享进程及进程退出都能造成差异。因此不以两者不相等直接判漏账，也不以数量级接近证明完整记账。来源及条件见[特殊映射分类](HOST_SPECIAL_MAPPINGS.md)。

定向校准已证明组外设备识别请求可以把后备缓存记到udev组；同时存在页已记在组内而file尚未汇总的情况。开启I/O记账不会把外部请求先缓存的页迁回本组。对整个沙箱给出物理缓存量时，不能把file曲线单独当作完整物理并集，也不能将小镜像的组外量作为大卷固定修正值。此次探针只用于一次原因校准，不在普通host采样中常驻。

## 图中的host和guest不是同一层

普通块设备访问下，guest文件缓存保存在guest RAM里。如果RAM对应host匿名映射，这部分记作host的`anon`，不会因为guest称它为page cache就计入host的`file`。恢复后RAM若使用文件后备，host的`file`也可能保存guest程序或内核内存，不仅是guest缓存。

因此host图明确写明`host file ≠ guest Cached`，与原guest三指标图分别展示。不能直接相减计算物理节省。新host图主指标是current总记账量，file用于解释文件缓存变化；历史图片保持当次file主图。

## 单沙箱到N沙箱的参考

实现保留用户提出的换算：单沙箱量为A，N沙箱量为B，线性参考量为`N×A`，相对线性参考减少比例为`(N×A−B)/(N×A)`。负值照实保留。

这是单沙箱外推，不是实测不共享后端。A/B需要相同任务、阶段、起始缓存和回收策略；完整流程中的公共输入准备和固定服务开销会影响比例。报告保留创建前基线，不将这些固定成本的重复外推全部归因于页共享。

有经过核对的A/B后，可离线计算；当前入口使用两份报告的完整流程`file`观测峰值，输出中明确注明这一范围：

```bash
python3 -B scripts/report_host_file.py \
  .artifacts/<A报告>/host-file/summary.json \
  .artifacts/<B报告>/host-file/summary.json \
  --sandboxes 2 --output .artifacts/<新的参考结果>.json
```

这个旧命令不用于上述相同后缀设计：完整流程峰值会将公共准备重复外推，且file存在已确认的组外遗漏。新设计只允许对范围明确的设备驻留列出受限的线性参考，不能将其写成完整host物理内存节省率；细则见设计页，旧入口和结果不变。
