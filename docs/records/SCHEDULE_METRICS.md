# 三调度测量的统一口径

2026-11-05。适用范围是Prettier #6604、七角色、GRPO／BPO／本项目TVCache的后续横向比较。依据[三次可用性验证](../../results/schedule-smoke-live-20261105/REPORT.md)及[本次离线核对](../../results/schedule-metrics-offline-20261105/REPORT.md)制定；没有修改运行代码、配置、普通入口默认或已有实验数值。其他密度实验的memory.current主指标保持原定义，不把不同入口的统计范围混用。

## 主表固定四类指标

| 主表指标 | 字段与单位 | 统一定义 |
| --- | --- | --- |
| 每沙箱PSS | `vmm_pss_endpoint_per_guest_mib`，MiB/guest | 全部原动作及下载完成后、官方检查及删除前，七个实际VMM的共同短窗口PSS总和除7 |
| host指定文件缓存 | `initial_lower_mincore_p1_mib`，MiB | 本任务固定19个初始不可变下层文件的全局驻留，按本次运行的设备号:inode去重，只查一次P1 |
| 任务耗时：调度执行窗口 | `schedule_run_seconds`，秒 | 从调用调度器前、尚未创建guest开始，到全部路径与结果下载返回结束；包含创建、准备、保存恢复及分支等待 |
| 工具累计 | `actual_tool_sum_seconds`，秒 | 所有实际执行动作的`steps.tsv.duration_ns`相加，不把复用前缀再乘进累计值 |

主表同时列出实际／逻辑动作数、官方结果及保存恢复次数。七角色的guest Cached曲线、服务组的file／current、原控制程序整轮和动作及下载窗口作为分开标注的辅助数据。PSS、mincore、file、Cached不相加或相减构造“总物理内存”。

MiB按字节除以2²⁰；smaps_rollup及meminfo中的kB按KiB处理。时间按纳秒除以10⁹。

## PSS/N固定在同一完成阶段，不称为峰值

时序统一为：调度器返回 → 核对七实例及文件身份 → 七VMM PSS → 19文件P1及前后组计数 → 原官方检查 → 删除。

PSS，即按共享比例分摊的驻留内存，来自七个root Firecracker的`/proc/PID/smaps_rollup`。按sandbox ID绑定本次私有服务cgroup内的VMM，核对启动标识、API身份和不同PID；共同顺序读取窗口记录起止、每进程值及CPU成本。七个值齐全才求总和／7；任何一个缺失则该项不完整，不补零或改除数。

该数覆盖VMM映射，包含guest RAM以及VMM自身映射的内存；不覆盖独立服务、块设备提供进程、未映射文件缓存和全部内核开销。它不是整个沙箱的部署成本。内核按所有相关映射分摊共享页，不只在本次七个VMM之间分摊。

三种调度均在“所有路径完成、七guest尚在”阶段读数，但各guest已等待的时间可以不同。这是原调度的实际终点状态，不人为等待相同秒数、暂停guest或强制驻留。PSS在本次完成点之后约0.080～0.135秒开始读取，七进程窗口约0.107～0.138秒；不把顺序读数称为原子快照，也不把七个各自峰值相加。

周期PSS保持1秒，普通计数保持0.1秒。各进程周期采样不完全同步，空白PSS单元格表示当次没有查询，不能补零。现有终点汇总作为主表值，周期数据用于观察过程，不另造“精确的七VMM同步峰值”。

## page cache必须写出是哪一层、哪些对象

### guest Cached：每个guest的逻辑缓存

读取guest的`/proc/meminfo`中`Cached`原值，保留Shmem作解释，不额外加Shmem或SReclaimable。它包含共享内存相关重叠，并不是仅某个任务进程的文件缓存。七guest各自记录，不能把其和当作host去重后的物理缓存。

三组本次均使用完整监控模式，不是guest-only轻量模式。普通计数0.1秒、PSS周期1秒，现有边界采样及CPU/I/O采集保持原样；本轮不调整它们。保存恢复前按原实现停止采集器，之后重启：GRPO为7个采集会话，BPO／TVCache各9个会话，始终各7个不同VMM。

guest曲线按会话及其单调时钟绘制，恢复空缺断线。guest与host时钟不能直接相减；现有host会话启动记录只提供粗略安排位置，不用于证明毫秒级内存变化导致某次动作变慢。官方检查阶段与任务阶段分别标注，不把检查期峰值冠为任务期峰值。

### host mincore P1：固定19个初始下层文件

由实际VMM的GET /vm/config、活跃rootfs配置及打开文件确认文件身份，不能只按目录猜清单。同一任务三调度的19个初始对象内容标识及大小必须一致；设备号:inode只在各次运行内去重，不跨已销毁又重建的文件系统合并。

使用文件元数据、`mmap(PROT_NONE)`和mincore查询当前驻留，不读取文件数据、预读、锁页或额外回收。以实际页数计容量，尾页按一页计算；保留稳定性、去重数、身份、查询窗口和墙钟／CPU成本。PSS与P1先后读取，不假装同一瞬间。

本次P1均5308.066 MiB且全驻留，入口在创建服务前复制过完整输入；P0没有采集。因此只称“终点指定文件驻留”，不称“任务新读入量”，也不据此计算共享节省。保持默认回收，后续若决定测冷起点或共享／独立副本，须作为另一项明确的实验设计，不悄悄加入本矩阵。

| 对象分类 | 本次状态 | 统一报告方式 |
| --- | --- | --- |
| 初始不可变下层文件 | 三调度均19个，P1已测 | 主表固定范围 |
| 保存时新增、成为活跃下层的快照文件 | GRPO未识别到额外活跃下层；BPO／TVCache各2个 | 单列身份及文件长度，驻留未测；不并入19文件P1 |
| 可写upper、VM内存快照后备、其他运行文件、loop后备缓存及设备缓存 | 19文件查询未覆盖 | 容量未知，不记零，不宣称整沙箱覆盖 |

BPO／TVCache这两个新增活跃下层的文件长度各合计9.8515625 MiB，只是文件长度，不是已用物理内存。其他任务应按各自冻结镜像确定初始层清单，不能沿用Prettier的19个数量。

### cgroup file：服务组记账，覆盖缺口单列

本轮读取的是新建私有Docker服务及其子进程所在cgroup，不包括在父组执行的输入准备和控制程序。此前host-file外层入口创建的统计slice还覆盖准备和控制程序，范围不同；两类同名file／current不直接拼成一条曲线。

`memory.stat.file`包含shmem；current是同组总内存记账，二者均是组内归属统计，不是指定文件的全局驻留。P1前后两次file与mincore并列。若mincore大于两次file中的较大值，记录`SHORTFALL_REQUIRES_RESOLUTION`；没有差额也只表示未检出不足，其他文件记账可能掩盖组外页。

本次三组差额为5224.355／1868.398／1740.949 MiB。它们是两个不同范围统计量之间的净不足，不是已查明的组外容量、可加回current的修正量或总误差上界。输入复制在服务创建前发生，支持准备缓存可能记在组外的解释；具体所属cgroup及容量没有逐页证据，统一留空。

所以三调度的file均标注“组内文件记账，指定文件覆盖不足”；current仍可作为同组上下文，但不能据此给整组物理节省或部署数量结论。本次不增加全盘扫描或页归属查询。

## 时间分成四层，历史字段保留

1. **调度执行窗口，主任务耗时：**`(original_paths_end_monotonic_ns − rollout_start_monotonic_ns) / 1e9`。两者均来自host单调时钟，包含最初创建及之后的保存恢复、工具、控制调用和结果下载；不含此前冻结输入准备、之后的终点观测、官方检查和清理。是调用边界经过时间，包含其间日志等开销，不是纯RPC或CPU时间。
2. **动作及下载窗口，辅助：**`(original_paths_end_monotonic_ns − first_tool_start_monotonic_ns) / 1e9`。first_tool字段实际是第一次段调用之前，不是guest第一条命令的精确起点；包含该点以后的保存恢复和分支准备，但不含最初创建。
3. **控制程序整轮，保留：**原`controller_elapsed_ns / 1e9`，覆盖原控制程序预检、创建准备、调度、终点查询、官方检查与清理。原34.497／54.484／85.430秒不替换成新的主任务耗时。
4. **外层调用至验收，保留：**原`private_service_round_seconds`，从调用私有服务运行入口前计到批次解析日志并完成`summarize()`验收后；还包含分卷、输入复制、服务启停及卷清理，不含批次共用RAM输入准备。此前简称“外层私有服务整轮”，不能当作纯服务运行时长；没有单独保存子进程返回时刻，不能再精确拆出验收耗时。

工具耗时直接复用guest执行器两次单调计时之差，包含shell／timeout包装、命令执行和输出重定向，边界meminfo／vmstat采样位于计时之外。工具运行期间的周期采样竞争仍会影响经过时间。工具累计存在并发重叠，不用累计除整轮来声称串行时间占比；模型推理、host调用和结果下载不在该工具计时内。

保存事件耗时只覆盖原snapshot-create调用，不包括之前的状态检查、停止采集器及之后重启采集器；恢复事件覆盖创建恢复实例的调用与返回，不包括随后准备和恢复状态验证。它们是调用方计时，不是服务端纯处理时间。并发恢复耗时之和不能充当恢复窗口。

## 动作与结果保持原调度

GRPO为189实际／189逻辑动作，无保存恢复；BPO和TVCache为84实际／189逻辑动作，各保存2次、恢复6次。逻辑动作表示七条完整路径的工作量，实际动作表示去掉复用前缀后真正执行的次数。不能为凑189次实际动作而改变恢复调度，也不将84步工具累计折算成189步。

BPO分支后缀并发；本项目TVCache为确定性前缀树顺序推进，没有动态容量预算或淘汰。本次三组均保持每实例官方0通过2失败、退出码及关键输出检查；只证明实现与采集可用，单次值不作稳定性能排名。
