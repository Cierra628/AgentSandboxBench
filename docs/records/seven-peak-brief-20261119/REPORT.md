# 七个恢复分支：怎样在缓存高位时确认宿主物理页

基线：handoff-20261118 · dd9ba4c9ebae59db68055da5e8ad566b87d6eb16
离线检查：退出码 0 · status=PASS scope=platform-offline

## 一、不暂停，查询追不上缓存变化

约 5 秒内，每支 guest（虚拟机）的缓存清单从约三万条降到几千条；前后还能核对身份的页已大幅减少。

| 不暂停的七支：每支确认 | 单支高位参照：恢复后 4.704 秒开始读取 |
|---|---|
| **2,299–6,003 页** | **37,352 页** |

## 二、为什么不能靠少查来提速

| 思路 | 为什么不行 |
|---|---|
| 按段抽样 | 抽 10% 的段时精度不达标；离线重放中，要让各组合的误差 95 分位都不超过 5%，等概率抽段（SRS）需抽 99%，按段长加权（PPS）需抽 75%。 |
| 按页抽样 | 随机保留 10% 的页会拆散连续段，驻留查询调用数从实测 38,434 次升至推算约 58,456 次。 |
| 只查一遍 | 必须用两份独立读数核对宿主物理页号；把首读填进末列，校验就会恒真。 |

## 三、磁盘清单不能代替内存后备清单

| 尝试 | 结果 |
|---|---|
| 查 rootfs 镜像的 19 个文件 | 与实际 RAM 后备匹配 0/19，只测到磁盘文件驻留。 |
| 查 GET /vm/config 的六个 drive | 该次 RAM 后备是 /dev/ublkb2，不在磁盘清单中，匹配 0/6。 |
| 让采集器自己选 | 宿主能找到设备，但没有本支当前的 guest 缓存清单，就选不出该查的偏移。 |

由采集器绑定对象，由本支清单选页，不从外部猜文件。

## 四、把必须早做的导出和可以稍后做的查询分开

| 步骤 | 七支串行批的实测时间 |
|---|---|
| 探针前置 | 宿主页查询探针在最早恢复命令发出前 35.627 ms 已就绪；这是提前量，挂载本身未单独计时。 |
| 并行恢复、并行导出 | 保留 16 MiB 内容核对；各支从恢复返回到可发请求为 712.838–1,808.051 ms，再用 7.745–25.984 ms 读回首份清单。 |
| 清单到齐，原地暂停 | 通过 Firecracker PATCH /vm 保留原进程和映射；从最后一份清单到齐至全部暂停为 15.014 ms。 |
| 逐支做两遍查询 | 整轮宿主读取 2.147 秒；全部查完才恢复运行，再导出清单核对页身份。 |

## 五、每支确认页数回到高位参照的量级

| 指标 | 旧法：不暂停 | 本法：暂停后串行 |
|---|---|---|
| 每支确认的宿主物理页 | 2,299–6,003 | **36,356–37,509** |
| 查询用时（实测） | 约 9.9 秒（七支共同读窗） | **2.147 秒**（首支开始至末支结束） |
| 整轮折合每页次 | — | 3.458 µs |

同口径速度对照：暂停后并行查询实测 9.053 秒、14.633 µs/页次；串行墙钟为并行的 23.7%，差额不能全归因于 CPU 争用。

稳定性：单支一个下层文件的驻留位图在 30 秒内逐位一致；七支串行读窗无重叠，各支读前、读后均确认为 Paused。

## 六、限制与未达成

| 项目 | 状态 |
|---|---|
| 1 秒目标 | **未达成。** 两遍实测 2.147 秒；单遍的 1.073 秒只是整轮减半的推算，还会失去物理页号核对。 |
| 同刻绝对峰值 | 未证明。各支暂停时刻不同，串行与并行两批在查询前的清单也已不同。 |
| 适用范围 | 七支都能暂停且允许分时读取；不适用于 guest 持续运行时的连续测量。 |
| 首支较慢 | 首支实测 408.762 ms，其余为 268.972–305.182 ms，原因未查。 |

## 七、一句话结论

**用暂停换查询时间：每支从只确认几千页提高到约三万七千页；代价是必须暂停 guest、保留两遍校验，整轮仍需 2.147 秒。**
