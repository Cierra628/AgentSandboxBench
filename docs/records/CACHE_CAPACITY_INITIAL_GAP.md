# 起始缓存大差异形成于控制启动过渡阶段（2026-10-18）

已只用[同一快照对照](CACHE_CAPACITY_SAME_SNAPSHOT.md)的原日志和缓存成员记录，定位B分支82.520 MiB起始差异的主要形成区间：两组首次物理采样的前半段分别约132、128 MiB，随后64 MiB组在约0.263秒内降到45 MiB，128 MiB组只下降约0.641 MiB。这个变化发生在原后缀执行及任何非零容量回收请求之前。

**建议把停止DAMON后台回收的时机提前到共同父guest保存快照之前。** 当前在恢复检查和采集就绪后才停止，已经留下数秒背景回收窗口。记录足以确认这项对照条件没有固定住；缺少逐页回收线程记录，尚不能把所有消失页都指定为DAMON回收。

## 恢复后先接近，大差异在首次采样区间形成

下面是B分支的逻辑缓存容量，MiB为1024²字节。`Cached`来自guest常规内存计数，成员表来自独立记录普通文件和共享内存缓存页的诊断接口；两者采样时刻不同，分别标明。

| 观测位置 | 64 MiB组 | 128 MiB组 | 128减64/MiB |
| --- | ---: | ---: | ---: |
| 恢复后首个常规`Cached`读数 | 195.215 | 191.465 | −3.750 |
| 首次物理采样，前份成员表 | 132.016 | 128.281 | −3.734 |
| 同次采样，后份成员表 | 45.129 | 127.641 | +82.512 |
| 容量控制器首个回收前读数 | 45.125 | 127.645 | +82.520 |

恢复后首个常规读数在两组guest单调时钟约7.651、7.633秒。首次成员表区间分别为12.677621–12.940821秒和12.678073–12.927446秒。两组起初已有约4 MiB的小差异，82.520 MiB的大差异主要在这个约四分之一秒的区间形成，不是后缀运行数秒之后才出现。

64组常规`Cached`的最大相邻下降也在同一区间：12.795566秒为132.016 MiB，12.898511秒为45.082 MiB，约103 ms内下降86.934 MiB。它早于停止DAMON完成后的控制计数起点12.926743秒。128组在控制计数起点12.961608秒之前，最后一个常规读数仍为127.641 MiB。

原始成员表独立解码后，64组从33796页变成11553页：11461页身份保持，22335页旧身份消失或被复用，加入92页新身份，净减少22243页，即86.887 MiB。128组从32840页变成32676页，净减少164页，即0.641 MiB。两组的共享内存计数前后均为284页；重复加入、缺失删除、越界及失效记录为零。这是缓存成员的真实变化，不只是常规内存计数的波动；页号相同但缓存生命周期标记变化的页不会当作稳定页。

按原始字节精确分解，B分支最终差异为：

```text
首次成员表的两组差异          −3.734375 MiB
采样区间内两组净变化的差异   +86.24609375 MiB
后份成员表至首次控制的差异    +0.0078125 MiB
最终起始差异                 82.51953125 MiB
```

A分支作为对照也在控制之前下降：常规首个`Cached`为195.215/191.469 MiB，首次成员表已分别约42.207/38.832 MiB，首次控制为45.219/41.051 MiB。大幅下降并非只在低目标下发生；A两组都在开始容量控制前已变小。

## 容量回收和原后缀不是这次大下降的起点

四个guest的容量控制器首个请求均为零。B分支64/128组首次非零请求分别在guest时钟13.382612、13.316445秒，均晚于首次物理采样区间结束。不能把64组这一段下降解释为“64 MiB控制器已经开始压低缓存”。

host日志同时显示，首次成员表读取的前半段在启动容量控制命令前约25/39 ms开始，后半段在该命令开始后约251/223 ms结束；后半段结束又分别早于原后缀命令约50/212 ms。故大差异已出现在采集就绪、控制进程启动和后台回收停止相邻的这一段。记录没有单独保存写入停止参数的guest时间，不能进一步确定每张页是在写入前还是等待线程退出时消失。

这些比较分别使用guest或host各自的单调时钟；不把guest日期时间直接减去host日志日期时间。原物理采样中的guest发布请求与host读取顺序用现有逐阶段记录核对。

## 源码说明为什么当前停止时机偏晚

实际冻结的任务控制器依次执行：恢复guest、启动常规监控、检查59份边界文件及原进程、等待两个物理采样器就绪，最后才启动容量控制器。两组B从恢复命令开始到启动容量控制命令分别约5.515、5.528秒，期间没有关闭原后台回收。

实际冻结的`guest_cache_capacity.py`先读取能力和DAMON参数，再调用`set_damon('N')`，同时等到`enabled=N`且`kdamond_pid=-1`，之后才记录`io_start_ns`并开始周期回收。四个guest在停止前均记录`enabled=Y`和工作线程71。因此当前接口确实等线程退出后才控制，问题在于等待开始得太晚，不是遗漏了退出确认。

实际Linux 6.1.175源码给出两项依据：

- `mm/damon/reclaim.c`中，写入`enabled`只把启停工作加入队列；停用工作随后调用`damon_stop()`，成功后才把工作线程号设为−1。它不是写入参数时就同步完成停止。
- 同文件的`damon_reclaim_after_aggregation()`复制累计统计；`mm/damon/core.c`先调用该回调，再执行本轮`kdamond_apply_schemes()`。停止前一次读取的导出统计可能没有覆盖随后或正在执行的回收。

B两组停止前读到的`bytes_reclaimed_regions`分别为72,261,632和72,282,112字节，相差仅20 KiB。这些是停止前逐文件读取的累计参数，不是首次成员表区间的回收增量，不能用它们把两组的后台回收视为相同，也不能当作当前缓存容量。

DAMON在该区间仍有运行机会，是需要优先固定的因素。现有数据没有逐页回收线程或每次停止操作的完整事件记录，具体哪些页由它回收仍未确认；私有服务恢复对host状态的影响也保留。上一段的耗时差、物理并集和未知量不因本次定位而改变。

## 选择在共同父guest中先停止，再保存

相比恢复每个guest后再停止，**在共同11步完成后、保存快照前停止一次并等线程退出**更合适：停止过程即使继续改变缓存，也只发生在同一个父guest中；保存后的两个组都继承关闭状态，恢复检查和采集准备期间不会再运行该后台回收。共同前缀仍沿用原运行方式，不必从冷启动起改变它。

后续最小改动应包括三件事，目前尚未修改在线代码：

1. 仅在新对照选项中保存父guest原DAMON状态，停止并确认线程退出，记录停止后容量，再调用原快照接口；不新增采集暂停或预读。
2. 两组恢复后检查均为关闭状态，再按相同流程执行64/128 MiB控制；实际起始容量仍要测，不能假定完全相等。
3. 两组停止容量控制后，依据父guest保存的原状态恢复后台回收，再进行官方检查。现有`serve()`默认会恢复它启动时读到的状态；新快照若继承`N`，只复用这个默认值会错误地继续保持`N`，必须在新选项中明确处理。旧入口的默认行为保持。

这项建议固定的是后台回收条件，不将周期目标改为硬上限，也不以获得更小的耗时百分比为完成标准。
