## 新诊断只加两次读取，普通轻量入口不变

继续使用普通guest-only GRPO的镜像环境：每组一份新私有服务、16 GiB隔离卷，七个新guest并发创建，每个2 CPU／4096 MiB；不复用预启动池。这里只创建guest，不清文件缓存，不执行仓库检查、负载上传、原任务、快照或官方评估；默认回收保持，不做host内存周期采样、PSS或mincore。

只有显式`--server-metrics`才启用本次诊断，外层运行范围也改为一对关闭→开启。无此参数时仍是原三对顺序，不读指标；普通任务入口不变。

- 创建前：原初始列表检查及采样控制对象初始化后读取一次，结束后才记录原创建开始时间、派发七请求。
- 创建后：七创建和采样初始化全部完成，先记录原结束时间，再读取一次，然后进行共同身份检查和并发清理。
- 两次都绕过代理，只访问本轮自有服务的本机地址；不需要读取API密钥，每次GET超时3秒、不重试。额外核对服务进程身份，防止跨进程相减。
- 原创建跨度仍由七个客户端事件计算；控制程序整轮包含实际新增工作，不扣除查询时间。原始响应只留在本地，公开证据只保留所需指标及脱敏时间。

实现为`scripts/cold_start_metrics.py`和显式参数链，复用原隔离、冷启动客户端、采样器及清理；没有改AgentENV后端、服务设置、镜像、代理或采样频率。指标文本仅解析本次需要的标量序列，不引入新依赖、周期轮询或单请求同步探针。

### 时间顺序进一步缩小了采样的影响范围

将本次七个客户端事件、按ID关联的创建日志和采样控制事件对齐：开启组的**最晚创建日志比第一次采样上传命令早0.876789秒**。源码顺序是先完成根文件系统解析，再调用创建服务并打印这条日志；因此七次根文件系统解析都已在首次guest采样部署前完成。客户端墙钟与单调时钟偏移的组内变化仅1.787微秒，远小于该间隔。

第一次上传命令仍比最后创建返回早0.159667秒，保留了“每个guest创建返回后立即部署”的行为；但最早采样就绪确认比最后创建返回晚0.024482秒。本组不能仅凭上传重叠就声称已确认实际采样点在创建期间产生，也没有为制造重叠增加等待或补跑。

这组证据足以说明：**本轮主要前置增量发生在guest采样部署之前，不是已经运行的guest周期采样在该阶段直接造成的。** 它没有区分regctl内部获取、进程运行和调度各用了多久；聚合指标没有请求ID，不能把51.657704累计秒拆回各角色，更不能用它解释旧运行的43秒请求。
