# 分段归属记录的离线验证（2026-10-16）

**采用每512字节一条“来源偏移＋改写代次”记录，可以在多次短读取后保留旧尾部身份。** 15项离线测试通过；模型还核对了已有48次单次读取变化，得到的27条旧尾部区间与上一轮完全一致。现有16槽、每槽256 KiB配置下，二进制元数据页对齐预算为192 KiB，比原64 KiB增加128 KiB。

交付是离线参考模型`scripts/provider_segment_model.py`、保存数据检查脚本`scripts/validate_provider_segments.py`及定向测试。运行时实现和采集器尚未接入新表；本轮没有启动沙箱或校准，原缓存物理并集保持。证据见[脱敏结果](evidence/provider-segment-model-20261016.json)，本机日志及独立检查器位于`.artifacts/provider-segment-model-20261016/`。

## 每段只保存来源偏移和自己的改写代次

此前[时序核对](PROVIDER_TAIL_CONTINUITY.md)证明了27条旧尾部，但38次比较跨过多次读取，缺少中间长度。新表在每次读取时直接更新覆盖范围，不再依赖采样器碰巧看到每一次请求。

选择512字节是因为当前请求、缓冲地址和长度都按512字节对齐，而host页为4096字节。每槽固定512条记录，无需动态拆分、合并区间。每条占16字节：

| 字段 | 大小 | 含义 |
| --- | ---: | --- |
| generation | 8字节 | 这段自己的改写代次；奇数表示记录正在更新，偶数表示更新结束 |
| source_offset | 8字节 | 这512字节在固定只读内存镜像中的起始字节偏移；`UINT64_MAX`表示未知 |

不另加长度或有效状态：每段固定512字节，未知偏移即可表示失效。代次必须独立于整槽，才能在前缀变化时继续确认未动的尾部；也能识别“覆盖后又读回同一偏移”，避免只比较来源偏移而遗漏中间改写。

适用范围仍是单个非池化、固定只读`memory/image.json`设备、每槽一个写入者，并且实际协商了GET_DATA。镜像层身份及缓冲生命周期必须不变；可写镜像、运行中更换来源层不在本次模型范围内。

## 覆盖前失效，完整成功后赋予归属

对一条记录的发布顺序为：代次加1变奇数 → 写来源偏移 → 代次再加1变偶数。运行时接入应沿用现有`AtomicU64`的`SeqCst`顺序。发布“未知”也更新代次，不能因为值原本未知就跳过。

| 动作 | 必须完成的更新 | 未覆盖尾部 |
| --- | --- | --- |
| 分配 | 所有来源偏移初始化为未知，再公布身份JSON | 初始未知，不推断此前内容 |
| READ填充前 | 在调用读取函数前，将整个请求前缀逐段发布为未知 | 保持原偏移和代次 |
| READ完整成功 | 确认返回长度等于请求长度且大于0后，逐段发布`请求偏移＋段内位置` | 保持原记录 |
| 短读、错误或取消 | 请求前缀保持未知；不按返回的部分长度恢复归属 | 保持原记录；槽位释放时再全部失效 |
| WRITE的GET_DATA前 | 先按复制前的原始请求长度使前缀失效，再发送允许内核复制的命令 | 保持原记录；WRITE完成不赋予快照归属 |
| 再次收到GET_DATA通知 | 再按此时待复制请求的长度失效，然后才发送命令 | 不因重复通知恢复旧归属 |
| 等待下一请求 | 协商了GET_DATA时不改表；未协商时仍采用原提交获取前整槽失效 | 不延迟请求等待采样 |
| 释放 | 全部段失效，原首部状态设为已释放，然后解除映射 | 全部失效 |

所有前缀失效都须在第一次实际缓冲改写之前完成。失效更新到一半时，尚未处理的段仍可显示旧归属，因为此时尚未允许负载写入；一旦开始填充，整个前缀已经未知。成功后逐段恢复归属时，数据读取已经结束，不会暴露未完成内容。

现有目标的FLUSH只同步镜像、DISCARD不接收用户缓冲、WRITE只读取用户缓冲；这些目标操作不为表添加READ归属。WRITE对缓冲的改写发生在更早的内核GET_DATA阶段，必须在那里失效，不能等目标返回只读错误后再处理。

### WRITE部分复制必须使用发出命令前的长度

实际内核`/home/yxli/linux-6.19.9-ioctl/drivers/block/ublk_drv.c`中，`ublk_map_io`先以`blk_rq_bytes(req)`构造从缓冲起点开始的写入范围，再调用`ublk_copy_user_pages`；见922–989行。`ublk_start_io`在复制后才可能将`io_desc.nr_sectors`缩短为实际复制量；见1257–1280行。

因此，后续接入须在发GET_DATA之前读取描述符，将原`nr_sectors×512`字节的前缀失效。不能等GET_DATA返回后再按缩短长度失效。复制失败、部分复制或再次通知均不恢复该前缀。此条件已加入定向测试。

READ前缀范围依据固定AgentENV基线的`OverlaybdTarget::handle_read`：只将`user_buf.subslice_mut(0, len)`交给读取函数。现有`dev.rs`在调用目标之前执行`begin`，在GET_DATA发送之前执行`before_get_data`。对应固定源码和协议证据沿用[旧尾部报告](PROVIDER_TAIL_CONTINUITY.md)及[GET_DATA实测](PROVIDER_GET_DATA_VALIDATION.md)，不重新运行协议设备对照。

## 采集器逐段核对，不要求整槽停止变化

接入后的每次槽位查询，仍在物理页号查询前后各读一次元数据。对前、后两次查询取得的四份段记录，只接受来源偏移和段代次均相同、代次为偶数且来源已知的段；任一观测为已释放则不接受。

新路径不要求旧首部的整槽代次或“本次完整读取状态”保持不变，否则前缀读取仍会把未改写尾部一起排除。进程启动身份、元数据文件身份、缓冲地址及容量检查继续保留。旧64字节首部和旧读取路径维持原语义。

这些段能否计入缓存物理量，仍按原条件判断：完整host页的所有字节都有稳定归属、物理页号稳定、对应guest缓存页身份稳定，当前版本与旧快照副本分开，并按物理页号去重。512字节分配对齐造成的host边界页继续单列。元数据段数和已知字节数都不直接当作物理驻留量。

## 格式和空间预算

建议将段表接在现有二进制首部后，从字节64开始，原8个64位字段不变。身份JSON保留现有`schema:1`及原字段，增加可选描述：`segments:{schema:1, unit_bytes:512, entry_offset:64, entry_bytes:16, count:512}`。只有启用私有观测且实际协商GET_DATA时公布段表；其他设备仍沿用原表和失效方法。

旧采集器只读前64字节，继续得到原单次读取记录；新采集器须检查新增描述才读取段表，保存时增加分段字段，不替换原`before/after/pagemap`。后续报告应分列原单条记录确认量、分段额外确认量及去重后的并集，旧结果不追溯改写。本轮已验证首部字节和段条目编码布局，真实读取器兼容性在接入时验证。

| 项目 | 每槽 | 16槽合计 |
| --- | ---: | ---: |
| 段条目 | 512条 × 16字节 = 8192字节 | 128 KiB |
| 首部加段表实际使用范围 | 8256字节 | 129 KiB |
| 按4096字节向上取整的映射预算 | 12 KiB | 192 KiB |
| 原映射预算 | 4 KiB | 64 KiB |
| 增量 | 8 KiB | 128 KiB |

表中是二进制文件/映射空间预算，不是实测物理驻留。身份JSON只增加格式描述。按每点四次完整元数据读取，读取字节数由4 KiB增至516 KiB，额外512 KiB；不含原有物理页号查询。每次READ对每个覆盖段做两次发布，共6次原子操作；4–128 KiB读取对应48–1536次新增原子操作，满256 KiB为3072次。实际CPU时间与采集影响须在后续私有接入中测量，不用离线Python耗时推算沙箱减速。
