## 改了哪些计数

原来两个CPU首次遇到同一个文件、时间段及记账组时，可能同时查到汇总键不存在。bpftrace 0.20.2编译出的插入操作使用`BPF_NOEXIST`（只在键不存在时创建），失败后没有重新查表累计；这种并发创建可能跳过一次更新。

`host_file_trace.py`现将CPU编号加入：

- 加入／移出的字节表、次数表；
- 四类事件的独立总计；
- 后备镜像加入事件的调用栈计数。

每次回调只读取一次CPU编号，同一次事件的表更新和日志均使用这个值。不同CPU不再首次创建同一个键；没有预填未知文件名单，也没有把总计修成与分组表一致。采集范围、0.1秒分段、未知归属保留、mincore覆盖检查及失败判定保持。

本机内核源码`include/uapi/linux/bpf.h:2036–2043`说明BPF程序执行期间CPU编号稳定；`kernel/trace/bpf_trace.c:2059–2082`对同一个raw tracepoint（内核事件回调）程序在单个CPU上防重入。编译结果进一步确认独立总计、字节、次数及调用栈四张表的键实际包含CPU编号，不只检查生成的字符串。

离线交错执行模型重现了“两个CPU都先查到空键，再分别尝试插入”的情况：原共享键保存1次，新CPU分开的键保存2次。这是针对已确认机制的模型验证，未将上一轮实际差额根因改写为已证实，也没有生成新的实测数据。

## 新格式先按CPU检查，不允许差额相互抵消

新日志明确写入`AGGREGATE_FORMAT 2`。字节表和次数表的键为`CPU、时间段、设备、inode、块设备号、实际记账组、事件类型`，独立总计按`CPU、事件类型`保存。低频统计汇总日志末尾增加CPU编号，原字段顺序不变。

解析器保留每个CPU的条目，逐CPU、逐事件类型比较分组次数和独立总计，再向原调用者返回按事件类型合计的次数。两个CPU一多一少、总数恰好相等，也会失败。字节／次数键集合不符、重复键、错误格式、低频日志CPU不符及非零丢事件提示仍失败。

mincore检查继续将目标设备所有CPU的加入减移出相加，不把不同CPU当成不同物理副本。未知初始容量和未知记账组规则不变。

结果中`aggregate_file_bins`继续表示不含CPU维度的原文件／时间段／记账组／事件类型键数；新增`aggregate_cpu_entries`单独表示CPU条目数，避免把键数增加误写成文件量或物理页增加。`event_counts`和`folio_event_count`仍是跨CPU的事件合计。
