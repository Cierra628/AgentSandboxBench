# 初始缓冲页的来源与分类（2026-10-16）

**10个已有恢复点中，1672–1728 KiB完整驻留页可以单列为“分配、注册后尚未用于请求的缓冲开销”。** 另有28–56 KiB完整页仅部分保留初始段，仍须作为整页未知量保留。两者逐点相加，恰好等于此前1700–1784 KiB“含初始未知段”的分类。

这里的初始化是建立缓冲和注册内存，不是把内容清零：实际代码使用`alloc`，没有显式清零，不能将这些页称为零初始化页。分类说明它们在本次分配中尚未承接设备请求，不说明字节值，也不等于注册额外增加了同样多的内存。

本轮只读固定源码、保存的段记录及页映射元数据，没有读取负载或缓冲内容，没有启动沙箱、设备或新校准。原4040 KiB完整缓冲驻留量、3476–4040 KiB未知字段及缓存物理并集保持。新分类仅在本报告中解释原未知量，不追溯改写旧结果。

证据见[脱敏结果](evidence/provider-buffer-initialization-20261016.json)，本机目录为`.artifacts/provider-buffer-initialization-20261016/`。输入仍为`20261016T050815Z-2211363/guest-cache/live-cache/restored/`，复用[上轮分类](PROVIDER_ACCOUNTING_OPTIMIZED.md)及[分段实测](PROVIDER_SEGMENTS_VALIDATION.md)。

## 首次请求前，整块缓冲已经注册，但没有清零

AgentENV固定基线为`2f48c9c78ec58e4d73c49aa07cb81d984a4a4184`，加此前已验证的槽位观测、GET_DATA和分段补丁。实际内核源码为`7e4e3f1145e0c02604b9afb140594764057e2f56`；沿用[实际内核身份核对](PROVIDER_SLOT_PROTOCOL.md)，不重新接触运行服务。`source-checks.json`保存11项源码核对：分配和注册文件与基线逐字节一致，发布和请求顺序与成功构建保存源码一致，内核相关文件与该提交一致。

按每个槽位的实际执行顺序：

1. [`io_buffer.rs:126–146`](../../AgentENV/storage/ublk/src/io_buffer.rs#L126)：`UserBufferInner::new`调用`alloc(layout)`分配完整容量，随后调用`ring.register_buffer(this.as_mut())`；没有`alloc_zeroed`、`fill(0)`或初始化写入。实际每槽256 KiB、512字节对齐。
2. [`uring.rs:340–363`](../../AgentENV/storage/util/src/io_ring/uring.rs#L340)：注册传入完整`iov_base`和`iov_len`，不是只注册第一次请求的长度。实际内核`io_uring/rsrc.c:305–325,780–832`把更新注册转入`io_sqe_buffer_register`，再调用`io_pin_pages`；`io_uring/memmap.c:40–68`覆盖地址范围内所有页，以`FOLL_WRITE | FOLL_LONGTERM`固定这些页，即取得长期可写的物理页引用。该路径不对缓冲做内容清零。因此，未被请求覆盖的尾部仍驻留，有直接的注册机制依据；无需假设它们保存了缓存内容。
3. [`dev.rs:144–188`](../../AgentENV/storage/ublk/src/dev.rs#L144)：上述分配、注册成功返回后，才建立`SlotObservation`，之后才发送首次`prep_slot/FETCH_REQ`。OverlayBD没有额外每槽缓冲，`init`也不接收该缓冲；启用观测时设备池被拒绝，见`overlaybd_target.rs:341–346`、`ublk-daemon/src/main.rs:327–334`。所以不存在先用旧设备处理请求、再把段表重置为初始值的路径。
4. [`slot_observation.rs:43–104`](../../AgentENV/storage/ublk/src/slot_observation.rs#L43)：以`create_new`新建元数据文件，零长度文件扩展后的映射使段代次初始为0，再把所有来源偏移设为`UINT64_MAX`，最后发布身份JSON并返回。这里清零的是元数据，不是设备缓冲。
5. [`dev.rs:117–139,188–234`](../../AgentENV/storage/ublk/src/dev.rs#L117)：首次FETCH若返回WRITE取数通知，也先使原请求前缀失效，再发送GET_DATA；正常READ则先调用`begin`使前缀失效，才进入实际读取。完整READ成功后才发布来源。后续循环使用同样顺序；短读、失败和释放都不会恢复代次0。

内核向用户缓冲写入数据的普通复制路径仅用于WRITE，长度为请求前缀；READ完成只从缓冲取走数据，见实际内核`drivers/block/ublk_drv.c:922–1009,1309–1324`。用户态READ只传入`subslice_mut(0,len)`，WRITE只读取`subslice(0,len)`；flush、discard及不支持的操作没有额外缓冲改写，见`overlaybd_target.rs:191–244,380–395`。等待FETCH不会自动填充未用尾部，也不需要通过拖延请求来保持分类。

## 只有整页八段都未用，才能单列整页开销

此分类限于上述固定的非设备池、用户缓冲、已协商GET_DATA路径。本轮保存身份记录确认16槽、标志24646、`before_overwrite`和512字节段表。准入条件为：

- 同一进程、设备和槽位的分配身份连续；四份首部的地址、容量相同，均未释放。不要求整个槽位的请求首部不变，因为前缀活动不影响未用尾部。
- 整张4096字节host页完全在缓冲分配范围内，页内八个512字节段的四份记录全部相同，且每段都是`generation=0, source_offset=UINT64_MAX`。代次每次覆盖前递增，因此在没有64位回绕的条件下，这表示本次分配以来没有请求覆盖这些段；不是“最后一次读取失败”。本次保存的最大段代次为1552。
- 两次页映射记录完全相同、页驻留且物理页号可见。按物理页号去重；任何已观测别名若为边界页、记录变化、已用或释放，都不按整页初始开销准入。已确认缓存集合与这批页无交集。

只要八段中有一段已进入请求处理，就不把整页算作未用开销；初始部分与其他部分同在一张物理页，不能把部分字节换算为可扣除的整页物理量。段记录变化、后续失效、分配变化及边界页也不因仍含初始段而放宽条件。

这一判断追踪的是本次缓冲分配的使用状态。`alloc`可能取得分配器重用的内存，源码没有提供初始字节来源；因此不推断内容全零，也不从“尚未用于请求”推断整个host物理页在系统历史上从未保存过文件内容。
