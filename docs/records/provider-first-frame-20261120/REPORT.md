# provider 首帧：真实记录是 128.310 ms，按相同输入离线重放没有复现

基线 `handoff-20261118`，提交 `dd9ba4c9ebae59db68055da5e8ad566b87d6eb16`。指定检查 `bash scripts/check-platform-offline.sh` 退出 **0**，末行 `status=PASS scope=platform-offline`。已读取 HANDOFF 分工边界。本轮只重放保存的槽位记录，未打开实验卷、运行沙箱或修改采集器。

**判断：128 ms 是真实发生的一次以 CPU 执行为主的慢帧，不是这批槽位的固定构造成本。** 上一轮实际保存了第二帧及分项：同一个子进程第二次构造只用 **1.178 ms**。离线换新子进程会看到几毫秒的首次开销，但 384 次构造没有一次达到 10 ms。现有证据不能再区分“该进程首次构造时特有的运行状态”和“不一定发生在首次的偶发 CPU 开销”。

## 原始两帧：慢的是构造，不是等待读盘

对象均为 restored-1。单位 ms；整帧是 `ProviderCache.snapshot` 的时间，不含其后的四来源身份核对。

| 真实批次 | 首帧整帧 | 首帧构造墙钟 / 线程 CPU | 第二帧整帧 | 第二帧构造墙钟 / 线程 CPU |
|---|---:|---:|---:|---:|
| 旧七支串行，该批首支 | 1.873 | 1.125 / 1.125 | 1.567 | 1.088 / 1.088 |
| 独立进程，只查该支 | 129.150 | **128.310 / 128.133** | 1.741 | **1.178 / 1.179** |

进程首帧构造期间，墙钟仅比线程 CPU 多 **0.177 ms**；不能用线程长期没被调度或阻塞等待 128 ms 来解释。16 个槽位的元数据首读、页表读、元数据复读都在另一计时段。本次只观察到一对真实进程帧，能说“这一对只有首帧慢”，不能说“每个新进程的首帧都慢”。旧串行另一个角色 restored-2 的**第二帧**构造也有 8.602 ms，长尾并非只能发生在首帧。

## 重建的输入：页表数据只差 16 字节

| 每帧输入 | 旧串行 | 独立进程 |
|---|---:|---:|
| 已绑定设备 / 队列 / 槽位 | 1 / 1 / 16（设备 7） | 1 / 1 / 16（设备 8） |
| 每槽位头部 / 每份分段条目 | 64 B / 512 条 × 16 B | 同左 |
| 两份槽位元数据（前、后） | 264,192 B | 264,192 B |
| 槽位页表记录 / 字节数 | 1,038 / 8,304 B | 1,040 / 8,320 B |
| 合计交给 Python 的输入字节 | 272,496 B | 272,512 B |

两批不是同一台运行中的设备，但工作量几乎一样；更强的对照是独立进程**自身第二帧**：输入字节数未减，构造耗时却从 128.310 降到 1.178 ms。

基线 `scripts/provider_slot_cache.py:135–164` 没有独立的构造函数。重放直接使用 **生产 snapshot 的同一个 Python 代码对象**：在离线调用中把三个 `pread` 的返回值替换为重建的字节，不改磁盘上的源码。用队列清单和槽位名对上 16 个槽位；用原 ROW / SEGMENT 布局重打包前后头部与条目，用保存的页表条目重建页表字节。每次读取检查顺序、偏移和长度，沿用原 `stage_costs.record_build` 的计时边界（解包、建列表、组装并追加记录）。每次均检查 16 次构造；每个子进程最后一对输出逐字段等于原始两帧。宿主身份检查和实际 I/O 不是这个离线实验的目标。

## 离线分布：区分“数据是首帧”与“进程是第一次调用”

同一宿主，CPython 3.12.3。每批开 **8 个**新的 fork 子进程，每个顺序重放 12 对帧；一半先放原首帧，另一半先放原第二帧。每对保持两份返回记录同时存活。没有预热、没有丢弃第一次，没有为追平 128 ms 人工放大堆。单位 ms，括号内为最小–最大；P95 用线性分位数。

| 构造输入与环境 | 首次调用 N / 中位 / P95（范围） | 后续调用 N / 中位 / P95（范围） |
|---|---|---|
| 旧串行的原始两帧，离线新进程 | 8 / 2.812 / 4.308（2.227–4.322） | 184 / 1.118 / 2.690（0.823–9.765） |
| 独立进程的原始两帧，离线新进程 | 8 / 4.165 / 4.324（2.872–4.371） | 184 / 1.201 / 2.766（0.838–9.366） |

独立进程批的数据若按**帧身份**而不是调用次序汇总：原首帧 96 次中位 **1.207 ms**，原第二帧 96 次中位 **1.206 ms**。首帧数据本身并不贵。离线记录了每次整帧前后的垃圾回收计数：16 次伴有第 2 代回收的调用，构造中位 **9.022 ms**；其余 368 次为 **1.146 ms**。这说明内存对象管理是有依据的排查方向，但不是原批发生了同一事件的证据。原批没有采集垃圾回收起止、缺页差值或当时的调用栈。

**环境差异决定能排除什么。** 本次机器上仍有其他用户，开始时 load 为 0.36 / 0.35 / 0.69；没有重建原进程的堆、分配器和 fork 后写时复制状态。两份存档 JSON 在计时前已读入，重放后用 mincore 检查，旧/新存档的 4,866 / 631 个文件页均驻留。重放在内存中供给已打包字节，未清宿主页缓存；384 次整帧均无主缺页。它验证的是**相同数据的构造成本**，不是原机器冷态下的完整首读。真实构造代码操作的是已经读入 Python 的字节，没有该段内的文件读取或显式导入/JIT。固然不能靠热态重放否定冷启动，但若要解释原来的 128 ms，首要考虑的是会消耗线程 CPU 的进程内状态，而不是单纯等文件从盘上读回来。

## 七进程是否值得再跑、止损线怎么选

**技术上仍可将七进程完整测量列为候选，不能据此宣布可进 1 秒，也不自动撤销上轮止损。** 单支 645.601 ms 是从子进程接令到身份证据和结果就绪；511.144 ms 是其中的宿主查询窗，旧同支的 408.762 ms 也是宿主查询窗。128 ms 不属于已证实的固定成本，没有依据给每个进程加一次，或从七进程墙钟直接减一次；七进程完整墙钟仍未知。

- **若要沿用原实验决策，建议保留 613.143 ms 及原终点（结果就绪）。** 上轮 645.601 ms 确实越线；若再遇相同形态会再次停，但本轮没有估出复发概率。原线取自较窄的旧查询窗，用来约束较宽的结果就绪窗，是保守的操作门槛，并非同口径性能比较。
- **若要比较查询本身，先对齐窗口，而非先加大数字。** 仍以旧同支 408.762 ms 为基准时，查询窗界线就是 613.143 ms；本次 511.144 ms 在此线内。若另立“相对当前进程版查询退化 50%”的门槛，则为 **766.716 ms**，只适用于查询窗。其基准已含异常首帧，作为保护线更松；不应拿它追认上一轮的结果就绪时间。是否采用新规则由实验负责人开跑前决定。

下一步若获准做真实测量，最小补充是在每个查询进程的两帧构造前后记线程 CPU、次/主缺页、各代垃圾回收起止，在三次读取处保留现有独立计时。这样能区分 I/O 等待、首次分配/写时复制和恰在构造时发生的长回收；不需要清全机页缓存。本轮未实施该采集、未运行七支。
