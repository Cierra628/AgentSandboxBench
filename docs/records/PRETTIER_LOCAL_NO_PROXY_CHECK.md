## 实际规则：普通新IPv4连接被拒绝，公网DNS在前面放行

保存的真实网络命名空间规则显示：

1. guest流量首先进入`AGENTENV-EGRESS`，允许已有连接的返回流量；
2. **到`8.8.8.8:53`的UDP和TCP请求被提前允许**；
3. 其余流量经过内部网段拒绝规则，最后进入`AGENTENV-USER-EGRESS`的全部拒绝规则。

因此，`allowInternetAccess=false`在这个后端上不等于完全断网。普通新IPv4连接会被拒绝，但DNS例外先于用户策略。此次没有发送外网探测，也没有采集实际DNS流量；规则允许DNS不能当作已经发生DNS请求，更不是使用17891。

源码与现场一致：`AgentENV/src/sandbox/network/slot.rs:935–976`会寻找非回环、非未指定的IPv4 DNS服务器，找不到时回退`8.8.8.8`；服务日志实际记录该回退。`network/policy.rs:312–385`把DNS放行放在内部网段限制和用户拒绝规则之前。因此，给用户的`denyOut`再加DNS地址也无法覆盖前面的静态DNS允许。

原检查器只接受内部DNS，这个前提与后端实际语义不符；原始运行仍保留`FAIL / local-no-proxy-network`，没有放宽规则重写成PASS。查询后的进程身份复核及最终写文件边界检查因该异常未完成。离线分析已逐条确认保存规则中除已有连接和这两条DNS外没有其他允许项，不需要为了读取同一证据重跑成功创建。

**建议以用户的实际目标为准：禁止使用17891，保留AgentENV默认DNS行为并明确记录例外。** 不建议为无代理测量额外改后端或主机DNS。如果需要完全断网，应另列隔离要求，不能仅依据当前API字段承诺。

## 原因明确：缺了启动必需的`regctl version`

私有日志的顺序是：依赖准备 → 调用regctl → 本地入口写`blocked`并退出78 → 后端尝试获取`regctl-linux-amd64` → 直连GitHub连接重置 → 服务退出。没有成功下载记录；本轮确有一次依赖直连尝试，不能记录为纯离线成功。外层已清除代理并对私有容器显式置空六种代理变量，没有回退17891。

源码`AgentENV/src/setup/deps.rs:384–418`直接解释了该行为：`ensure_regctl()`先执行精确的`regctl version`；只有退出成功且版本原文包含独立字段`v0.11.5`才复用。检查失败便删除私有入口并调用下载器。初版白名单仅覆盖镜像清单与配置，遗漏了服务启动命令；不是镜像lower缺失，也不是guest任务失败。
