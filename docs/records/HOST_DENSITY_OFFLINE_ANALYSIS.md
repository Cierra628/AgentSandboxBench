# 密度对照离线分析：host日志等待影响C4窗口，P0分项存在刷新错位

[完整分析与数值表](../../results/host-density-offline-20261102/ANALYSIS.md)已完成，原始12组点表、峰值、百分比及拟合保持。只读保存日志、文件元数据和源码，没有新guest、驻留查询、负载数据读取或运行设置改动。

## C4额外时间主要在本地日志记录，不在工具执行

原执行版本的call先等待subprocess.run返回、写stdout文件，再记录调用结束计时，之后写events.json，最后返回。C4共享guest-03／04的stdout文件mtime约在调用后63.816／63.413秒，事件却在111.010／111.139秒结束，中间47.194／47.726秒落在host日志记录路径。guest-02事件在62.215秒结束，call返回后的状态时间又晚48.797秒，主要空档在events.json写入期间；从状态时间到采样停止调用仅约0.0004秒。

因此原replay duration含本地stdout落盘，却漏掉随后写events.json的时间，不能作为纯RPC耗时。这是计时边界及标签需要澄清的问题，不将原值重算成更快的请求。mtime由原保存程序的copy2保留；分析用同一host的wall／monotonic锚点定位几十秒的区间，不把文件时间当精确子进程计时。没有当时的系统调用／等待栈，不能进一步指定open、write、close、锁或调度中的唯一原因；期间脏页持续写回，文件系统争用是优先候选。

共享组原窗口112.081秒，中位数82849.301 MiB；另算截至最晚stdout文件mtime的64.390秒敏感性窗口，中位数38753.910 MiB。独立组原窗口71.721秒、中位数61246.828 MiB，对应敏感性窗口71.336秒、中位数61170.828 MiB。长尾足以反转中位数排序；两边峰值均不变。敏感性值单列，不替换原动作及下载窗口，也不当作新实验。

## P0分项与current不是原子拆账

运行内核6.19.9+的build ID与本机build目录vmlinux一致。源码显示current直接读页记账计数；file来自NR_FILE_PAGES的分级／按CPU汇总，读取时尝试按更新量刷新，并有后台周期刷新，不与current构成原子快照。

12组中5组P0出现file大于current，P0结束后0.129～0.295秒出现首个不再大于current的周期点。N=10独立组file从83394.984降至48665.828 MiB期间，current仍约50074～50134 MiB，不能仅归因于两次用户态读取相差几百微秒。保存的序列确认分项更新时点错位；没有具体rstat事件，仍不能还原是哪一次汇总导致每个差值。P0驻留为0的验收来自mincore，未依赖file分项；P1未检出不足下界也不等于已证明组外容量为零。

## 下一步建议：先离线修正计时边界，不追加实跑

在subprocess.run返回后立即把结束时刻写到内存，stdout和events.json落盘各自计时；原控制程序整轮保留。用临时文件模拟慢日志写入，以命令调用、日志成本和整轮时间不会混算为完成条件。P0只增加分项不同步标记，不通过延迟请求、额外回收或强制驻留改变数据。是否补C4一对实跑另由用户检查，本阶段不自动执行。
